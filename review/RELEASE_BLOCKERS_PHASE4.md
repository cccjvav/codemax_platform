# 第四批：可信查单与管理员收款工作台

状态：本地实现与双后端验收已完成；本提交的最终六项CI以交付回复绑定SHA/run为准，外部未执行项仍不签收。上一批交付为fecbb49，本批不继承它的CI结果。

## 交付范围

- 新增 `/admin/payments` 登录外壳、管理员只读订单发现、冻结合同/凭证/尝试历史，以及人工核账、历史绑定和显式查单操作。无依赖/schema变化，仍沿用0010。
- Native下单与商户单号GET查单共用有界HTTP交换，固定微信域名、禁止重定向/压缩，真实平台应答验签；不仅回调要验签。
- 查单开始先持久，网络期间不持数据库写锁；回来重查并锁住管理员权限/凭据。完整匹配SUCCESS才将成功事件、唯一收款凭证和paid原子提交，精确重试不重复收入。
- 未可信响应、HTTP错误和超时保留未知；NOTPAY/CLOSED/REFUND只记录观察，不关单、不退款、不撤销已有权益。异常筛选指有历史记录，不是已实现异常结案。
- 三种财务写接口增加Cookie来源/Fetch Metadata检查；Bearer仍需验证，来源头缺失非浏览器客户端兼容，不自称完整CSRF token系统。

实际使用：[管理员操作手册](../docs/PAYMENTS_ADMIN_GUIDE.md)。Windows继续采用VS Code CMD、Conda和系统Node；不开放生产/docs来代替管理页。

## 调查依据与取舍

官方普通商户Native单号查询、API应答验签/探测和公钥ID来源列在操作手册。API文档金额等字段对未付订单可选；SUCCESS仍保守要求完整金额/CNY、NATIVE、商户/app、原单号、流水与带时区付款时间。不复制官方示例中的MICROPAY类型。

审核中发现原Native响应未验签、SameSite/JSON保护没有额外服务端来源检查；后者的合成Cookie跨源测试确实进入了业务处理，不代表已证明真实浏览器能越过Lax/CORS。此处补强三种财务写，未扩展全站认证架构。

前端同账号/跨账号旧结果都需序号拒绝；退出/abort不能承诺撤销已发出的服务端操作。成功应答不能先settle提交、后另写audit，否则提交故障会造成已收款却丢核查过程。本批把audit纳入原子边界。
