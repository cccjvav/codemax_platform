## 3. 问题清单

### P2（应该修）

#### P2-1 TD-214 与 `app/tools/support.py::_retrieve_articles` 相反；RAG 每次请求读整张文章表 【代码阅读 + 文档比对】 · ROADMAP O-02 / 交接 F-07

- **现象**：`TECH_DECISIONS.md` TD-214 写"RAG 索引按 `(count, max(id))` 指纹缓存复用 … 先用一次极轻的 `select(count(id), max(id))` 算指纹，命中缓存就完全不必把全表正文捞进内存 … 第二次查询 250.4 → 2.8 ms（89×）"。现行代码：`rows = select(Article).order_by(Article.id)` **全表含 `content` 捞出** → `json.dumps([(id,title,content)…])` → SHA-256 作指纹；只有分词 / 建索引命中缓存。代码注释自己承认："代价：每次读取语料正文"。改代码时没有回写 TD-214。
- **影响**：① 权威决策文档给出与代码相反的实现说明与性能数字；② `/support/ask` 不鉴权（每 IP 每分钟 10 次），专业问题分支每次请求的数据库传输量 ∝ 语料总字节，且 `json.dumps + sha256` 在事件循环里同步执行；`test_support_rag_perf` 用 200 篇 × 约 1 KB 语料，看不出来。
- **建议**：`sys_article` 增加 `update_time`（迁移 0018，`save_article` 更新），指纹改回 `select(count(id), max(id), max(update_time))`；或在数据库侧算摘要（PG：`md5(string_agg(id||':'||md5(content), ',' ORDER BY id))`）。同步改写 TD-214（保留历史数字并注明"实现已于 2026-09 改为 …"）；在 `test_support_rag_perf.py` 增加"命中缓存时不 SELECT `content` 列"的 SQL 事件断言（`diagrams` 已有同款 `load_only` 断言可照抄）。

#### P2-2 `sys_order.user_id` 缺少普通索引 【代码阅读】 · ROADMAP O-08

- **现象**：`full_init.sql` / `app/models.py` 中 `sys_order` 只有 `uq_sys_order_user_pending ON sys_order(user_id) WHERE status='pending'`。`GET /shop/orders`（`order_history`）执行 `WHERE user_id = ? [AND id < ?] ORDER BY id DESC LIMIT 50`，部分索引只覆盖 pending 行，PostgreSQL 会顺序扫描；外键本身也无索引。
- **建议**：迁移 0018 `CREATE INDEX idx_sys_order_user ON sys_order(user_id, id)`，`models.py` 同步 `Index(...)`；`tests/test_schema_sync.py` 会强制两边一致。顺带评估 P3-17。

#### P2-3 两个微信入站回调的加固程度不一致，验签逻辑三处重复 【代码阅读】 · ROADMAP 未列

#### P2-9 解析前没有请求体预算；422 回显大输入 【实测】 · **ROADMAP A-01（P1）/ 交接 F-01**

- **现象**：`main.py` / `app/middleware.py` 没有任何请求体大小或读取时间上限；Starlette/FastAPI 默认先把整个 body 读完再交给 pydantic，字段 `max_length=10000` 在**读完 2 MiB 之后**才生效；默认 422 处理器把 `input` 原样放进响应。探针：匿名 chunked POST `/tools/mermaid` 2 MiB → 服务端读完 2,097,163 B，回 2,097,303 B。只有两个微信回调自己做了 64 KiB 流式上限。`/support/ask`、`/tools/er`、`/tools/word-export`、`/auth/register`、`/oauth/token`、`/shop/orders` 等全部 JSON/表单 POST 同理。
- **评级说明**：ROADMAP 定 P1（公开前必须）。本报告列 P2 的原因：`docs/DEPLOY.md` 要求的 nginx 默认 `client_max_body_size 1m` 能把单请求限到 1 MiB，且现有每 IP 限流能限次数；但 **Compose 直连部署没有任何上限**，且回显放大 1:1。不影响执行顺序 —— 按 ROADMAP G1 首位处理。
- **建议**：一个 ASGI 中间件按路由前缀设定原始 `receive` 字节预算（普通 JSON 路由 64 KiB、`/tools/er` 与 `word-export` 按现有 SQL 上限放宽、回调保持自身逻辑），超限立即 413 并停止读取；注册 `RequestValidationError` 处理器，剔除 `input` 或截断到 200 字符。测有/无/伪造 Content-Length、分块、超时取消四种情形。

#### P2-10 签名下载 `GET /dl` 每次全文件哈希、无限流 【代码阅读】 · **ROADMAP O-01（P2）/ 交接 F-06**

- **现象**：`shop.py::serve_download` 依赖链里没有 `rate_limit`；每次请求先 `run_in_threadpool(verify_snapshot, …)`（`delivery.file_digest`：1 MiB 分块 SHA-256、30 s 期限）再 `FileResponse`。合法快照上限 512 MiB。签名链接在 `DOWNLOAD_URL_TTL` 内可被任何持有者重复请求（含 Range 请求、中断重连）。
- **影响**：一条泄露 / 被分享的链接即可让单进程 CPU 池与磁盘持续满载；`POST /download/{order_no}`（发链接）有限流而 GET（真正干活的）没有，是限流放错了位置。
- **建议**：`GET /dl` 加独立限流桶（按 IP + `order_no`）；哈希结果按 `(key, mtime, size)` 做进程内短期缓存或在发链接时校验一次并把校验时间签进链接（保持每次请求仍查退款凭证与订单状态，不缓存权益）；先用合成 512 MiB 文件测量再定阈值（ROADMAP O-01 的"先测量"）。

#### P2-11 同一订单可并发进入两次预支付 【实测】 · **ROADMAP A-03（P2）/ 交接 F-03**

- **现象**：`POST /shop/orders` 无限流、无同单在途标记；已登录用户并发两次 POST，在提供方桩内屏障等待时观察到 **2 个同时在途的 `native_prepay`、1 个订单、0 个凭证、两次 200**（`RATE_LIMIT_TOOLS=1` 也拦不住，因为该路由根本没挂限流）。
- **影响**：不是重复扣款（同一 `out_trade_no`，渠道幂等 + 收款唯一凭证）；是配额消耗与"两个预支付应答先后落地"的复杂度（后到的 `prepay_unknown` 事件可能覆盖前一个观察）。
- **建议**：① 路由加 `rate_limit('order-create', 'RATE_LIMIT_TOOLS')`；② 订单行上加"预支付在途租约"（`prepay_lease_until` 列或 PaymentEvent `prepay_started` 事件），第二个请求直接返回现有 `code_url` 或 409；不得持数据库锁等待网络。

#### P2-12 表单登录不检查来源（login-CSRF 路径开放） 【实测 + 代码阅读】 · **ROADMAP A-04（P2）/ 交接 F-04**

- **现象**：`POST /auth/login` 带 `Origin: https://untrusted.invalid`、`Sec-Fetch-Site: cross-site` 仍 200 并 `Set-Cookie: access_token=…`。Cookie 为 `SameSite=Lax`：Lax 限制的是跨站请求**携带**已有 Cookie，不阻止跨站顶层表单 POST 导航的响应**写入**新 Cookie。
- **影响**：攻击者可让受害者浏览器悄悄登录到攻击者账号；随后受害者在本站的操作（例如下单付款）落在攻击者账号下，权益归攻击者。财务写端点已有 `require_finance_origin`，但**登录本身**是所有后续操作的入口。交接报告要求先做浏览器双来源 PoC，本报告同意；服务端接受是已证实的一半。
- **建议**：`/auth/login`（及 `/auth/register`）复用 `require_finance_origin` 的判断逻辑：有 `Sec-Fetch-Site: cross-site` 或 `Origin` 与本站不一致时拒绝 403；保留无来源头的非浏览器客户端。测两种拒绝与一种合法通过。
