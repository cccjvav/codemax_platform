# 资金与交付权益：第三批实施记录

## 结论与范围

承接已通过六项CI的第二批 `f37bb8d`。本批落实收款凭证原子提交、流水唯一归属、预支付尝试记录与本地文件交付快照。**仍不能签收真实收款上线**：自动查单/关单/退款/争议、预支付响应验签、运营核账界面和真实商户联调尚未完成。

不新增项目依赖、不操作业务库、不调用真实商户/模型；保留Agnes、关闭embedding和动态Chromium、保留已付款用户重领链接的权益。本批是现有固定数字文件链路，不把它冒充定制服务的需求确认、里程碑、验收与退款流程。

## 1. 收款凭证不能只是一条日志

`payment_receipt`每张订单最多一条，`(source, transaction_id)`也唯一：同一来源流水不能被两张订单重复认领。金额必须为正、币种CNY、来源受限，人工凭证必须包含操作人和依据。

`payment_ledger.settle`先取得订单写锁并刷新状态，再核对冻结渠道/商户/app、金额和已有凭证，最后把凭证与paid状态一次提交；任何失败同时回滚。不同订单争抢同一流水由数据库唯一约束兜底。同一流水重复通知成功且不新增凭证；同单不同流水409，不再假装是正常重复，也不覆盖第一次的交易号或操作人。关闭订单的迟到成功仍可结算。

回调保留真实RSA/AES与商户/金额校验，记录提供方带时区的success_time和本地received_at，二者用途不同。未接入退款等事件返回422而不是虚假SUCCESS；需要后续接入与告警，不能用重试代替退款处理。

### 人工确认接口有意收紧

管理员、manual模式、订单自己的manual渠道，三者均需满足：

```http
POST /shop/orders/{order_no}/confirm
Content-Type: application/json

{"reference":"BANK-20260916-0001","amount":19900,"evidence":"核对的账单位置及到账依据，不粘贴完整银行资料"}
```

上例是格式示例，须换成实际核实的唯一参考号，不能复制为每单同一个值。reference使用1–64位字母数字及 `._:/-`。amount为实际核对的整数分金额，必须精确等于订单；evidence为3–500字符，不能空白。不要把同一笔银行收款重复分配给多张订单，本批未实现拆分收款。重复请求返回第一次的confirmed_by，changed=false。操作日志仅补充检索，不再作为唯一财务依据。

管理员可读取 `GET /shop/admin/orders/{order_no}/ledger?before=...`：最多50条事件及一条凭证，禁止缓存，不对普通客户开放。当前是API，不是假装已经做完了运营网页或银行账单自动核对。

## 2. 预支付失败不等于没有发生外部操作

`payment_event`先持久化prepay_started，再调用提供方；收到可用二维码记prepay_ready，网络/解析等失败记prepay_unknown。进程中断或结果提交失败可能只留下started，仍按未知处理，不能当作未付款。重试复用持久订单号，使用新的attempt_id把每次开始与结果关联，不存服务商原始正文、密钥或付款人openid。

这不是完整对账系统；多个并发尝试可能使用同一商户订单号，外部结果仍需查询与核对。这里未生成假的查单或退款成功记录。

## 3. 买到的是下单时的文件，不是当前配置指向的任何文件

新下单先把本地商品复制到 `.snapshots/<SHA-256>/<文件名>`，订单保存key、digest和size，再进行收款。对象按内容寻址，硬链接发布不覆盖既有快照，应用的put拒绝改写该目录。改STORAGE_PRODUCT_KEY或覆盖原商品文件，都不会换掉已购买的字节。

复制分块进行、最多512MiB、检查30秒截止、每进程最多两个复制任务，并移到线程执行；POSIX上同步文件及发布目录。原文件复制过程中变化会拒绝。文件未准备或存储不支持发布时，下单503，不先收款。Windows/NTFS硬链接、实际磁盘及备份恢复仍需实机验证。

发链接与下载快照时都检查哈希；损坏拒绝交付，不把其他文件作为替代。恢复相同字节后可重领链接；downloaded依然不是权益消费完毕。文件系统管理员仍是信任边界，不能把本地目录当WORM或防主机入侵存储。存储ROOT变更必须搬迁全部快照；只改配置不会自动搬文件。失败下单可能留下未引用快照，不能在错误清理中误删已经售出的对象。

## 4. 0010迁移：不猜历史、不伪造旧收入

新增订单支付/交付字段、payment_receipt、payment_event及PostgreSQL保护触发器。已绑定订单的客户、名称、金额、币种、渠道/商户/交付指向不能覆盖；凭证和事件禁止UPDATE/DELETE。数据库所有者仍可改触发器，这不是不可抵赖审计或法定会计账簿。未来纠错/退款必须另建追加式工作流，不能直接改旧凭证。

0009旧库停写备份后运行migrate；0008无账本库仍可adopt，旧基线列集合已固定，不再随最新ORM增加字段而变化。维护器识别顶层事务控制，允许函数体内部BEGIN，拒绝顶层COMMIT/START TRANSACTION等；这只是防误加事务包装，不是任意SQL沙箱。0001–0009历史文件不改。

迁移保留旧订单状态、金额、流水和所有权；新渠道/交付字段留NULL、凭证表不自动回填。旧paid/downloaded仍有购买权益，但不能靠今天的配置猜文件。管理员核实原交易和原交付物后调用一次：

```http
POST /shop/orders/{order_no}/legacy-binding
Content-Type: application/json

{"payment_mode":"manual","source_key":"经核实的原交付文件.zip","evidence":"原合同和交易记录核对依据"}
```

只有尚未绑定的订单能使用，绑定与审计事件同事务；不改变历史金额/状态、不凭空生成收款凭证。新订单或已绑定订单拒绝覆盖。旧已付款订单不能通过confirm重记收入；历史凭证导入和账务纠错仍待专门工作流。生产禁止绑定mock。

**部署必须把数据库备份与完整storage目录一起恢复演练**。不得重跑旧full_init、删账本绕过迁移、手工删除快照或用UPDATE修改已接受凭证。
