# 文档方案选择与执行契约

## 结论与取舍

采用“目录内 README + 单一生成站点 + 可复算清单”，不推倒重建。
用户上传的[旧方案](../代码级文档方案旧.md)和[新方案](../代码级文档方案新.md)保留原文，属于参考提案，不是已经实现的规格。

| 方面 | 旧方案 | 新方案 | 本仓库选择 |
| --- | --- | --- | --- |
| 阅读入口 | 每个源码目录 README | docs 镜像目录和文件页 | 保留原目录入口，站点负责聚合 |
| 覆盖检查 | 提示 Agent 查漏 | manifest 驱动 | Git 已跟踪和未忽略新增文件反向扫描 |
| 源码定位 | 手写行范围 | 符号、行范围和证据 | Python AST + 限定名 + 完整 SHA-256 生成 JSON；其他语言声明文件级覆盖 |
| 更新策略 | 修改文字约定 | 中间 JSON 与渲染状态 | 源码变化使 README 指纹检查失败；复核后显式刷新 |
| 解释可信度 | 要求详尽 | JSON 字段和 TODO | 机器证明结构，人工负责业务含义；不声称 JSON 消除幻觉 |
| 生成物 | 缺少明确排除规则 | 缓存目录排除 | 两条例外有负责人及理由，禁止给压缩依赖生成伪解释 |

不采用两套并存的模块 README：重复解释会让维护成本翻倍，并产生“哪份才是准的”的问题。
不逐行翻译每个简单分支：优先解释输入、输出、权限、状态、失败边界与修改影响，源码页承担逐行阅读。

新方案仍有需要纠正之处：`parsed`/`rendered` 的完成口径前后不一致；示例中模块目录有省略 `src` 和保留 `src` 两种写法；嵌套代码块应使用更长外层围栏；同名方法需要限定名；本地 Markdown 不保证支持 GitHub 的行号跳转。不能原样复制后宣称验收完成。

## README 范围与内容

执行入口：[check_docs_contract.py](../scripts/check_docs_contract.py)。规则：[documentation_policy.json](documentation_policy.json)。

1. 每个含识别到的源码、配置、模板或可读资源的目录必须有自己的 `README.md`，不能用父目录的说明糊弄过去。根目录同样检查。
2. 常见扩展名与特殊文件名集中在脚本中，未知后缀的 UTF-8 文本也必须归属，不能靠新语言后缀绕过。密钥形态和符号链接拒绝发布。Markdown 文档、缓存、依赖目录、密钥和被 Git 忽略的构建物不当作源码。
3. 生成 JS 归 `app/static/README.md`；npm 锁文件归根 README。例外必须显式写明 owner 和 reason。
4. 四个非空章节：模块职责、文件与入口、数据流与约束、变更与验证。自动文件表必须完整且没有重复生成区。
5. 任何源码字节改变都会改变 SHA-256，即使函数名和行数未变，检查也会失败。
6. 新目录、新文件、缺失 README、清单过期都必须失败。`--write` 只刷新已有生成区，不自动编造职责或补空壳 README。

本次实际扫描发现 `docs/documentation_policy.json` 所属的 `docs/README.md` 缺失，已补齐；其他现有源码目录已有 README。之后新增目录同样受到约束，不能只校验本次列出的目录。

## 更新与验收

从仓库根目录运行：

```bash
python scripts/check_docs_contract.py --write
python scripts/check_docs_contract.py
python scripts/build_docs_site.py
```

第一条仅在读取改动并复核人工说明后执行。普通检查与构建绝不自动刷新，避免 CI 把过期文档悄悄“修绿”。
构建入口直接调用相同门禁，所以既有 CI 文档作业会执行，无需新增第二套工作流规则。
新增 Markdown 还必须登记到文档站，已有反向清单测试继续生效。

构建生成 `docs/site/data/code-manifest.json`：文件→README、完整源码指纹、行数、Python 限定符号名与行范围、解析覆盖类别。它是可重建的中间表示，不提交 Git，不制造第二套手写清单。

## 诚实边界

“文件覆盖完整”不等于“所有函数都得到正确的业务解释”。JS/HTML/CSS/SQL/配置目前只声明文件级覆盖，未引入新解析依赖，不假称完整跨语言符号树。
现有手写说明中的历史行号和旧统计不因新增门禁而自动变准确；生成清单是本次源码定位的依据，历史讲解仍需在对应修复中更新。
结构门禁不能判断一段非空文字是否认真解释了代码，也不能证明 `--write` 前确实做了评审。代码评审必须检查人工职责、变更原因和验证证据。禁止把“可执行检查”宣传成“自动消除所有文档遗漏与语义错误”。
