## 第 1 课：整体架构 —— 一个请求在电脑里走了什么路

### 1.1 这个项目到底在做什么生意

一句话：**这是一个「毕设服务平台」，靠免费工具引流、靠付费服务赚钱。**

它由两个平台拼成，共用一套账号：

| 平台 | 给用户什么 | 怎么赚钱 |
| --- | --- | --- |
| **免费工具平台** | 画 ER 图（数据库结构图）、画流程图、自然语言生成图 | 不赚钱，负责把人吸引进来 |
| **商业平台** | 导出数据字典 Word 文档等付费服务 | 微信支付下单 → 付款 → 下载 |

再加三块基础设施：**统一登录**（一次注册，两个平台通用）、**智能客服**（自动答疑，减少人工）、**内容抓取**（自动收集毕设相关文章充实站内内容）。

> **为什么不拆成两个独立网站？** 因为「引流」和「变现」必须共用同一个身份。用户在免费工具里画好了图，想导出 Word 时如果还要再注册一次，绝大多数人就走了。这就是代码里反复出现的 **SSO（单点登录）** 的商业理由。

### 1.3 一次请求的完整旅程

假设你在浏览器里点了「导出 Word」，接下来发生的事：

```
你的浏览器
   │  ① 发出请求 POST /tools/word-export
   ▼
┌─────────────────────────────────────────────────┐
│ ② 登记台（RequestLoggingMiddleware）             │
│    给这次请求发一个「快递单号」X-Request-ID       │
│    记下：谁、什么时候、花了多少毫秒               │
├─────────────────────────────────────────────────┤
│ ③ 安检（SecurityHeadersMiddleware）              │
│    在回执上贴安全标签，告诉浏览器哪些东西不许加载 │
├─────────────────────────────────────────────────┤
│ ④ 楼层指引（路由匹配 /tools/word-export）         │
│    → 交给 app/routers/tools.py 的 word_export()  │
├─────────────────────────────────────────────────┤
│ ⑤ 检查申请表（schemas.ErDiagramIn）               │
│    DDL 太长？格式不对？当场退回，不用惊动后厨     │
├─────────────────────────────────────────────────┤
│ ⑥ 限流闸门（rate_limit）                          │
│    这一分钟你已经来过太多次了？请先等等           │
├─────────────────────────────────────────────────┤
│ ⑦ 后场工坊                                        │
│    parse_ddl（解析建表语句）→ 丢到**线程**里      │
│    build_data_dictionary（生成文档）→ 丢到**进程**里│
├─────────────────────────────────────────────────┤
│ ⑧ 打包出餐（Response，带文件名与类型）            │
└─────────────────────────────────────────────────┘
   │
   ▼
浏览器收到 .docx 文件，同时回执上带着 X-Request-ID
```

**那个「快递单号」是干嘛的？** 将来你打电话报障说「我刚才导出失败了」，客服让你报出浏览器里那串 ID，工程师就能在成千上万行日志里**精确捞出你那一次请求**。没有它，线上排障只能靠时间戳猜 —— 这是 `app/middleware.py` 注释里写明的设计意图。

### 1.4 五个「为什么非要这样设计」

这一节是本笔记的重点。**只看「代码怎么写」学不到东西，看「不这样会出什么事」才行。**

#### ① 为什么用「异步」？—— 一个服务员照看十桌

**大白话**：普通写法（同步）是「服务员给 A 桌上完菜，站在旁边等 A 桌吃完，再去 B 桌」。异步是「给 A 桌下单后转身去招呼 B 桌，A 桌菜好了再回来」。

**为什么这个项目非用不可**：它大量时间在**等别人** —— 等数据库回话、等微信服务器回话、等 AI 接口回话。这些等待动辄几十上百毫秒，如果用同步写法，这段时间整个服务器就干等着，别的用户全部卡住。

**不这样会怎样**：10 个人同时用，第 10 个人要等前 9 个人全部办完。

#### ② 为什么「重活」要丢到另一个进程里？—— 收银员不能自己跑去炒菜

这是本项目最深的一个坑，代码里 `app/cpu_pool.py` 的注释记录了完整过程。

**大白话**：生成 Word 文档要**纯算**约 470~500 毫秒（本机实测）。这种「算」和「等」不一样 —— 它在抢 CPU。

Python 有一条规矩叫 **GIL（全局解释器锁）**：**同一时刻只允许一个线程执行 Python 代码**。

- 把重活丢到**线程**里：收银员虽然走开了，但**厨房钥匙只有一把**，后厨炒菜时前台照样开不了收银机。
- 把重活丢到**进程**里：相当于**另开一间厨房、另配一套钥匙**，前台完全不受影响。

**代价**：开进程比开线程贵得多（内存、启动时间）。所以代码里做了兜底 —— 进程池万一坏了，自动退回线程池，「慢但不坏」，而不是让用户看到报错页。

> **这个设计怎么被守住的？** 有一条测试专门检查这段重活**跑在哪个进程里**。曾经它是靠「测卡顿了多少毫秒」来判断的，但在 CI 服务器上误报过（机器调度抖动，不是代码变慢），后来改成直接查进程号 —— 详见 `TECH_DECISIONS.md` 的 TD-193。

#### ③ 为什么网页是「后端直接生成 HTML」，而不是用 Vue/React？

**大白话对比**：

- **前端框架（Vue/React）** = 餐厅给你食材、菜谱和一口锅，让你自己在餐桌上做菜。好处是菜能做花样，坏处是你得先有厨房（要装 Node.js、要打包、要构建）。
- **Jinja2 SSR（本项目）** = 餐厅直接把做好的菜端上来。浏览器拿到就是能看的页面。

**为什么这个项目选后者**：这是个**要上搜索引擎**的平台。搜索引擎的爬虫不喜欢「先下载一堆 JavaScript 再慢慢渲染」的页面。后端直接吐 HTML，爬虫一眼就能读到内容。

**不这样会怎样**：免费工具页搜不到 → 引流失败 → 整个商业模式的第一环断掉。

#### ④ 为什么「安检」要写得这么绕？—— 盖章 vs 重新填表

`app/middleware.py` 顶部有一段很坦诚的注释，记录了第一版的失败：

> 第一版用了框架提供的便捷写法（`BaseHTTPMiddleware`），功能全对，但客服接口从 14 毫秒涨到 **21 毫秒**，两条性能测试当场变红。

**比喻**：便捷写法相当于「每个客人进门，安检员都让他把入场表重新填一遍再核对」；现在的写法是「安检员只在原有表格上盖个章」。功能一样，开销差一大截。

**代价**：代码啰嗦、难读，所以那个文件里注释特别多。**这是典型的「用可读性换性能」，而且换的过程被记录了下来** —— 商业项目里这种记录比代码本身更值钱。

#### ⑤ 为什么「管理员权限」每次都查数据库，不写进登录凭证里？

**大白话**：登录凭证（JWT）像**演唱会手环** —— 上面写着你是谁、什么时候进的场，撕不下来也改不了，所以不用每次进门都查身份证。

但如果把「他是管理员」也印在手环上，就会出问题：**你把某人降权了，他手上那只旧手环还印着「管理员」，在过期前照样能进后台。**

所以本项目的做法是：手环上**只写你是谁**，「你是不是管理员」**每次刷卡都实时问人事部（数据库）**。

**效果**：降权**立刻生效**，不用等凭证过期。代价是每个请求多一次数据库查询 —— 用一点点性能换「权限变更即时生效」，在管理后台这种地方绝对划算。

### 1.6 行业里管这些叫什么

| 本项目的做法 | 行业术语 | 为什么是「标准做法」 |
| --- | --- | --- |
| 楼层（routers）/ 工坊（tools）/ 账本（models）分开 | **分层架构** | 改一处不会牵动全身；换数据库不用改页面 |
| 「申请表」和「账本」是两套定义 | **DTO（数据传输对象）** | 数据库里有的字段（比如密码）绝不能原样返回给用户 |
| 安检→登记→楼层，一层套一层 | **中间件洋葱模型** | 加新功能不用改老代码，套一层就行 |
| 38 项配置全放 `.env` 文件 | **12-Factor App 的第 3 条** | 同一份代码，测试环境和生产环境只换配置 |
| `/healthz` 与 `/readyz` 分开 | **存活探针 / 就绪探针** | 「活着」和「能接客」是两件事（见 1.7） |
| 417 条自动化测试 + 每次提交都跑 | **CI 持续集成** | 改坏了当场发现，不是上线后用户发现 |
| 每个取舍都编号记录在 `TECH_DECISIONS.md` | **ADR（架构决策记录）** | 半年后接手的人不用猜「当初为什么这么写」 |

## 第 2 课：登录与权限 —— 服务器是怎么认得你的

### 2.1 先说清楚登录在解决什么问题

HTTP 有个天生的毛病：**它没有记性**。你这一次请求告诉服务器「我是张三」，下一次请求服务器完全不记得你是谁 —— 就像每天去同一家便利店，店员每天都把你当新客人。

所以「登录」这件事的本质是：**给你一个随身携带、难以伪造的身份证明**，之后每次请求你都出示它。

整个流程只有两步：

```
① 你输入账号密码  →  服务器核对  →  发你一张「凭证」
② 之后每次请求，你都带上这张凭证，服务器验一下真伪就放行
```

难点全在第 ① 步发的那张凭证上。

---

### 2.2 生活比喻：演唱会手环

进场时工作人员核对你的票，然后给你**戴上一个一次性手环**。之后你在场内买饮料、进 VIP 区，都只看手环，不用再翻票。

这个比喻很准，但要看清它的四个细节：

| 手环的特点 | 对应到代码 |
| --- | --- |
| 上面印着你的名字和场次 | 凭证里写着「你是谁」和「什么时候过期」 |
| **戴上就撕不下来**，也没法自己画一个 | 凭证有防伪签名，改一个字符就作废 |
| 上面印的字**谁都能看** | ⚠️ 凭证内容**没有加密**，任何人都能读（见 2.4） |
| 手环有截止日期 | 默认 30 分钟后过期 |

---

### 2.3 密码：为什么数据库里根本看不到你的密码

**大白话**：数据库里存的**不是你的密码**，而是密码的「单向指纹」。

**实测**（在本地真的跑了一遍 `hash_password('123456')` 两次）：

```
第一次：$2b$12$e7yh1lzgog/aNC2Z4G72vuW.2r6DhVGdg7Fa8/8P9EMvpjfInfF.G
第二次：$2b$12$KxfhrIWXfBpFT0poda40/uG49O9uA4m5lhtkBTJLHPqQp62HFh1mS
```

**同一个密码，两次结果完全不同** —— 这不是 bug，这是设计。

**为什么要故意不一样？** 假设两个用户都用 `123456`，如果加密结果固定，攻击者拖走数据库后一眼就能看出「这两人密码相同」，还能拿一张预先算好的「密码 → 指纹」对照表（叫**彩虹表**）批量反查。每次都掺一点随机料（叫**盐**），这张表就废了。

**关键点：这个过程不可逆。** 你没法从 `$2b$12$e7yh...` 算回 `123456`。那服务器怎么验证你登录？

> 它**不算回**你的密码，而是把你这次输入的密码**用同样的盐再算一次指纹**，比对两个指纹一不一样。
>
> 生活比喻：**指纹锁**。锁不保存你的手指，只保存指纹图案；你来了它现场采一次比对。

**不这样做会怎样？**

- 存明文 → 数据库一泄露，全站用户密码裸奔。而且**大量用户在多个网站用同一个密码**，你的泄露会连累他们的邮箱和网银。
- 用 MD5 这类「快」的算法 → 攻击者用显卡每秒能试几百亿次。**密码存储必须故意慢**，`bcrypt` 就是为此设计的（那串里的 `12` 是「难度档位」，越大越慢）。

**落地文件**：`app/security.py` 的 `hash_password()` / `verify_password()`，底层是 `passlib` + `bcrypt`。数据库列 `sys_user.password` 长度 255，实测指纹 60 字符。

> **绝不自己写加密算法。** 这是行业铁律 —— 自己想出来的加密一定有你没考虑到的攻击面。

---

### 2.4 凭证（JWT）：拆开看它在电脑里长什么样

**大白话**：登录成功后服务器发给你的，是一串用两个点分成三段的字符串。

**实测**（真的签发了一张然后拆开）：

```
第 1 段（头部）  eyJhbGciOiJIUzI1NiIsInR5cCI6...  →  {"alg": "HS256", "typ": "JWT"}
第 2 段（内容）  eyJzdWIiOiJ6aGFuZ3NhbiIsImV4...  →  {"sub": "zhangsan",
                                                       "exp": 1788515449,
                                                       "pwd": 1788508800}
第 3 段（签名）  ZEi5MTlb3K0DxPRXjhgzqoWBM55h...     （二进制，读不出字）
```

#### ⚠️ 必须记住的一点：**第 2 段没有加密**

上面那个 `→` 右边的内容，是我用**任何语言十行代码**就能还原出来的。也就是说：

> **任何人拿到你的凭证，都能直接读出里面写了什么。**
> 只是他**改不了** —— 一改，第 3 段的签名就对不上。

**实测**：把凭证最后一个字符改掉，服务器的校验函数返回 `None`（即「无效」）。

**生活比喻**：手环上的名字是**明刻**的，谁都能看；但手环上有一个**防伪钢印**，你想把「张三」磨掉改成「李四」，钢印就花了，一眼假。

**所以凭证里绝不能放密码、手机号、身份证号。** 本项目的凭证里只有三样东西：

| 字段 | 意思 |
| --- | --- |
| `sub` | 你是谁（用户名） |
| `exp` | 什么时候过期 |
| `pwd` | 签发那一刻，该用户「上次改密码的时间」的副本 ← 这个是精髓，见 2.6 |

#### 为什么故意不把「你是不是管理员」放进去？

见第 1 课 1.4 ⑤：放进去就等于把职位**印死在手环上**，降权了旧手环照样能进后台。所以本项目每个请求都去数据库现查一次。

**落地文件**：`app/security.py` 的 `create_access_token()` / `decode_token()`。

### 2.5 凭证存在哪：为什么浏览器脚本读不到它

这是本项目真实做过的一次安全改造（`TECH_DECISIONS.md` 的 TD-44）。

**大白话**：网页里跑的 JavaScript 是**别人写的代码**。如果页面被塞进一段恶意脚本（这类攻击叫 **XSS**），那段脚本能读到的东西就等于攻击者能读到的东西。

两种存法的区别：

| 存法 | 恶意脚本能拿到吗 | 比喻 |
| --- | --- | --- |
| 存在 `localStorage`（很多教程这么教） | **能，一行代码就读走** | 把家门钥匙放在门口地垫下 |
| 存在 **HttpOnly cookie**（本项目的做法） | **读不到**，浏览器直接拒绝 | 钥匙交给门卫，你刷脸进门 |

所以本项目的登录接口**同时走两条通道**：

- **浏览器** → 收到 `Set-Cookie`，之后浏览器自动带上，前端代码全程碰不到凭证
- **API 客户端 / Swagger 调试页** → 从响应体里拿 `access_token`，手动放在请求头里

代码在 `app/routers/auth.py` 的 `_set_auth_cookie()`，四个属性每个都有讲究：

| 属性 | 值 | 为什么 |
| --- | --- | --- |
| `HttpOnly` | 是 | 脚本读不到 —— **这就是整件事的目的** |
| `SameSite` | `Lax` | 挡住跨站的写操作（防 **CSRF**：别的网站偷偷用你的身份提交表单） |
| `Secure` | **仅生产环境** | 本地是 http，加了这个浏览器根本不存 cookie，本地就没法调试了 |
| `Max-Age` | 与凭证同寿命 | 免得 cookie 活得比凭证久，反复撞「未登录」 |

#### `Lax` 是有代价的，而且这个项目把代价管起来了

`Lax` 只挡跨站的 **POST/PUT/DELETE**；跨站的 **GET**（比如从微信里点个链接跳过来）**照样会带上凭证**。

所以推出一条铁律：**凡是「会产生副作用」的接口，一律不能是 GET。**

**这条铁律不是靠自觉，是靠测试钉住的**：`tests/test_auth_cookie.py` 里有一份「需要登录的 GET 路由」清单，谁新增一个就会被测试拦下来，逼他解释「你这个 GET 为什么没有副作用」。

> 举个真实例子：下载已购文件这个接口，本来最自然的写法是 `GET /shop/download/xxx`。但它会把订单状态从「已付款」烧成「已下载」—— 这是副作用，所以最终实现是 **`POST /shop/download/{order_no}`**，并且有专门的测试验证「用 GET 请求会被拒」。

同一个测试文件里还有一条更狠的：它**真的用 node 跑了一遍前端页面的内联脚本**，并给 `localStorage` 塞了一个「一被碰就报错」的假对象。谁哪天又把凭证写回浏览器存储，这条测试当场炸。

> **静态搜一遍只能证明「现在没有」；真的跑一遍才能证明「这段代码的执行路径上没有」。**

### 2.6 三个灵魂拷问：这张凭证到底什么时候失效？

这一节全部有**实测结果**，不是推理。

#### ① 改了密码，之前所有设备上的登录还有效吗？→ **立刻全部失效**

**做法很巧**：凭证里带一个 `pwd` 字段，值是「签发那一刻，用户上次改密码的时间」。每次请求，服务器拿它和**数据库里的当前值**比一比：

```
凭证里的时间  <  数据库里的时间   →  说明这张凭证是「改密码之前」签的  →  拒绝
```

**为什么不用一张「已作废凭证名单」？** 那种做法（叫**黑名单**）要建表、要写入、要清理过期条目。用时间戳比大小，**零存储成本**就实现了「一次吊销该用户所有旧凭证」。

> 这正是「改密码」最主要的用途：怀疑密码泄露时，**光改密码而旧凭证还能用，等于没改**。

而且改密码接口会**返回一张新凭证**并替换掉 cookie —— 当前这次会话不该被自己踢下线，要踢的是**其他**设备。

#### ② 账号被封了，手上那张还没过期的凭证还能用吗？→ **不能，立刻失效**

**这一条曾经记错过。** `TECH_DECISIONS.md` 的 TD-70 原文暗示「封号后旧凭证仍有效」，后来被测试订正了 —— 现在 `tests/test_token_revocation.py` 里有一条用例专门钉住它，名字就叫 `test_disabled_user_token_is_rejected_immediately`：

```
1. 注册并登录，拿到凭证        → 用它访问 /auth/me  → 200 ✓
2. 把该用户的 status 改成 0（封号）
3. 用同一张凭证再访问 /auth/me → 401 ✗ 被拒
```

我本地实跑了这个文件：**15 passed**。

**为什么能立刻生效？** 因为第 1 课讲过的那个设计 —— 每个请求都要查一次数据库（本来就要查密码修改时间），顺手就把账号状态一起看了。**这就是「不缓存、每次查库」换来的好处。**

#### ③ 点了「退出登录」，那张凭证真的作废了吗？→ **没有**

这一条要**诚实说清楚**，因为它是本项目的一个已知取舍。

退出接口做的唯一一件事是：**让浏览器把 cookie 删掉**。服务端**没有记录**发出去过哪些凭证，所以也就没有「作废」这个动作。

**后果**：如果那张凭证在退出前已经被人偷走了，它在那 30 分钟内**仍然有效**。

**为什么接受这个取舍？** 要真正做到「退出即作废」，就必须维护一张黑名单表 —— 而那恰恰是 ① 用时间戳巧妙绕开的东西。**代价记在 TD-70 的粒度说明里。**

> 顺带一个有意思的设计：退出接口**故意不要求登录**。因为拿着一个已过期凭证的客户端也应该能把它清掉，否则用户会卡在「我明明点了退出，浏览器却还带着一个死凭证」的怪状态。

### 2.7 完整流程串起来

```
你输入 张三 / 123456
        │
        ▼
┌────────────────────────────────────────────┐
│ 限流闸门：这一分钟你试太多次了？先等等      │
├────────────────────────────────────────────┤
│ 查库找到张三 → 取出那串指纹                  │

├────────────────────────────────────────────┤

之后每次请求：
   带上凭证 → 验签名 → 验过期 → 查库 → 验 status
            → 比 pwd 时间戳 → 取 role 判断权限 → 放行
```

### 2.9 行业里管这些叫什么

| 本项目的做法 | 行业术语 |
| --- | --- |
| 单向指纹 + 盐 + 故意慢 | **密码哈希（password hashing）**，`bcrypt` 是主流选型之一 |
| 三段式、带签名、内容可读 | **JWT（JSON Web Token）** |
| 内容不加密、只防篡改 | **签名（signature）而非加密（encryption）** |
| 每次请求都要出示凭证 | **无状态认证（stateless auth）** |
| 服务端不记会话 | 与 **Session/Cookie 有状态方案**相对 |
| 脚本读不到的 cookie | **HttpOnly cookie** |
| 挡跨站写操作 | **CSRF 防护**（靠 `SameSite`） |
| 挡注入脚本偷数据 | **XSS 防护**（靠 HttpOnly + CSP） |
| 返回信息里剔除敏感字段 | **DTO 白名单**（`UserOut` 只有 4 个字段，**不含 password**） |
| 「一次操作最多试几次」 | **限流 / 防暴力破解** |
| 登录失败不透露具体原因 | **防用户枚举（user enumeration）** |

### 2.10 术语白皮书（第 2 课）

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **哈希 / 指纹** | 单向压缩，算得出来但倒推不回去 | 指纹锁：不存手指，只存图案 |
| **盐（salt）** | 每次掺一点随机料，让相同密码产生不同结果 | 同一道菜，每家放不同的香料 |
| **彩虹表** | 攻击者预先算好的「密码 → 指纹」对照表 | 一本万能钥匙对照册 |
| **JWT** | 三段式的防伪身份凭证 | 演唱会手环 |
| **签名** | 防篡改的防伪印记（内容仍可被阅读） | 手环上的钢印 |
| **加密** | 让内容变得读不懂（与签名是两回事） | 把字放进保险箱 |
| **XSS** | 攻击者往网页里塞进自己的脚本 | 有人在你的公告栏贴了小广告 |
| **CSRF** | 别的网站偷偷借用你的身份提交操作 | 有人拿着你的印章去盖章 |
| **HttpOnly** | 这个 cookie 脚本读不到 | 钥匙交给门卫，不放地垫下 |
| **SameSite=Lax** | 跨站的写操作不带凭证 | 出了这个商场，印章就不认了 |
| **黑名单** | 记录「哪些凭证已作废」的清单 | 挂失名单 |
| **无状态** | 服务端不记你是谁，全靠你每次出示凭证 | 每次都看手环，不认脸 |
| **限流** | 单位时间最多试几次 | 输错三次锁卡 |
| **用户枚举** | 通过报错差异猜出「哪些账号存在」 | 挨家敲门看哪家有人应 |
| **role / 角色** | 你是普通用户还是管理员 | 工牌上的岗位 |

## 第 3 课：支付闭环 —— 钱和货怎么保证不出错

### 3.1 这一课的核心矛盾

前面两课讲的功能，做错了大不了是「页面显示不对」。**支付不一样：做错了就是真金白银的事故。**

具体有三种事故，严重性完全不同：

| 事故 | 严重程度 |
| --- | --- |
| 用户付了钱，没拿到货 | **最严重** —— 这是欺诈，要退款、要道歉、要上投诉平台 |
| 用户没付钱，拿到了货 | 严重 —— 亏钱，但不至于违法 |
| 用户买了一份，下载了十次转卖 | 中等 —— 亏钱 |

**记住这个排序，本课所有设计都是在给它排序。** 当两种错误只能避免一种时，代码选择避免第一种。

---

### 3.2 生活比喻：为什么不能「先查一下再改」

想象一个**只剩一张票**的售票窗口，同时来了两个人。

**错误做法**（先查再改）：

```
A：还有票吗？  窗口：有。
B：还有票吗？  窗口：有。      ← 问的是同一时刻的状态
A：给我一张。  窗口：好，给你。
B：给我一张。  窗口：好，给你。  ← 票只有一张，卖出去两张
```

问题出在**「查」和「改」是两步**，中间有空隙，另一个人可以挤进来。

**正确做法**（本课的主角，叫 **CAS**）：

```
把两步合成一步：「如果还有票，就把它卖给我」——由数据库保证这中间插不进别人。
```

数据库天然能做到这一点，因为它对同一行数据的写操作是排队的。**关键是不要自己拆成两步。**

---

### 3.3 订单状态机：只允许走这几条路

**大白话**：一张订单从生到死，只能按固定路线走，任何「跳跃」都被拒绝。

本项目一共 4 个状态（`app/order_state.py`）：

```
        付款成功              请求下载
待支付 ─────────→ 已支付 ─────────→ 已下载
pending            paid            downloaded
   │
   │ 30 分钟没付
   ▼
已关闭 closed ─────→ 已支付        ← 注意这条「反直觉」的边，见下
```

代码里就是一张表，**所有地方都查这张表，谁都不许自己写 if**：

```python
ALLOWED = {
    "pending":    ("paid", "closed"),
    "closed":     ("paid",),        # ← 故意的，见 3.4
    "paid":       ("downloaded",),
    "downloaded": (),               # 终点，出不去
}
```

**为什么非要集中成一张表？** 因为支付回调、发货、下载是**三段不同的代码**。如果每段各写一遍 `if`，迟早会出现某一段漏了一个条件 —— 比如「未支付也能下载」。**把规则收成一处，就没有「漏掉」的可能。**

#### 那条反直觉的边：已关闭的订单为什么还能变成已支付？

第一眼看这是 bug：订单都关了，怎么还能付款？

**因为「关单」只是我们这边不再等它了，用户完全可能已经扫了那个旧二维码把钱付了。**

> 这时候如果拒绝，就是**收钱不发货** —— 正是 3.1 里排第一的那种事故。

代码注释写得很直白：

> 钱到账就必须发货，否则是收钱不发货（TD-156）。

而且这条边**不是靠注释守着的**，有一条测试专门钉住它：`test_late_payment_on_closed_order_still_delivers` —— 把订单时间改到 999 分钟前 → 触发关单 → 确认状态是 `closed` → 再付款 → **断言必须 200 且状态变成 `paid`**。

#### 一个「少即是多」的设计：没有 `expire_at` 字段

订单表里**没有**「过期时间」这一列。因为：

```
过期时间 = 下单时间 + 配置里的 30 分钟
```

**能算出来的东西就别存。** 多存一列，就多了一个「改了配置但老数据没同步」的隐患。

---

### 3.4 幂等：同一件事发生十次，结果和发生一次一样

**大白话**：**幂等**就是「重复做不会出事」。

**生活比喻**：电梯的上行按钮。你按一次它来，你急得按十次它也还是来一次 —— 不会来十部电梯。反过来，**取快递**就不幂等：取一次少一件，取两次就少了两件。

#### 为什么支付必须幂等？

因为**微信支付会重复通知你**。网络抖一下、你的服务器响应慢了一点、微信没收到你的确认 —— 它都会**再推一次**。这是设计好的，不是故障。

所以回调处理必须能应对「同一笔支付被通知五次」。本项目的做法：

```python
if order.status == PENDING:
    order.transaction_id = ...      # 只有第一次才写入支付信息
    order.paid_at = ...
await mark_paid(db, order)          # 已经是 paid 了就返回 False，不报错
```

**注意两个细节**：

1. **重复通知不报错**，只是「什么也不做」。如果报错，微信会认为你没处理成功，**继续重推，无限循环**。
2. **不覆盖首次的支付信息**。否则第二次通知带来的数据会把第一次的覆盖掉，对账时就乱了。

#### 一个容易忽略的规矩：什么时候必须回「成功」

微信的规矩是：**你回 4XX/5XX，它就重推。**

所以本项目里，「重试也没用」的情况一律回 200：

| 情况 | 回什么 | 为什么 |
| --- | --- | --- |
| 验签失败 | 401 | 可能是攻击，也可能证书没配好，值得重试 |
| 金额不符 | 400 | 数据有问题，要人工介入 |
| 订单不存在 | 404 | 同上 |
| **这是退款通知，本阶段不处理** | **200** | 重试一百次也不会变成支付通知 |
| **这单早就处理过了** | **200** | 同上 |

**把后两种写成报错，就会招来无限重推。** 这是接第三方回调最容易踩的坑。

### 3.5 原子性：并发下只能有一个赢

回到 3.2 的售票比喻。「一次性下载」面临的就是这个问题。

**代码里原本已经有一道检查了**：

```python
if order.status == DOWNLOADED:
    raise HTTPException(403, "该订单已下载过")
```

**但这道检查在并发下是无效的。** 因为 4 个请求同时进来，它们**同时读到** `status = paid`，于是 4 个都认为「还没下载过」，4 个都放行。

真正起作用的是下面这句 —— 它必须**看返回值**：

```python
won = await mark_downloaded(db, order)   # 内部是 UPDATE ... WHERE status='paid'
if not won:
    raise HTTPException(403, "该订单已下载过")
```

`UPDATE ... WHERE status='paid'` 的意思是「**只有当它现在还是 paid，才改成 downloaded**」。数据库保证这中间插不进别人，所以 4 个并发请求里**只有 1 个的 `rowcount` 是 1**，其余 3 个是 0。

代码里专门写了一段注释警告：

> **必须看返回值**……忽略返回值的话，并发 4 个请求会全部拿到有效链接，「一次性下载」直接失效。

**这个警告有测试兜底**（`tests/test_e2e.py::test_concurrent_download_only_one_wins`）：

```python
results = await asyncio.gather(*[client.post(f"/shop/download/{order_no}") for _ in range(4)])
assert codes.count(200) == 1        # 恰好一个成功
assert set(codes) - {200} == {403}  # 其余全是 403
```

> **串行测试通过，不代表并发也守得住。** 这类 bug 在开发时几乎不可能手动测出来，只有专门写并发测试才能钉住。

### 3.6 回调安全：怎么确认「真的是微信在通知我」

支付回调这个接口**故意不做登录鉴权** —— 因为调用方是微信服务器，它没有你网站的账号。

那怎么防止**别人伪造一个「用户已付款」的通知**来白拿货？三道关：

#### 第一关：验签（确认「真的是微信发的」）

**生活比喻**：信封上的**火漆印**。任何人都能写信，但只有微信有那个印章。

微信用它的私钥在报文上盖一个签名，你用微信的**平台证书**（公钥）验。签名对不上 → 401。

#### 第二关：解密（确认内容没被看/被改）

报文体是**加密的**（AES-GCM 算法），密钥是你和微信之间约定的 `WX_API_V3_KEY`。

**AES-GCM 的好处**：它不只加密，还**自带防篡改** —— 内容被动过一个字节，解密直接失败。

#### 第三关：校验金额（最容易被漏掉的一关）

```python
if total != order.amount:
    return _fail(400, f"金额不符：回调 {total} 分，订单 {order.amount} 分")
```

**为什么必须校验？** 因为前两关只证明「这是微信发来的、关于某笔真实支付的通知」，**不证明这笔钱的数额对得上你的订单**。

> 攻击场景：商品 199 元，攻击者用另一个渠道付了 1 分钱，然后把那笔真实支付的通知**重放**到你的回调地址 —— 签名是真的、解密也成功，只有金额对不上。**这一行就是拦这个的。**

本项目商品金额是 `SHOP_PRODUCT_AMOUNT = 19900`，**单位是「分」**（¥199.00）——
这不是我推测的，`app/models.py` 里那一列的定义就写着
`amount: Mapped[int] = mapped_column(Integer)  # 金额，单位：分`，类型是**整数**。

> **为什么用「分」而不用「元」？** 因为 `0.1 + 0.2` 在计算机里**不等于** `0.3`（浮点数误差）。钱的计算一律用整数最小单位，这是行业铁律。

#### 三个「本地测不出来、上线才炸」的细节

`app/wechat_pay.py` 顶部记录了三个必须钉死的点，值得单独讲，因为它们**在本地怎么测都是对的**：

1. **参与签名的字节，必须和实际发出去的字节一模一样。** 所以代码先把数据序列化成字符串 → 用**这串**去签名 → 再把**同一串**发出去。中途任何一次重新序列化（键的顺序变了、空格多了、中文被转义了）都会让验签失败。
2. **参与签名的网址不含域名**，只有路径和参数。
3. **回调验签必须用「原始报文」**，不能先解析成对象再重新序列化 —— 理由同第 1 条。所以代码里用的是 `await request.body()` 取原文。

> 这三条是接第三方支付最典型的坑：**本地全绿，真机验签失败**。因为本地没有真正的微信服务器来挑你的刺。

### 3.7 下载：两重校验

拿到「已支付」只是第一步，下载还有两道闸：

| | 校验什么 | 防什么 |
| --- | --- | --- |
| **第一重** | 数据库里的订单状态（`paid → downloaded` 只能走一次） | 同一份资源被无限下载、转卖 |
| **第二重** | 下载链接的签名 + **5 分钟**过期（`DOWNLOAD_URL_TTL = 300`） | 链接被转发给别人用 |

**主力是第一重。** 第二重只是「缩小转发窗口」—— 因为链接一旦发出去，在那 5 分钟内谁拿到都能用。

#### 签名里为什么要把「文件名」也签进去

```python
hmac.new(secret, f"{key}\n{expires}", sha256)
```

如果只签过期时间，那么**拿到一个合法链接的人，把网址里的文件名改掉，就能下载别的文件**。把文件名一起签进去，改一个字签名就对不上了。

#### 一个细节：比较签名要用「防侧信道」的写法

```python
hmac.compare_digest(算出来的签名, 传进来的签名)
```

普通的 `==` 比较字符串时，**遇到第一个不同的字符就返回**。攻击者可以精确测量响应时间：猜对第一位比猜错的慢一点点……以此逐位试出正确签名。这叫**时序侧信道攻击**。`compare_digest` 不管对不对都比完全部再返回，时间恒定。

#### 一个诚实的取舍：「已下载」是在发链接时就标记的

代码注释说得很清楚：

> 标记为已下载发生在**发出链接时**，不是文件真的被下载时。云存储是客户端直连对象存储，应用根本看不到那次下载（TD-129）。

**后果**：如果链接发出去后用户网络断了、没下成，这一份额度也已经烧掉了。这是「用云存储省服务器带宽」必须付的代价。

### 3.8 没有商户号怎么开发：模拟支付开关

微信支付需要**六项凭据**（商户号、API 证书、密钥……）外加一个**公网 https 回调地址**。开发时两样都没有。

本项目的做法是一个开关：`SHOP_PAY_MODE`

| 值 | 行为 |
| --- | --- |
| `wechat`（默认，生产） | 调真微信下单；六项没配齐直接 **503** 拒绝，不发出注定失败的请求 |
| `mock` | 不调微信，二维码指向本站的模拟收银台页面 |

**两个关键设计**：

1. **生产环境下模拟端点一律 404。** 不是「返回错误」，是**根本不存在**。这样演示用的后门不可能被带上生产环境。
2. **模拟支付复用与真实回调完全相同的状态机**（都调 `mark_paid`）。

> 第 2 点特别重要：**演示走通的路径和上生产走的是同一条**。如果为演示单独写一套代码，那套代码永远不会被真实场景验证过，上线当天才第一次跑。

### 3.9 完整流程串起来

```
① 用户点「下单」
   └→ 已有未支付单？没过期就复用（避免连点刷出一堆单）
                 过期了就关掉、另起一单
   └→ 先把订单落库，再去微信下单
      （微信那边付了、我们这边没单，比反过来难收拾得多）
   └→ 拿到 code_url → 前端画成二维码

② 用户扫码付款（微信 App 里完成，与本站无关）

③ 微信回调 POST /shop/pay/notify
   └→ 验签（平台证书）        不过 → 401
   └→ 解密（AES-GCM）         不过 → 400
   └→ 是支付成功通知吗？      不是 → 200（避免无限重推）
   └→ 订单存在吗？            不在 → 404
   └→ 金额对得上吗？          不符 → 400
   └→ mark_paid（幂等 + 原子）
   └→ 回 200

④ 用户点「下载」POST /shop/download/{order_no}
   └→ 是自己的单吗？          不是 → 404（不暴露是否存在）
   └→ 付过钱吗？              没有 → 403
   └→ 已经下过吗？            下过 → 403
   └→ 生成预签名链接（5 分钟）
   └→ mark_downloaded —— **看返回值**，抢不到就 403
   └→ 返回链接

⑤ 用户点链接 GET /shop/dl?key=...&expires=...&signature=...
   └→ 验签名与过期时间        不过 → 403
   └→ 吐文件
```

| 本项目的做法 | 行业术语 |
| --- | --- |

| 比较密钥时用恒定时间 | **防时序侧信道（timing-safe comparison）** |
| 钱用整数最小单位 | **避免浮点误差** |
| 第三方主动通知你 | **Webhook / 回调** |

### 3.12 术语白皮书（第 3 课）

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **幂等** | 重复做多少次，结果都一样 | 电梯上行按钮：按十次也只来一部 |
| **CAS** | 「只有还是原样才改」，一步完成 | 「如果还有票就卖给我」，中间插不进人 |
| **并发** | 多件事同一瞬间发生 | 两个人同时问「还有票吗」 |
| **状态机** | 规定好的、只能按路线走的状态变化 | 地铁闸机：不刷卡进不去，进去了就不能再进 |
| **回调 / Webhook** | 别人办完事主动来通知你 | 快递到了驿站打电话给你 |
| **重推** | 你没确认收到，对方就再通知一次 | 打电话没人接，隔一会儿再打 |
| **验签** | 确认消息真的来自对方且没被改 | 信封上的火漆印 |
| **AES-GCM** | 一种加密方式，顺带能发现内容被改过 | 保险箱 + 封条，动过就知道 |
| **预签名 URL** | 带签名和有效期的下载链接 | 限时限次的取货码 |
| **HMAC** | 用共享密钥算出的防伪码 | 只有你俩知道的暗号 |
| **时序侧信道** | 靠「响应快慢」偷猜密钥 | 听保险箱「咔哒」声逐位试密码 |
| **重放攻击** | 把截获的真实请求再发一遍 | 录下你的语音去骗门禁 |
| **分（金额单位）** | 用整数存钱，避免小数误差 | 记账记「19900 分」而不是「199.00 元」 |
| **503 / 400 / 401 / 403 / 404 / 409** | 服务器回话的「状态码」，见下方补充 | 快递单上的处理结果代码 |

#### 补充：这一课出现的状态码

| 码 | 大白话 | 本课哪里用到 |
| --- | --- | --- |
| **200** | 办好了 | 回调处理成功（含「重试也没用」的情况） |
| **400** | 你给的东西不对 | 金额不符、报文解不开 |
| **401** | 我不知道你是谁 | 验签失败 |
| **403** | 我知道你是谁，但你不能做这件事 | 未支付、已下载过 |
| **404** | 没这东西 | 订单不存在（**别人的单也回这个**，不泄露它是否存在） |
| **409** | 状态冲突了 | 非法状态迁移 |
| **503** | 我现在没法服务 | 支付没配置、存储后端不可用 |

## 第 4 课：智能客服三层 —— 为什么高频问题不该用 AI 回答

### 4.1 先看清三个矛盾

「接个 AI 客服」听起来很简单，但它同时撞上三堵墙：

| 矛盾 | 具体表现 |
| --- | --- |
| **AI 会瞎编** | 你问「怎么退款」，它能编出一套根本不存在的退款流程，说得还很自信 |
| **AI 要花钱** | 每次调用都按字数计费。「多少钱」这种问题一天被问一百遍，每次都花钱 |
| **AI 很慢** | 一次调用几百毫秒到几秒。「你好」也要等两秒，体验很差 |

**所以这一课的核心结论是：能用规则和查表解决的，绝不动用 AI。**

这不是「技术保守」，而是把 AI 用在它**真正不可替代**的地方。

---

### 4.2 生活比喻：医院分诊台

大医院进门有个**分诊台**，护士看一眼就把你分去不同地方：

| 分诊台判断 | 客服的三层 | 代价 |
| --- | --- | --- |
| 「量体温这种小事，自助机就行」 | **第一层 FAQ**：库里已有标准答案，直接给 | 几乎为零 |
| 「普通感冒，去门诊找医生」 | **第二层 闲聊**：交给轻量 AI 自由发挥 | 花钱、慢一点 |
| 「疑难杂症，得找专家，还要调病历」 | **第三层 RAG**：先查资料，再让 AI **照着资料**回答 | 最贵 |
| 「这个我也说不准，你去找主任」 | **兜底 转人工** | 人工成本 |

**关键在于「分诊」本身要便宜。** 如果分诊也要挂一次专家号，那分诊就失去意义了 —— 这就是为什么第一层必须是纯查表。

### 4.3 第一层 FAQ：这是「检索」，不是「分类」

#### 一个必须纠正的直觉

很多人以为「判断用户想问什么」是个**分类**问题（像邮件分垃圾/非垃圾）。**但对于高频 FAQ，它其实是「找最像的那句话」。**

- **分类**：把输入塞进预先定义好的几个格子里。
- **检索**：在已有的问法库里，找一条**最像**的，把它的标准答案给你。

本项目 12 条 FAQ，每条都带一个「标准问法」和一组「其它说法」：

```python
Faq("毕业设计服务怎么收费", "按题目难度与工作量报价，本科毕设 199 元起……",
    ("价格", "多少钱", "报价", "费用", "贵吗"))
```

用户问「服务多少钱」，检索发现它和这条最像，于是直接返回那条答案。**全程没有 AI 参与。**

#### 为什么要两种算法一起用

单一算法各有死角，所以两路融合（`BM25_WEIGHT = 0.6`，即 BM25 占六成、余弦占四成）：

| 算法 | 擅长什么 | 生活比喻 |
| --- | --- | --- |
| **BM25** | 关键词命中。「发票」这个词在讲发票那条里出现得多，而且这个词在全库很稀有，所以权重高 | 图书馆按**书名关键词**找书 |
| **余弦相似度** | 换了说法也能认。「怎么开票」和「能否开发票」字面不同，但整体用词分布接近 | 按**书的内容气质**找书 |

BM25 的分数**没有上限**，而余弦是 0~1，两者不能直接相加。所以先用一个「饱和函数」把 BM25 压进 0~1：

```python
x / (x + 3.0)     # x 越大越接近 1，但永远到不了 1
```

那个 `3.0` 不是随手写的，是按现有语料的实测分布定的。

#### ⚠️ 一个真实的坑：`score` 和 `confidence` 不是一回事

代码里每个检索结果同时带这两个数，注释专门警告过：

- **`score`** 是**在这一批结果内部**归一化的 —— 排第一的那条**恒等于 1.0**。
- **`confidence`** 是用**未归一化的原始分**算的 —— 可以跨不同提问比较。

**如果拿 `score` 当「有多大把握」用，那么任何提问都会被判成「命中」**，因为 top1 永远是 1.0。代码注释里直接点名了这个后果：

> 那会让「python 部署 nginx 报错」也判成 FAQ 命中。

#### 阈值 0.40 是怎么来的：实测标定，不是拍脑袋

我把代码里记录的标定值**自己跑了一遍**验证：

| 用户提问 | 我实测的置信度 | 结果 |
| --- | --- | --- |
| 毕业设计服务怎么收费 | **0.537** | ✅ 命中 FAQ |
| 可以开发票吗 | **0.522** | ✅ 命中 FAQ |
| 服务多少钱 | **0.502** | ✅ 命中 FAQ（认出了「多少钱」= 收费那条） |
| 交付要多久 | **0.425** | ✅ 命中 FAQ |
| — | — | **阈值 0.40 在这里** |
| 这个能便宜点不 | **0.389** | ❌ 不命中 → 最终转人工 |
| 怎么退款 | **0.322** | ❌ 不命中（确实没有退款 FAQ） |
| python 部署 nginx 报错 | **0.316** | ❌ 不命中 → 判为专业问题 |

（代码注释里最后一条记的是 0.306，我实测 0.316 —— 有细微漂移，但两者都远低于阈值，不影响结论。）

**⚠️ 注意表里有两个不同的「置信度」，别搞混**（我把「这个能便宜点不」端到端跑了一遍）：

```
FAQ 检索置信度 0.389  → 没过 0.40，不算命中
        ↓
路由兜底置信度 0.30   → 三种都不像，按闲聊兜底但故意给低分
        ↓
0.30 < 0.35（LOW_CONFIDENCE）→ 转人工
        ↓
最终 source = "human"，escalated = True
回复：「这个问题我暂时答不好，已为你转接人工客服，请稍等。」
```

**第一个数是「检索有多像」，第二个数是「路由有多大把握」。** 两条线、两个阈值（0.40 与 0.35），各管一段。

顺便看这个例子有多妙：用户在**砍价**。这种事 AI 答不好也不该答（答「可以便宜」就成了承诺），系统识别出自己没把握，直接甩给人工 —— **这正是兜底机制存在的意义**。

**看这个表能看出两件事**：

1. **阈值的位置是有依据的** —— 它落在「真的命中」（0.425）和「差一点」（0.389）之间。
2. **但它也很脆** —— 0.425 和 0.389 只差 0.036。代码注释自己也承认：

> 语料变大后必须重新标定，否则这个数没有意义（TD-151）。

> **这是一个很重要的工程观念：有些数字不是「算出来的」，是「量出来的」。它们只在特定的数据分布下有效，换了数据必须重新量。** 把它们当常量写死，是这类系统日后出错的头号原因。

### 4.4 第二层 意图路由：一个「没做」的诚实决定

#### ROADMAP 要求的 BERT，代码里明确写了没做

原始需求是「训练或微调一个 BERT 多分类模型」。`app/tools/intent.py` 顶部的注释是这么写的：

> **这部分没有做，也不该假装做了。** 训练 BERT 需要：标注数据（三类各上千条，本项目一条都没有）、GPU 或至少数小时 CPU、以及几百 MB 的预训练权重下载。沙箱里三样都不具备，写出来的「模型」无法验证，只会是个不能跑的摆设。

**我认为这是整个项目里最值得学的一段注释。** 它做了三件事：

1. 直说没做（不含糊过去）
2. 说清楚为什么做不了（三个具体障碍，不是「没时间」）
3. 说清楚「假装做了」的后果（**无法验证的摆设**）

#### 那实际做了什么：接口 + 可替换实现

```python
class IntentRouter(Protocol):          # ← 接口：只规定「要有一个 classify 方法」
    def classify(self, text: str) -> IntentResult: ...

class RuleIntentRouter:                # ← 当前实现：纯规则，完全确定
    def classify(self, text: str) -> IntentResult: ...
```

**生活比喻**：定义好一个**插座标准**，现在插的是「规则」这个插头；将来有了 BERT，做一个符合同样标准的插头换上就行，**墙里的电线（业务代码）一根都不用动**。

这就是行业里说的**面向接口编程**。它的价值在这里体现得特别清楚：

> 将来训练出 BERT 后，写一个 `BertIntentRouter` 实现同一个接口即可，`app/tools/support.py` 与路由层一行都不用改。

#### 判定顺序为什么是「先查 FAQ」

```
① FAQ 检索有把握吗？  有 → 直接返回（不调 AI）
② 命中技术词吗？      有 → 判为专业问题
③ 命中寒暄词吗？      有 → 判为闲聊
④ 都不像            → 按闲聊兜底，但给低置信度
```

**第 ① 步必须放最前面**，因为 FAQ 命中是三种结果里唯一「答案已在库里、可以秒回」的 —— **优先判它，能省掉一次 AI 调用（既花钱又慢）**。

第 ④ 步也有讲究：它给的是 **0.3** 的低置信度，**故意低于**兜底线 0.35，好让上层有机会转人工。

还有一个细节：命中技术词时，置信度是 `0.5 + 0.15 × 命中个数`，但**封顶 0.9**：

> 词表判定不该给出「绝对确定」。

> **这是个很成熟的习惯：确定性的东西才敢给 1.0，靠规则猜的就留一点余地。**

### 4.5 第三层 RAG：不让 AI 生产事实，只让它组织事实

**RAG** 的全称是「检索增强生成」，说人话就是：**先查资料，再让 AI 照着资料回答。**

**为什么非这样不可？** 因为让 AI「凭记忆」回答专业问题，它会**杜撰**。而且它杜撰的时候语气非常肯定，外行根本分不出来。

本项目的做法分三步：

```
① 从 sys_article 表里检索最相关的 3 篇文章（RAG_TOP_K = 3）
② 每篇截前 600 字（RAG_SNIPPET_CHARS），塞进提示词
③ 提示词里明确要求：「只依据下面提供的材料作答，材料里没有的内容
   要明确说『资料中没有提到』，不要凭记忆补充」
```

然后把**引用的文章标题一起返回给前端展示** —— 用户能自己点进去核对。

**这个原则在代码注释里被明确总结过**：

> 这和 S4-01 让 LLM 只指认选择器、正文由 BeautifulSoup 提取是同一个原则：**不让模型生产事实，只让它组织已有的事实**。

> **这是当前用 AI 最重要的一条工程纪律。** 模型擅长「改写、归纳、组织」，不擅长「提供事实」。把这两件事分开，AI 就从「不可信的信源」变成「有用的编辑器」。

### 4.6 兜底：六种情况一律转人工

这一层是整套设计的安全网。代码里的原则是：

> 任何一层出问题都退到「转人工」，不抛异常给用户。

| 触发情况 | `reason` 里会写什么 |
| --- | --- |
| 用户明说要人工（命中「人工」「投诉」「举报」等 5 个词） | `用户明确要求人工（命中 […]）` |
| 空提问 | `空提问` |
| 路由置信度 < 0.35 | `置信度 0.30 < 0.35（未命中 FAQ、无技术词、无寒暄词…）` |
| 判为 FAQ 但检索已无命中 | `路由判为 FAQ 但检索已无命中` |
| **AI 服务挂了** | `闲聊应答失败：…` / `RAG 生成失败：…` |
| 知识库不可用 / 无相关内容 | 见下方 |

**注意第五条**：AI 接口挂了，用户**不该看到 500 错误页**，而应该看到「已为你转接人工客服」。

> **生活比喻：医院的应急预案。** 停电了不能把病人赶出去，得有备用方案。系统里叫**优雅降级**。

#### 一个值得单独讲的细节：「没有」和「坏了」必须区分开

```python
async def _retrieve_articles(...) -> list | None:
    ...
    except SQLAlchemyError:
        return None      # ← None：知识库**不可用**（表不存在、连不上）
    if not rows:
        return []        # ← 空列表：库能查，但**没有相关内容**
```

**为什么不能用同一个返回值？** 因为排错时这两件事的处理方式完全不同：

- `None` → 数据库或迁移出问题了，要**叫工程师**
- `[]` → 内容库太薄，要**叫运营去补文章**

**而且这里藏着一个真实的陷阱**，注释里写得很清楚：

> `sys_article` 是 S4-01 才加的表，用旧版 `full_init.sql` 建的库、或没跑过迁移的库上它压根不存在，直接查会抛异常变成 500。**注意两个测试套件都发现不了这个问题：fixture 里 `create_all` 总会把表建出来，只有真起服务连真库才会暴露。**

> **这是一条对所有写测试的人都适用的教训：测试环境的「自动准备」常常会掩盖真实环境的缺失。** 你的测试里表总是存在，因为测试自己建了它 —— 但这恰恰让你测不到「表不存在时会怎样」。
>
> 本项目为此专门写了一条测试 `test_missing_article_table_degrades_to_human_not_500`，**故意把表删掉**再跑。

### 4.7 性能：一个 560 毫秒的坑

ROADMAP 要求客服响应 **< 80 毫秒**。这里有个陷阱：中文分词用的 `jieba` 库，**第一次**分词要加载词典，代码注释记录的实测值是 **约 560 毫秒**。

如果不处理，**第一个用户**就会等半秒以上 —— 指标当场不达标。

解决办法只有一行，放在模块导入时：

```python
jieba.initialize()   # 预热词典，别把 ~560ms 算进第一次请求
```

**代价**是应用启动慢一点。这笔交易很划算：**启动慢一次，好过每个冷启动后的第一个用户都慢。**

**实测**（我本地跑的，1000 次检索）：

```
1000 次检索总耗时 42.1 ms → 单次 0.0421 ms
1000 次检索总耗时 37.2 ms → 单次 0.0372 ms
```

单次 **0.04 毫秒**，对 80 毫秒的指标有约 **2000 倍**余量。

> 顺带说明：这个 80ms 指标是**能安全写成断言**的，因为余量极大。对比第 3 课讲的那个 CI 偶发失败 —— 那条断言的余量只有 1.6 倍，所以它必然抖。**判断一个延迟断言该不该写，看的是余量倍数，不是「它现在过了没有」。**

### 4.9 行业里管这些叫什么

| 本项目的做法 | 行业术语 |
| --- | --- |
| 先查资料再让 AI 照着答 | **RAG（检索增强生成）** |
| 找最像的问法而不是归类 | **语义检索 / 信息检索** |
| BM25 + 余弦一起用 | **混合检索（hybrid retrieval）** |
| 把无上界的分数压进 0~1 | **饱和函数归一化** |
| 定义插座标准，实现可替换 | **面向接口编程 / 依赖倒置** |
| 测试时塞一个假的 AI 客户端 | **依赖注入（DI）** |
| AI 挂了就转人工 | **优雅降级（graceful degradation）** |
| 判断用户想干什么 | **意图识别（intent recognition）** |
| 「有多大把握」 | **置信度（confidence）** |
| 单位时间最多问几次 | **限流（rate limiting）** |
| 返回引用来源让用户核对 | **可溯源 / 可解释性** |

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **RAG** | 先查资料，再让 AI 照着资料回答 | 开卷考试，不许凭记忆 |

| **余弦相似度** | 按「整体用词分布像不像」打分 | 按内容气质找书 |
| **分词** | 把中文句子切成词（中文没有空格，必须切） | 把「毕业设计服务」切成「毕业/设计/服务」 |
| **意图识别** | 判断用户想干什么 | 分诊台护士 |
| **置信度** | 有多大把握，0~1 | 医生对诊断的确信程度 |
| **阈值** | 低于这个数就不算数 | 及格线 |
