# 架构讲解：按请求理解当前实现

本文是 2026-09-12 重新核对源码后的当前指南，不沿用旧版手写行号、性能秒数或已撤销的产品规则。完整函数契约见各模块 README，历史故事可从 Git 记录查询。

## 2026-09-15 边界修订

当前修复与未结项见[交叉台账](../review/README.md)。微信下单先提交本地订单再跨外部网络，失败保留稳定单号可重试；现在记录预支付尝试与唯一收款凭证，但自动对账/退款仍未完成。限流请求路径只做固定批量维护，并有 key 容量上限，不能扩大为多实例承诺。生产下载基址来自 canonical 配置；日志 ID/路径有界转义。SQL 只是明确的语法子集，部分合法方言 DDL 仍需人工核对；此前“简化不影响结构”不成立。

## 1. 应用如何接收一次请求

### 核心概念大白话

main 装配 FastAPI、中间件、路由和静态文件。配置先被模块加载，生产自检在接流量前执行；启动生命周期尝试预热 FAQ。页面 HTML 与处理业务的 API 是不同入口。

### 生活比喻

页面是服务台表格，路由是办理窗口，公共模块和工具是窗口后面的处理步骤。当前窗口也自己做一些查询和事务，不能说所有工作都在“后台工坊”。

### 落到代码

main.py、app/middleware.py、app/routers/site.py、app/site.py。Jinja 渲染页面外壳，原生 JS 调同源 API；Node 只负责构建/测试，不是生产第二个服务。接口输入由 Pydantic 校验，具体权限仍由依赖及业务所有权检查保证。

### 行业术语

ASGI：异步服务接口；middleware：请求/响应外围处理；router：HTTP 路径映射；SSR：服务器生成 HTML，不意味着页面没有浏览器交互。

## 2. 登录、授权码和撤销

### 核心概念大白话

JWT 是签过名且有期限的凭据，不是无需查库的永久通行证。每次鉴权还查用户状态与 credential_version。改密递增版本，所以同一秒内两次改密也能分别撤销旧凭据。

### 生活比喻

JWT 像有到期日的门禁卡，数据库版本是当前锁的代号。改锁后旧卡不能因为印着“未过期”继续使用；清浏览器 Cookie 只是把本机卡收起来，不等于改锁。

### 落到代码

security.create_access_token / decode_token 处理签名与声明；deps.get_current_user / require_admin 查库授权。OAuth GET 只显示同意页，POST 才签发一次性 code；同意签名绑定当前用户和版本，兑换时再次核验并原子消费。

### 行业术语

HttpOnly：脚本不能直接读 Cookie；SameSite：限制跨站携带 Cookie；credential revision：凭据版本；authorization code：短时一次性授权码。这里不是完整 OIDC/PKCE/统一单点退出平台。

## 3. 数据库事务与浏览器状态为什么都需要版本

### 核心概念大白话

数据库防止两个请求同时突破配额或重复落单；浏览器还需防止旧请求覆盖新页面。两种问题发生在不同层，单独加一个锁不能全解决。

### 生活比喻

数据库是在库存本上核对“还有多少”，ETag 是核对“你改的是哪一版”，页面 epoch 是核对“这条迟到消息属于哪次打开的窗口”。

### 落到代码

database.lock_user 在事务内协调用户写入，订单 pending 唯一索引和状态 CAS 约束竞争。Drawio 保存使用 If-Match；导出请求获取实时 XML，而非相信旧 autosave 缓存；切换账号/文件更新 iframe 生命周期并丢弃旧响应。
软删除仅释放活跃名额，总条数/字节仍占用；永久删除只对回收站对象开放且不可撤销。

### 行业术语

CAS：带期望状态的条件更新；ETag/If-Match：版本前置条件；epoch：一次生命周期编号；幂等：相同操作重试不会重复产生效果。SQLite 写锁比 PostgreSQL 行锁粗，必须做真实 PostgreSQL 并发测试。

## 4. 付款、文件与人工沟通

### 核心概念大白话

付款确认给予下载权益，短时链接只是领取文件的临时凭证。downloaded 记录发过链接，不证明传输完成，不阻止重领。定制服务先在会话中协商，不自动套用数字商品价格。

### 生活比喻

付款记录像提货凭证，下载链接像临时通行码。通行码过期可以换，但有效期内转给别人仍可能被使用；不能把短时链接说成绝对防分享。预支付像先记账再给银行打电话：电话掉线也要保留单号，不能把“等待回复”当作“肯定没产生付款”。

### 落到代码

shop 的状态查询只读；download_url 检查所有者、状态和对象后发链接；serve_download 校验签名并流式发送，目前只支持本地后端。wechat预支付前先持久提交本地订单，失败留单可同号重试，付款依可信平台回调或显式验签查单；manual必须管理员核账，mock仅开发。原商户和交付文件已冻结，单笔全额原路退款核验与人工退款登记已接入；已有默认关闭的显式申请发送；自动对账/关单及商户验收仍阻断。
messages 提供持久会话、游标分页、管理员回复和 nonce 去重；support.ask 的人工建议只提供入口，不会自动派单或通知。

### 行业术语

Bearer link：持有即具访问能力的链接；presign：预签名；nonce：这里用于客户端消息去重；cursor：以消息/订单 ID 定位分页，不是页码。

## 5. 模型、解析器和抓取的失败边界

### 核心概念大白话

模型返回的是待验证的数据，不是可以直接信任的指令或事实。网站预检查不能控制之后浏览器自己的连接，因此当前未隔离 Chromium 明确停用，静态 HTTPX 抓取保留。

### 生活比喻

检查地址像核对收件单，固定实际连接才是保证快递送到核对过的地点。读到材料像拿到参考书，不代表回答自动正确。

### 落到代码

PublicTransport 固定检查过的 IP 并保留 Host/SNI；crawler 对重定向、解压体积与骨架大小设边界，politeness 管 robots/节流。extract 让模型选 CSS 选择器、由 BeautifulSoup 提取实际文本；save_article 原子 upsert，拒绝超长字段。
FAQ 词袋先行，低置信才考虑语义和模型分类；RAG 内容指纹使更新可见，语义缓存绑定提供方/凭据/模型/语料。无资料、低置信或模型不可用应回退，不能编造“已接通人工”。

### 行业术语

SSRF：服务端请求越过预期网络边界的风险；SNI：TLS 服务名；RAG：检索材料辅助生成；embedding：文本向量。真实模型阈值需要自己的语料标定。

## 6. 文档、测试与部署各能证明什么

### 核心概念大白话

文件都登记、链接都存在，不证明文字正确；单元测试通过，不证明已部署；本地通过也不等于远端同一提交通过。

### 生活比喻

目录像书的索引，链接检查像确认页码没印错，人工对照源码才是在检查内容。三者缺一不可，但不能互相冒充。

### 落到代码

check_docs_contract 检查归属、非空人工章节和指纹，build_docs_site 提取 AST、渲染页面并校验实际链接。CI 日志是临时产物，精确忽略，不应在构建过程中被反向当成新增源码。
默认单实例：内存限流/CPU 槽位不跨进程共享。升级备份、停写、执行缺失迁移、部署、重登录；当前full_init拒绝非空库，历史版本含DROP，均不能代替存量迁移。

### 行业术语

Manifest：清单；fingerprint：内容指纹；contract test：接口约定测试；integration test：组合模块测试；E2E：真实用户链路测试。Node VM 不等于真实浏览器，MockTransport 不等于真实商户联调。

## Agnes 模型配置边界

默认使用 Agnes 2.5 Flash 的 Chat Completions，显式非流式请求，输出仍经项目合同校验；“OpenAI 兼容”是协议，不代表请求发给 OpenAI。LLM_EMBED_ENABLED 默认 false，FAQ 预热/查询会短路且不发外部向量请求；开启增强必须另行确认同一提供方的向量能力并标定，不能把聊天模型当向量模型。错误保留 network/http/response/configuration 类别和 HTTP 状态，不打印提供方错误正文。接口、默认值与部署迁移详见 [Agnes 接入说明](AGNES_AI.md)。


## 第二批：初始化、启动与支付信任边界

像“签收本+钥匙验收”：db_admin在离线维护事务中持PG锁、写SQL和校验和；Web lifespan只核对账本、已知演示凭据和管理员，异常时不接流量，并在finally释放资源。新建仅空库，旧0008库明确接入账本；不宣称完整DDL属性等价。

支付不能只看“签名数学上正确”：回调还要来自当前固定平台证书/公钥ID，X509在有效期，交易属于本商户/app并是CNY/NATIVE。预支付响应有字节上限/总deadline，错误不透传服务商正文；已有唯一凭证/过程事件、应答验签、主动查单和文件快照；默认关闭的显式退款申请见第九批；显式渠道关单见第十六批；第十七批只读日账差异CLI不代替完整结算对账，部分退款及真实商户验收仍在后续范围。OAuth按完整站点SSO限定受信第一方，不冒充开放授权平台。

## 第三批：把收款签收本与交付包分开

可以把PaymentReceipt理解为每张订单的一张正式签收条，流水参考号不能借给另一张订单；PaymentEvent是每次尝试的过程记录，只有开始没有结果时不能猜失败。锁住订单、核对合同、记凭证与paid状态，必须同一事务。它不是复式会计账簿或外部对账。

文件则像封存的交付包：下单时复制并以SHA命名，订单绑定这份包而不是“今日商品”的指针。哈希检查坏包不会替换成新商品，已购买权利不消失。历史包需人工找回并核准一次，数据库和全部快照须一起备份。应用层使用独立SQLite连接测试事务，PG另外验证唯一约束及迁移触发器。实际合同与接口见[第三批](../review/RELEASE_BLOCKERS_PHASE3.md)。

## 第四批：管理员核查不是新的付款按钮

像“给收银台打电话核对，再把签收条和核对记录一同归档”：payments_admin先保存query_started，释放数据库事务后通过wechat_pay发送签名GET；微信应答先验原文签名、平台身份和时效，再核对原订单。回来重新锁住管理员核验权限，只有SUCCESS才交settle原子记凭证/paid/query_success。收到NOTPAY、CLOSED或REFUND只是观察，不逆转已有权益；超时或验签错误是未知，不是失败付款。

浏览器工作台只取管理员API数据，会话/列表/详情三层序号防迟到回填；财务写接口额外检查来源。公开HTML壳不藏客户记录，JSON用textContent显示。历史绑定和人工核账复用既有不可改写合同与唯一流水规则，不新增schema/依赖，也不把单文件数字商品误称定制服务完整生命周期。操作和剩余边界见[工作台手册](PAYMENTS_ADMIN_GUIDE.md)。

## 第五批：复核便签贴在资料快照上

像给“这一叠已经看过的资料”贴一张签名便签，后来来了新资料，便签不能自动盖住它。payment_review按事件数量/最大ID、到账凭证、状态和孤立尝试时限计算摘要；operator_review记录摘要、上轮版本、动作及操作者。最新close仅在资料未变化时显示已复核，不改付款真相。不能只用最大ID，因为拿到较小序列号的事务可能晚提交。读取按批聚合而不偷偷写任务；写入由管理员显式POST与乐观校验/锁保护。该第五批子项无新schema/依赖，也没有实现退款、分派或定制服务里程碑；退款证据和通知进展见后两节。

## 第六批：付款收据与退款收据，门票再查一次

大白话：付款收据不能因退款就撕掉，另开一张退款收据；下载链接像带订单号的临时门票，进门时仍要查看这一单是否已退款。代码上RefundReceipt与PaymentReceipt分表，原paid/downloaded不变；退款成功凭证和审计原子提交。下载签名用带用途标识的JSON数组绑定订单/key/期限，出口逐次读退款事实并核对冻结文件，不能只把签名算法改一下就算可撤权。

这里的撤权只限制本地下载的新授权，不能删除用户副本或强制终止已接纳连接；只读微信GET核验/人工已退款登记不发起资金划转。申请、PROCESSING、ABNORMAL、CLOSED及未知与完成分别记录；ordinary transaction REFUND与退款SUCCESS不是同一证据。显式退款申请见第九批；部分退款记账/权益、异常转其他账户、渠道账单和定制服务取消仍未实现；退款回调仅接入下一节的线索箱。


## 第七批：签收通知放进线索箱，不把信封当退款收据

大白话：邮差送来“退款成功”的通知，先确认邮差身份、把通知可靠收好再回“收到”。通知没有写是否原路，不能擅自补字、撕掉客户门票。管理员拿通知里的商户退款号去独立查询，拿到完整原路成功证据后才进入上一节的退款收据流程。

落到代码：main挂载refund_notify路由；parse_notice按原文签名→AES解密→字段核对产生RefundNotice；save_notice锁订单、复核原收款、对商户+通知ID去重，同事务提交PaymentEvent及唯一核验任务才204。不调用record_refund、不修改paid/downloaded、不触发后台任务或外部请求。payment_review将该事件列为复核线索；shop的管理员ledger独立读取最新摘要，payments-admin只展示和填号，仍要求人手确认与原有权限检查后查询。

术语：inbox是“可靠入站记录”，不是退款请求台账；幂等是同通知ID同事实再送不会多一条，冲突不能覆盖。指纹覆盖实现明确接收的业务字段，不保留原签名包/用户账号，也不能独立证明RSA签名。乱序通知只增加线索，不逆转成功退款凭证。partial标记只是部分退款提醒，没有实现部分退款资金结算或撤权规则。4秒应用deadline不是完整生产SLA；默认仍由管理员最终确认；独立worker可另行授权仅对可信成功查询登记系统凭证，无主动外部提醒。通知原子入站现需0015及既有只追加保护。


## 第八批：先给准备单编号，不是先让银行退款

大白话：先写一张带固定编号的准备单并归档；窗口突然断线时，找回原单而不是再开一张。准备单不是给银行的付款授权，也不是退款收据。以后接发送器还必须让管理员明确授权，不能把抽屉里所有旧准备单自动寄出去。

落到代码：RefundRequest/0012冻结原PaymentReceipt、原商户/app、全额CNY、客户端幂等ID与服务器商户退款号、登记人/内部依据；原单/原收款各唯一。prepare_refund先锁并复核用户，prepare_request锁订单、检查原付款/既有活动，原准备与PaymentEvent同事务commit后才响应。精确重发保留首笔；同单新ID/跨人跨单复用/改事实均拒绝。只读ledger独立展示，不受历史分页影响；复核候选和资料摘要直接含准备行，即使缺过程事件也能发现。

术语：本批“幂等恢复”针对本地保存丢应答，不是退款发送后的补偿系统。prepared是本地存在性，不推断微信是否受理；confirmed/completed_elsewhere仅由独立成功退款凭证派生。通知仍不生成成功收据，下载仍只按RefundReceipt撤权。SQL只追加保护不能防数据库所有者篡改；无新依赖，无真实业务库/转账。主动发送见第九批；部分/纠错、服务取消继续未实现。


## 第九批：签一张固定的申请单，再亲自点击寄出

大白话：准备单不是授权书；本批另签一张内容不能改的申请单。签好也不会自动寄出，当前管理员还须手动确认发送。断线时先看是否已有寄出尝试，不能换一个退款号码重寄。

落到代码：RefundAuthorization/0013冻结客户reason、原交易号、原退款号、全额CNY和本站回调URL的JSON正文与SHA。authorize只提交；send核开关/当前权限/原单/摘要，begin_send提交started后释放锁，再submit_full_refund签固定POST字节，finish_send持久accepted/unknown观察。申请SUCCESS不直接调用record_refund，独立查询仍是金融完成与下载撤权入口。复核直接包含授权行。

术语：attempt_id是本站一次发送尝试，out_refund_no是渠道退款幂等号；换尝试ID绝不换后者或正文。精确尝试重放是读回，不是重发；新显式尝试需60秒且无受理/独立观察。这个冷却不是worker租约，没有自动发送器/补偿消费者。默认关闭的开关也不是授权，打开后仍逐次人工确认。


## 第十批：锁住出件口，不追认已经寄出的信被追回

大白话：在已签的退款申请旁追加一张“停止以后寄出”便条，不能擦掉申请或重写金额。快递员如果已取得这次出件资格，之后仍可能送到银行；便条不等于银行已经取消退款。

落到代码：RefundSendStop/0014绑定原授权。stop_sending与begin_send都在当前用户锁之后取原订单锁，停止与audit同事务提交，新started检查stop；精确旧attempt重放只读。finish_send仍保留在途观察，query仍用原号独立核验。只读投影和复核摘要直接包含停止行，不依赖过程事件永远完整。

术语：这里的线性化点是订单锁内持久开始/停止的提交顺序，不是公网HTTP先后。停止只阻止新的本站尝试，没有worker召回、渠道取消、金额更正、号码释放或权益恢复。SQL只追加不防数据库所有者篡改。


## 第十一批：收好信，再给核验员一张派工单

大白话：通知和派工单放进同一个保险柜事务，确认收好才告诉邮差“收到”。核验员领单会留下90秒有效的领取凭条；途中断电，下一个人可重新领。旧人迟到不能拿旧凭条覆盖新结果。重复查账可以，重复转钱不可以；本worker只有GET能力。

落到代码：save_notice→enqueue是入站事务；refund_worker先检查开关/完整schema，repair_missing补旧收件箱，再claim→inputs→query_full_refund→finish。令牌、原归属、次数和数据库时钟约束最终写入，无数据库锁跨网络。队列状态可更新，PaymentEvent观察只追加；shop ledger与管理页只读取。默认保持只观察；第十三批另有系统登记权限，见下节，不改变GET-only网络边界。

术语：租约是限时领取，不是分布式恰好一次；退避是失败后逐渐延长等待；fencing是拒绝旧领取凭条。verified指独立查询观察，不是本站资金结案。系统成功凭证权限见第十三批；默认保留管理员原号核验，部分退款、发送后纠错和真实商户验收未完成；发送前重新授权见第十四批。

## 第十二批：人手接管自动待办

可把队列看成待办夹：hold把一张任务暂交人工，retry在剩余预算内放回；不是重新填写一张无限次数的退款单。管理页→control_verification（当前身份/来源/严格输入）→control_job（用户→订单→任务锁、原请求重放、最新任务摘要）→任务状态与PaymentEvent原子提交。worker不被远程召回，finish的token/状态栅栏拒绝旧结果。claim只锁任务并写事件，其订单外键KEY SHARE与订单NO KEY UPDATE兼容；不增加反向用户锁或跨网络锁。

snapshot把订单控制事件ID也算入，避免同秒hold/retry回到看似相同状态时误接旧请求（ABA）。控制重放先查不可变事件再验可变快照，返回首笔动作而非当前状态保证；GET各任务snapshot/最近操作与历史分页独立。默认成功退款仍由管理员独立查询完成；系统归属及独立授权见第十三批。

接管的界线是持久领取，而不是HTTP到达渠道：领取已提交的尝试，即使尚未发出HTTP，也可能在接管返回后继续GET；接管保证不再领取该暂停任务，并使旧结果不能覆盖当前任务，不是网络召回。


## 第十三批：系统成功凭证：把“核实”与“有权登记”分开

大白话：核验员原本只抄查询结果；运维另给登记权限后，只有拿到可信完整成功结果才可把已退款事实写入账本。不会替管理员签字，也不会按通知直接转钱。术语中“系统结算”指本站凭证落库，不是渠道资金结算。

落到代码：run_once的auto_record默认False，仅在独立query_full_refund验签/合同检查、通知退款ID及时间通过后传settlement。finish按订单→任务锁重读，核token/次数/订单/通知/DB时钟租约，在SAVEPOINT内stage_system_receipt重新绑定原收款、配置、出站参数、通知与开始事件，再用共享_stage_receipt检查全额/时间/唯一事实。最终CAS前再读数据库时钟，连暂存凭证一起拒绝租约途中耗尽。预期金融/唯一冲突回退savepoint并转attention，其他数据库故障回滚整笔；凭证、终态审计与任务只commit一次，不跨HTTP持锁。

0016允许actor_id为空但必须有唯一verification_event_id，CHECK区分真实人和固定系统归属；PG触发器核同单系统开始事件与仍有效的running租约，原全额/只追加保护不变。SQL不能验证远端RSA，类型对象本身也不是凭证；只有可信查询调用链可传入，未新增公共登记端点。授予数据库所有者权力仍可绕过触发器，不是防篡改硬件账本。默认行为和人工独立查询不变；开关不能复活旧终态。


## 第十四批：改申请用新页，不擦掉已签的旧页

大白话：把尚未寄出的申请先盖“这版不再寄”，然后另签一页更正申请。旧页、停办依据和签字都留下，新页写清接哪一页；如果曾登记“已开始寄出”，即使没看到邮差出门，也不能猜没寄而改正文。这里只更正客户原因/正式回调，不换退款号码、金额或原付款。

代码链路：管理页显式reauthorize → 来源/限流/严格schema → active_actor锁用户并重查凭据版本 → reauthorize锁订单、原key重放先行 → 验最新已停止叶子及全单无发送/查询/通知等事实 → 固定新正文与supersedes_id → 新授权和refund_reauthorized审计一次commit。初始authorize仍只能建唯一根；begin_send先按显式授权ID定位，旧尝试重放仅读，新的发送必须是当前叶子且未停止。stop按原授权ID保存/恢复，不误停止新版本。没有网络锁、自动POST或新的系统资金权限。

0017的唯一根+每前版最多一个后继和只追加形成链，不用覆盖旧行来纠错。authorization_for按无后继判当前，不靠最大ID猜；submission_view有界50版含首次人/正文/前版/停止，事件翻页不藏当前；review_states把所有授权/停止的排序事实纳入指纹，保留单版本旧摘要格式。术语：supersedes是“另版替代”，不是撤销历史；幂等重放返回首次请求，当前投影可能已更新。只认本站从未开始，不保证外部未办理；固定原号仍是渠道重复保护。

## 第十五批：值班牌不是退款凭证

大白话：独立核验员每完成一轮，就更新私有“最近值班”牌；队列有待人工或排队太久，另外亮警示灯。牌新不代表每一笔核账都成功，灯亮也不代表要不断把核验员赶走重启。

代码链路：refund_worker启动写starting→限时核完整账本→run_once原GET/租约流程→queue_snapshot按DB时间只读汇总→Publisher临时文件fsync/replace→独立refund_health命令仅读本机文件。单写OS锁在崩溃后释放，SIGTERM取消保留原租约；过期恢复仍由既有CAS/token/总次数负责，而非读取JSON重排。状态日志只记固定状态/告警变化，没有外部发送器或新财务权限。

术语：heartbeat是有时效的进度证据，默认120秒内可能滞后；liveness/freshness与业务attention分开。Compose profile默认不启动，非零退出最多重试5次，unhealthy不会自动重启；没有把容器配置文本验收当成真实监督上线。新模块不加schema、路由或依赖，不改0017及资金默认门禁。

## 第十六批：本站收起订单，不等于微信收起付款码

大白话：本地closed只是本站暂时不再等待；旧二维码可能仍能付款。管理员先按原单查微信，最新可信NOTPAY才允许再确认“把这个旧码对应订单关掉”。即使关单收到签名204，付款通知可能迟到，不能擦掉钱已到账的事实。

代码：管理页query→reconcile独立验签观察→close-channel严格确认/用户锁→order_closures.begin订单锁内先幂等恢复再验门禁/合同/无收款/新鲜NOTPAY→commit started→wechat_pay.close_order无锁签名POST→finish只记观察。不会在GET、本地下单过期或worker自动POST，closed→paid和唯一收款凭证链保持；新的观察使复核摘要变化。

术语：渠道关单不是退款，acknowledged是验签204应答，不是本站“未付款证明”；unknown需要原key恢复或先新查单+等待后新确认。此项是单笔核查衔接；日账差异见下一节，手续费结算与服务取消仍待后续。

## 第十七批：清单对照，不把差异报告当作付款证明

大白话：微信日账像供应商的送货清单，本地PaymentReceipt像签收单；清单缺一行要调查，不能直接删签收记录。退款行更像“已申请退货”时的照片，不是今天的退款状态。

落到代码：`wechat_bills.fetch_bill`复用已验签JSON取SHA1与白名单地址，单独有界读无签名文件，哈希通过才交给`parse_bill`；严格现代27列/7项汇总、定点金额与完整性预算。`bill_reconcile.run`显式开关/目标确认/迁移预检→无DB会话HTTP→只读一致性快照→纯比较→私有原子JSON。付款同时从账单找本地、从付款日凭证找账单；时区明确UTC+8，不随丹麦机器时区漂移。商品/OpenID/下载token不落报告。

术语：REPEATABLE READ是本次读取的一致视图，不是锁住将来回调；SHA1核对来自可信元数据，文件本身没有微信应答签名；SHA256仅定位此次内容。退出0也只是限定范围未见差异，`accounting_closed`始终false。没有新表、财务写入、Web接口或自动修复，运维身份不冒称网站管理员审计。操作与限制见[日账指南](WECHAT_BILLS_GUIDE.md)。
