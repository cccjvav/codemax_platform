## 第 1 课：整体架构 —— 一个请求在电脑里走了什么路

### 1.1 这个项目到底在做什么生意

一句话：**这是一个「毕设服务平台」，靠免费工具引流、靠付费服务赚钱。**

它由两个平台拼成，共用一套账号：

| 平台 | 给用户什么 | 怎么赚钱 |
| --- | --- | --- |
| **免费工具平台** | 画 ER 图（数据库结构图）、画流程图、自然语言生成图 | 不赚钱，负责把人吸引进来 |
| **商业平台** | 导出数据字典 Word 文档等付费服务 | 微信支付下单 → 付款 → 下载 |

再加三块基础设施：**统一登录**（一次注册，两个平台通用）、**智能客服**（自动答疑，减少人工）、**内容抓取**（自动收集毕设相关文章充实站内内容）。

> **为什么不拆成两个独立网站？** 因为「引流」和「变现」必须共用同一个身份。用户在免费工具里画好了图，想导出 Word 时如果还要再注册一次，绝大多数人就走了。这就是代码里反复出现的 **SSO（单点登录）** 的商业理由。

### 1.3 一次请求的完整旅程

假设你在浏览器里点了「导出 Word」，接下来发生的事：

```text
你的浏览器
   │  ① 发出请求 POST /tools/word-export
   ▼
┌─────────────────────────────────────────────────┐
│ ② 登记台（RequestLoggingMiddleware）             │
│    给这次请求发一个「快递单号」X-Request-ID       │
│    记下：谁、什么时候、花了多少毫秒               │
├─────────────────────────────────────────────────┤
│ ③ 安检（SecurityHeadersMiddleware）              │
│    在回执上贴安全标签，告诉浏览器哪些东西不许加载 │
├─────────────────────────────────────────────────┤
│ ④ 楼层指引（路由匹配 /tools/word-export）         │
│    → 交给 app/routers/tools.py 的 word_export()  │
├─────────────────────────────────────────────────┤
│ ⑤ 检查申请表（schemas.ErDiagramIn）               │
│    DDL 太长？格式不对？当场退回，不用惊动后厨     │
├─────────────────────────────────────────────────┤
│ ⑥ 限流闸门（rate_limit）                          │
│    这一分钟你已经来过太多次了？请先等等           │
├─────────────────────────────────────────────────┤
│ ⑦ 后场工坊                                        │
│    parse_ddl（解析建表语句）→ 丢到**线程**里      │
│    build_data_dictionary（生成文档）→ 丢到**进程**里│
├─────────────────────────────────────────────────┤
│ ⑧ 打包出餐（Response，带文件名与类型）            │
└─────────────────────────────────────────────────┘
   │
   ▼
浏览器收到 .docx 文件，同时回执上带着 X-Request-ID
```

**那个「快递单号」是干嘛的？** 将来你打电话报障说「我刚才导出失败了」，客服让你报出浏览器里那串 ID，工程师就能在成千上万行日志里**精确捞出你那一次请求**。没有它，线上排障只能靠时间戳猜 —— 这是 `app/middleware.py` 注释里写明的设计意图。

### 1.4 五个「为什么非要这样设计」

这一节是本笔记的重点。**只看「代码怎么写」学不到东西，看「不这样会出什么事」才行。**

#### ① 为什么用「异步」？—— 一个服务员照看十桌

**大白话**：普通写法（同步）是「服务员给 A 桌上完菜，站在旁边等 A 桌吃完，再去 B 桌」。异步是「给 A 桌下单后转身去招呼 B 桌，A 桌菜好了再回来」。

**为什么这个项目非用不可**：它大量时间在**等别人** —— 等数据库回话、等微信服务器回话、等 AI 接口回话。这些等待动辄几十上百毫秒，如果用同步写法，这段时间整个服务器就干等着，别的用户全部卡住。

**不这样会怎样**：10 个人同时用，第 10 个人要等前 9 个人全部办完。

#### ② 为什么「重活」要丢到另一个进程里？—— 收银员不能自己跑去炒菜

这是本项目最深的一个坑，代码里 `app/cpu_pool.py` 的注释记录了完整过程。

**大白话**：生成 Word 文档要**纯算**约 470~500 毫秒（本机实测）。这种「算」和「等」不一样 —— 它在抢 CPU。

Python 有一条规矩叫 **GIL（全局解释器锁）**：**同一时刻只允许一个线程执行 Python 代码**。

- 把重活丢到**线程**里：收银员虽然走开了，但**厨房钥匙只有一把**，后厨炒菜时前台照样开不了收银机。
- 把重活丢到**进程**里：相当于**另开一间厨房、另配一套钥匙**，前台完全不受影响。

**代价**：开进程比开线程贵得多（内存、启动时间）。所以代码里做了兜底 —— 进程池万一坏了，自动退回线程池，「慢但不坏」，而不是让用户看到报错页。

> **这个设计怎么被守住的？** 有一条测试专门检查这段重活**跑在哪个进程里**。曾经它是靠「测卡顿了多少毫秒」来判断的，但在 CI 服务器上误报过（机器调度抖动，不是代码变慢），后来改成直接查进程号 —— 详见 `TECH_DECISIONS.md` 的 TD-193。

#### ③ 为什么网页是「后端直接生成 HTML」，而不是用 Vue/React？

**大白话对比**：

- **前端框架（Vue/React）** = 餐厅给你食材、菜谱和一口锅，让你自己在餐桌上做菜。好处是菜能做花样，坏处是你得先有厨房（要装 Node.js、要打包、要构建）。
- **Jinja2 SSR（本项目）** = 餐厅直接把做好的菜端上来。浏览器拿到就是能看的页面。

**为什么这个项目选后者**：这是个**要上搜索引擎**的平台。搜索引擎的爬虫不喜欢「先下载一堆 JavaScript 再慢慢渲染」的页面。后端直接吐 HTML，爬虫一眼就能读到内容。

**不这样会怎样**：免费工具页搜不到 → 引流失败 → 整个商业模式的第一环断掉。

#### ④ 为什么「安检」要写得这么绕？—— 盖章 vs 重新填表

`app/middleware.py` 顶部有一段很坦诚的注释，记录了第一版的失败：

> 第一版用了框架提供的便捷写法（`BaseHTTPMiddleware`），功能全对，但客服接口从 14 毫秒涨到 **21 毫秒**，两条性能测试当场变红。

**比喻**：便捷写法相当于「每个客人进门，安检员都让他把入场表重新填一遍再核对」；现在的写法是「安检员只在原有表格上盖个章」。功能一样，开销差一大截。

**代价**：代码啰嗦、难读，所以那个文件里注释特别多。**这是典型的「用可读性换性能」，而且换的过程被记录了下来** —— 商业项目里这种记录比代码本身更值钱。

#### ⑤ 为什么「管理员权限」每次都查数据库，不写进登录凭证里？

**大白话**：登录凭证（JWT）像**演唱会手环** —— 上面写着你是谁、什么时候进的场，撕不下来也改不了，所以不用每次进门都查身份证。

但如果把「他是管理员」也印在手环上，就会出问题：**你把某人降权了，他手上那只旧手环还印着「管理员」，在过期前照样能进后台。**

所以本项目的做法是：手环上**只写你是谁**，「你是不是管理员」**每次刷卡都实时问人事部（数据库）**。

**效果**：降权**立刻生效**，不用等凭证过期。代价是每个请求多一次数据库查询 —— 用一点点性能换「权限变更即时生效」，在管理后台这种地方绝对划算。

### 1.6 行业里管这些叫什么

| 本项目的做法 | 行业术语 | 为什么是「标准做法」 |
| --- | --- | --- |
| 楼层（routers）/ 工坊（tools）/ 账本（models）分开 | **分层架构** | 改一处不会牵动全身；换数据库不用改页面 |
| 「申请表」和「账本」是两套定义 | **DTO（数据传输对象）** | 数据库里有的字段（比如密码）绝不能原样返回给用户 |
| 安检→登记→楼层，一层套一层 | **中间件洋葱模型** | 加新功能不用改老代码，套一层就行 |
| 41 项配置全放 `.env` 文件 | **12-Factor App 的第 3 条** | 同一份代码，测试环境和生产环境只换配置 |
| `/healthz` 与 `/readyz` 分开 | **存活探针 / 就绪探针** | 「活着」和「能接客」是两件事（见 1.7） |
| 565 条自动化测试 + 每次提交都跑 | **CI 持续集成** | 改坏了当场发现，不是上线后用户发现 |
| 每个取舍都编号记录在 `TECH_DECISIONS.md` | **ADR（架构决策记录）** | 半年后接手的人不用猜「当初为什么这么写」 |

## 第 2 课：登录与权限 —— 服务器是怎么认得你的

### 2.1 先说清楚登录在解决什么问题

HTTP 有个天生的毛病：**它没有记性**。你这一次请求告诉服务器「我是张三」，下一次请求服务器完全不记得你是谁 —— 就像每天去同一家便利店，店员每天都把你当新客人。

所以「登录」这件事的本质是：**给你一个随身携带、难以伪造的身份证明**，之后每次请求你都出示它。

整个流程只有两步：

```text
① 你输入账号密码  →  服务器核对  →  发你一张「凭证」
② 之后每次请求，你都带上这张凭证，服务器验一下真伪就放行
```

难点全在第 ① 步发的那张凭证上。

---

### 2.2 生活比喻：演唱会手环

进场时工作人员核对你的票，然后给你**戴上一个一次性手环**。之后你在场内买饮料、进 VIP 区，都只看手环，不用再翻票。

这个比喻很准，但要看清它的四个细节：

| 手环的特点 | 对应到代码 |
| --- | --- |
| 上面印着你的名字和场次 | 凭证里写着「你是谁」和「什么时候过期」 |
| **戴上就撕不下来**，也没法自己画一个 | 凭证有防伪签名，改一个字符就作废 |
| 上面印的字**谁都能看** | ⚠️ 凭证内容**没有加密**，任何人都能读（见 2.4） |
| 手环有截止日期 | 默认 30 分钟后过期 |

---

### 2.3 密码：为什么数据库里根本看不到你的密码

**大白话**：数据库里存的**不是你的密码**，而是密码的「单向指纹」。

**实测**（在本地真的跑了一遍 `hash_password('123456')` 两次）：

```text
第一次：$2b$12$e7yh1lzgog/aNC2Z4G72vuW.2r6DhVGdg7Fa8/8P9EMvpjfInfF.G
第二次：$2b$12$KxfhrIWXfBpFT0poda40/uG49O9uA4m5lhtkBTJLHPqQp62HFh1mS
```

**同一个密码，两次结果完全不同** —— 这不是 bug，这是设计。

**为什么要故意不一样？** 假设两个用户都用 `123456`，如果加密结果固定，攻击者拖走数据库后一眼就能看出「这两人密码相同」，还能拿一张预先算好的「密码 → 指纹」对照表（叫**彩虹表**）批量反查。每次都掺一点随机料（叫**盐**），这张表就废了。

**关键点：这个过程不可逆。** 你没法从 `$2b$12$e7yh...` 算回 `123456`。那服务器怎么验证你登录？

> 它**不算回**你的密码，而是把你这次输入的密码**用同样的盐再算一次指纹**，比对两个指纹一不一样。
>
> 生活比喻：**指纹锁**。锁不保存你的手指，只保存指纹图案；你来了它现场采一次比对。

**不这样做会怎样？**

- 存明文 → 数据库一泄露，全站用户密码裸奔。而且**大量用户在多个网站用同一个密码**，你的泄露会连累他们的邮箱和网银。
- 用 MD5 这类「快」的算法 → 攻击者用显卡每秒能试几百亿次。**密码存储必须故意慢**，`bcrypt` 就是为此设计的（那串里的 `12` 是「难度档位」，越大越慢）。

**落地文件**：`app/security.py` 的 `hash_password()` / `verify_password()`，底层是 `passlib` + `bcrypt`。数据库列 `sys_user.password` 长度 255，实测指纹 60 字符。

> **绝不自己写加密算法。** 这是行业铁律 —— 自己想出来的加密一定有你没考虑到的攻击面。

---

### 2.4 凭证（JWT）：拆开看它在电脑里长什么样

**大白话**：登录成功后服务器发给你的，是一串用两个点分成三段的字符串。

**实测**（真的签发了一张然后拆开）：

```text
第 1 段（头部）  eyJhbGciOiJIUzI1NiIsInR5cCI6...  →  {"alg": "HS256", "typ": "JWT"}
第 2 段（内容）  eyJzdWIiOiJ6aGFuZ3NhbiIsImV4...  →  {"sub": "zhangsan",
                                                       "exp": 1788515449,
                                                       "pwd": 1788508800}
第 3 段（签名）  ZEi5MTlb3K0DxPRXjhgzqoWBM55h...     （二进制，读不出字）
```

#### ⚠️ 必须记住的一点：**第 2 段没有加密**

上面那个 `→` 右边的内容，是我用**任何语言十行代码**就能还原出来的。也就是说：

> **任何人拿到你的凭证，都能直接读出里面写了什么。**
> 只是他**改不了** —— 一改，第 3 段的签名就对不上。

**实测**：把凭证最后一个字符改掉，服务器的校验函数返回 `None`（即「无效」）。

**生活比喻**：手环上的名字是**明刻**的，谁都能看；但手环上有一个**防伪钢印**，你想把「张三」磨掉改成「李四」，钢印就花了，一眼假。

**所以凭证里绝不能放密码、手机号、身份证号。** 本项目的凭证里只有三样东西：

| 字段 | 意思 |
| --- | --- |
| `sub` | 你是谁（用户名） |
| `exp` | 什么时候过期 |
| `pwd` | 签发那一刻，该用户「上次改密码的时间」的副本 ← 这个是精髓，见 2.6 |

#### 为什么故意不把「你是不是管理员」放进去？

见第 1 课 1.4 ⑤：放进去就等于把职位**印死在手环上**，降权了旧手环照样能进后台。所以本项目每个请求都去数据库现查一次。

**落地文件**：`app/security.py` 的 `create_access_token()` / `decode_token()`。

### 2.5 凭证存在哪：为什么浏览器脚本读不到它

这是本项目真实做过的一次安全改造（`TECH_DECISIONS.md` 的 TD-44）。

**大白话**：网页里跑的 JavaScript 是**别人写的代码**。如果页面被塞进一段恶意脚本（这类攻击叫 **XSS**），那段脚本能读到的东西就等于攻击者能读到的东西。

两种存法的区别：

| 存法 | 恶意脚本能拿到吗 | 比喻 |
| --- | --- | --- |
| 存在 `localStorage`（很多教程这么教） | **能，一行代码就读走** | 把家门钥匙放在门口地垫下 |
| 存在 **HttpOnly cookie**（本项目的做法） | **读不到**，浏览器直接拒绝 | 钥匙交给门卫，你刷脸进门 |

所以本项目的登录接口**同时走两条通道**：

- **浏览器** → 收到 `Set-Cookie`，之后浏览器自动带上，前端代码全程碰不到凭证
- **API 客户端 / Swagger 调试页** → 从响应体里拿 `access_token`，手动放在请求头里

代码在 `app/routers/auth.py` 的 `_set_auth_cookie()`，四个属性每个都有讲究：

| 属性 | 值 | 为什么 |
| --- | --- | --- |
| `HttpOnly` | 是 | 脚本读不到 —— **这就是整件事的目的** |
| `SameSite` | `Lax` | 挡住跨站的写操作（防 **CSRF**：别的网站偷偷用你的身份提交表单） |
| `Secure` | **仅生产环境** | 本地是 http，加了这个浏览器根本不存 cookie，本地就没法调试了 |
| `Max-Age` | 与凭证同寿命 | 免得 cookie 活得比凭证久，反复撞「未登录」 |

#### `Lax` 是有代价的，而且这个项目把代价管起来了

`Lax` 只挡跨站的 **POST/PUT/DELETE**；跨站的 **GET**（比如从微信里点个链接跳过来）**照样会带上凭证**。

所以推出一条铁律：**凡是「会产生副作用」的接口，一律不能是 GET。**

**这条铁律不是靠自觉，是靠测试钉住的**：`tests/test_auth_cookie.py` 里有一份「需要登录的 GET 路由」清单，谁新增一个就会被测试拦下来，逼他解释「你这个 GET 为什么没有副作用」。

> 举个真实例子：下载已购文件这个接口，本来最自然的写法是 `GET /shop/download/xxx`。但它会把订单状态从「已付款」烧成「已下载」—— 这是副作用，所以最终实现是 **`POST /shop/download/{order_no}`**，并且有专门的测试验证「用 GET 请求会被拒」。

同一个测试文件里还有一条更狠的：它**真的用 node 跑了一遍前端页面的内联脚本**，并给 `localStorage` 塞了一个「一被碰就报错」的假对象。谁哪天又把凭证写回浏览器存储，这条测试当场炸。

> **静态搜一遍只能证明「现在没有」；真的跑一遍才能证明「这段代码的执行路径上没有」。**

### 2.6 三个灵魂拷问：这张凭证到底什么时候失效？

这一节全部有**实测结果**，不是推理。

#### ① 改了密码，之前所有设备上的登录还有效吗？→ **立刻全部失效**

**做法很巧**：凭证里带一个 `pwd` 字段，值是「签发那一刻，用户上次改密码的时间」。每次请求，服务器拿它和**数据库里的当前值**比一比：

```text
凭证里的时间  <  数据库里的时间   →  说明这张凭证是「改密码之前」签的  →  拒绝
```

**为什么不用一张「已作废凭证名单」？** 那种做法（叫**黑名单**）要建表、要写入、要清理过期条目。用时间戳比大小，**零存储成本**就实现了「一次吊销该用户所有旧凭证」。

> 这正是「改密码」最主要的用途：怀疑密码泄露时，**光改密码而旧凭证还能用，等于没改**。

而且改密码接口会**返回一张新凭证**并替换掉 cookie —— 当前这次会话不该被自己踢下线，要踢的是**其他**设备。

#### ② 账号被封了，手上那张还没过期的凭证还能用吗？→ **不能，立刻失效**

**这一条曾经记错过。** `TECH_DECISIONS.md` 的 TD-70 原文暗示「封号后旧凭证仍有效」，后来被测试订正了 —— 现在 `tests/test_token_revocation.py` 里有一条用例专门钉住它，名字就叫 `test_disabled_user_token_is_rejected_immediately`：

```text
1. 注册并登录，拿到凭证        → 用它访问 /auth/me  → 200 ✓
2. 把该用户的 status 改成 0（封号）
3. 用同一张凭证再访问 /auth/me → 401 ✗ 被拒
```

我本地实跑了这个文件：**15 passed**。

**为什么能立刻生效？** 因为第 1 课讲过的那个设计 —— 每个请求都要查一次数据库（本来就要查密码修改时间），顺手就把账号状态一起看了。**这就是「不缓存、每次查库」换来的好处。**

#### ③ 点了「退出登录」，那张凭证真的作废了吗？→ **没有**

这一条要**诚实说清楚**，因为它是本项目的一个已知取舍。

退出接口做的唯一一件事是：**让浏览器把 cookie 删掉**。服务端**没有记录**发出去过哪些凭证，所以也就没有「作废」这个动作。

**后果**：如果那张凭证在退出前已经被人偷走了，它在那 30 分钟内**仍然有效**。

**为什么接受这个取舍？** 要真正做到「退出即作废」，就必须维护一张黑名单表 —— 而那恰恰是 ① 用时间戳巧妙绕开的东西。**代价记在 TD-70 的粒度说明里。**

> 顺带一个有意思的设计：退出接口**故意不要求登录**。因为拿着一个已过期凭证的客户端也应该能把它清掉，否则用户会卡在「我明明点了退出，浏览器却还带着一个死凭证」的怪状态。

### 2.7 完整流程串起来

```text
你输入 张三 / 123456
        │
        ▼
┌────────────────────────────────────────────┐
│ 限流闸门：这一分钟你试太多次了？先等等      │
├────────────────────────────────────────────┤
│ 查库找到张三 → 取出那串指纹                  │
│ 把 123456 用同样的盐算一遍指纹 → 比对        │
│   不一样 → 401「用户名或密码错误」           │
│        （故意不说清是账号错还是密码错，       │
│          否则这接口就成了「猜账号」工具）     │
├────────────────────────────────────────────┤
│ 检查 status：被封了？→ 403「账号已禁用」      │
├────────────────────────────────────────────┤
│ 签发凭证：{sub: 张三, exp: 30分钟后,          │
│            pwd: 上次改密码的时间}             │
├────────────────────────────────────────────┤
│ 两条通道一起给：                             │
│   浏览器     ← Set-Cookie（HttpOnly）        │
│   API 客户端 ← 响应体里的 access_token        │
└────────────────────────────────────────────┘

之后每次请求：
   带上凭证 → 验签名 → 验过期 → 查库 → 验 status
            → 比 pwd 时间戳 → 取 role 判断权限 → 放行
```

### 2.9 行业里管这些叫什么

| 本项目的做法 | 行业术语 |
| --- | --- |
| 单向指纹 + 盐 + 故意慢 | **密码哈希（password hashing）**，`bcrypt` 是主流选型之一 |
| 三段式、带签名、内容可读 | **JWT（JSON Web Token）** |
| 内容不加密、只防篡改 | **签名（signature）而非加密（encryption）** |
| 每次请求都要出示凭证 | **无状态认证（stateless auth）** |
| 服务端不记会话 | 与 **Session/Cookie 有状态方案**相对 |
| 脚本读不到的 cookie | **HttpOnly cookie** |
| 挡跨站写操作 | **CSRF 防护**（靠 `SameSite`） |
| 挡注入脚本偷数据 | **XSS 防护**（靠 HttpOnly + CSP） |
| 返回信息里剔除敏感字段 | **DTO 白名单**（`UserOut` 只有 4 个字段，**不含 password**） |
| 「一次操作最多试几次」 | **限流 / 防暴力破解** |
| 登录失败不透露具体原因 | **防用户枚举（user enumeration）** |

### 2.10 术语白皮书（第 2 课）

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **哈希 / 指纹** | 单向压缩，算得出来但倒推不回去 | 指纹锁：不存手指，只存图案 |
| **盐（salt）** | 每次掺一点随机料，让相同密码产生不同结果 | 同一道菜，每家放不同的香料 |
| **彩虹表** | 攻击者预先算好的「密码 → 指纹」对照表 | 一本万能钥匙对照册 |
| **JWT** | 三段式的防伪身份凭证 | 演唱会手环 |
| **签名** | 防篡改的防伪印记（内容仍可被阅读） | 手环上的钢印 |
| **加密** | 让内容变得读不懂（与签名是两回事） | 把字放进保险箱 |
| **XSS** | 攻击者往网页里塞进自己的脚本 | 有人在你的公告栏贴了小广告 |
| **CSRF** | 别的网站偷偷借用你的身份提交操作 | 有人拿着你的印章去盖章 |
| **HttpOnly** | 这个 cookie 脚本读不到 | 钥匙交给门卫，不放地垫下 |
| **SameSite=Lax** | 跨站的写操作不带凭证 | 出了这个商场，印章就不认了 |
| **黑名单** | 记录「哪些凭证已作废」的清单 | 挂失名单 |
| **无状态** | 服务端不记你是谁，全靠你每次出示凭证 | 每次都看手环，不认脸 |
| **限流** | 单位时间最多试几次 | 输错三次锁卡 |
| **用户枚举** | 通过报错差异猜出「哪些账号存在」 | 挨家敲门看哪家有人应 |
| **role / 角色** | 你是普通用户还是管理员 | 工牌上的岗位 |

## 第 3 课：支付闭环 —— 钱和货怎么保证不出错

### 3.1 这一课的核心矛盾

前面两课讲的功能，做错了大不了是「页面显示不对」。**支付不一样：做错了就是真金白银的事故。**

具体有三种事故，严重性完全不同：

| 事故 | 严重程度 |
| --- | --- |
| 用户付了钱，没拿到货 | **最严重** —— 这是欺诈，要退款、要道歉、要上投诉平台 |
| 用户没付钱，拿到了货 | 严重 —— 亏钱，但不至于违法 |
| 用户买了一份，下载了十次转卖 | 中等 —— 亏钱 |

**记住这个排序，本课所有设计都是在给它排序。** 当两种错误只能避免一种时，代码选择避免第一种。

---

### 3.2 生活比喻：为什么不能「先查一下再改」

想象一个**只剩一张票**的售票窗口，同时来了两个人。

**错误做法**（先查再改）：

```text
A：还有票吗？  窗口：有。
B：还有票吗？  窗口：有。      ← 问的是同一时刻的状态
A：给我一张。  窗口：好，给你。
B：给我一张。  窗口：好，给你。  ← 票只有一张，卖出去两张
```

问题出在**「查」和「改」是两步**，中间有空隙，另一个人可以挤进来。

**正确做法**（本课的主角，叫 **CAS**）：

```text
把两步合成一步：「如果还有票，就把它卖给我」——由数据库保证这中间插不进别人。
```

数据库天然能做到这一点，因为它对同一行数据的写操作是排队的。**关键是不要自己拆成两步。**

---

### 3.3 订单状态机：只允许走这几条路

**大白话**：一张订单从生到死，只能按固定路线走，任何「跳跃」都被拒绝。

本项目一共 4 个状态（`app/order_state.py`）：

```text
        付款成功              请求下载
待支付 ─────────→ 已支付 ─────────→ 已下载
pending            paid            downloaded
   │
   │ 30 分钟没付
   ▼
已关闭 closed ─────→ 已支付        ← 注意这条「反直觉」的边，见下
```

代码里就是一张表，**所有地方都查这张表，谁都不许自己写 if**：

```python
ALLOWED = {
    "pending":    ("paid", "closed"),
    "closed":     ("paid",),        # ← 故意的，见 3.4
    "paid":       ("downloaded",),
    "downloaded": (),               # 终点，出不去
}
```

**为什么非要集中成一张表？** 因为支付回调、发货、下载是**三段不同的代码**。如果每段各写一遍 `if`，迟早会出现某一段漏了一个条件 —— 比如「未支付也能下载」。**把规则收成一处，就没有「漏掉」的可能。**

#### 那条反直觉的边：已关闭的订单为什么还能变成已支付？

第一眼看这是 bug：订单都关了，怎么还能付款？

**因为「关单」只是我们这边不再等它了，用户完全可能已经扫了那个旧二维码把钱付了。**

> 这时候如果拒绝，就是**收钱不发货** —— 正是 3.1 里排第一的那种事故。

代码注释写得很直白：

> 钱到账就必须发货，否则是收钱不发货（TD-156）。

而且这条边**不是靠注释守着的**，有一条测试专门钉住它：`test_late_payment_on_closed_order_still_delivers` —— 把订单时间改到 999 分钟前 → 触发关单 → 确认状态是 `closed` → 再付款 → **断言必须 200 且状态变成 `paid`**。

#### 一个「少即是多」的设计：没有 `expire_at` 字段

订单表里**没有**「过期时间」这一列。因为：

```text
过期时间 = 下单时间 + 配置里的 30 分钟
```

**能算出来的东西就别存。** 多存一列，就多了一个「改了配置但老数据没同步」的隐患。

---

### 3.4 幂等：同一件事发生十次，结果和发生一次一样

**大白话**：**幂等**就是「重复做不会出事」。

**生活比喻**：电梯的上行按钮。你按一次它来，你急得按十次它也还是来一次 —— 不会来十部电梯。反过来，**取快递**就不幂等：取一次少一件，取两次就少了两件。

#### 为什么支付必须幂等？

因为**微信支付会重复通知你**。网络抖一下、你的服务器响应慢了一点、微信没收到你的确认 —— 它都会**再推一次**。这是设计好的，不是故障。

所以回调处理必须能应对「同一笔支付被通知五次」。本项目的做法：

```python
if order.status == PENDING:
    order.transaction_id = ...      # 只有第一次才写入支付信息
    order.paid_at = ...
await mark_paid(db, order)          # 已经是 paid 了就返回 False，不报错
```

**注意两个细节**：

1. **重复通知不报错**，只是「什么也不做」。如果报错，微信会认为你没处理成功，**继续重推，无限循环**。
2. **不覆盖首次的支付信息**。否则第二次通知带来的数据会把第一次的覆盖掉，对账时就乱了。

#### 一个容易忽略的规矩：什么时候必须回「成功」

微信的规矩是：**你回 4XX/5XX，它就重推。**

所以本项目里，「重试也没用」的情况一律回 200：

| 情况 | 回什么 | 为什么 |
| --- | --- | --- |
| 验签失败 | 401 | 可能是攻击，也可能证书没配好，值得重试 |
| 金额不符 | 400 | 数据有问题，要人工介入 |
| 订单不存在 | 404 | 同上 |
| **这是退款通知，本阶段不处理** | **200** | 重试一百次也不会变成支付通知 |
| **这单早就处理过了** | **200** | 同上 |

**把后两种写成报错，就会招来无限重推。** 这是接第三方回调最容易踩的坑。

### 3.5 原子性：并发下只能有一个赢

回到 3.2 的售票比喻。「一次性下载」面临的就是这个问题。

**代码里原本已经有一道检查了**：

```python
if order.status == DOWNLOADED:
    raise HTTPException(403, "该订单已下载过")
```

**但这道检查在并发下是无效的。** 因为 4 个请求同时进来，它们**同时读到** `status = paid`，于是 4 个都认为「还没下载过」，4 个都放行。

真正起作用的是下面这句 —— 它必须**看返回值**：

```python
won = await mark_downloaded(db, order)   # 内部是 UPDATE ... WHERE status='paid'
if not won:
    raise HTTPException(403, "该订单已下载过")
```

`UPDATE ... WHERE status='paid'` 的意思是「**只有当它现在还是 paid，才改成 downloaded**」。数据库保证这中间插不进别人，所以 4 个并发请求里**只有 1 个的 `rowcount` 是 1**，其余 3 个是 0。

代码里专门写了一段注释警告：

> **必须看返回值**……忽略返回值的话，并发 4 个请求会全部拿到有效链接，「一次性下载」直接失效。

**这个警告有测试兜底**（`tests/test_e2e.py::test_concurrent_download_only_one_wins`）：

```python
results = await asyncio.gather(*[client.post(f"/shop/download/{order_no}") for _ in range(4)])
assert codes.count(200) == 1        # 恰好一个成功
assert set(codes) - {200} == {403}  # 其余全是 403
```

> **串行测试通过，不代表并发也守得住。** 这类 bug 在开发时几乎不可能手动测出来，只有专门写并发测试才能钉住。

### 3.6 回调安全：怎么确认「真的是微信在通知我」

支付回调这个接口**故意不做登录鉴权** —— 因为调用方是微信服务器，它没有你网站的账号。

那怎么防止**别人伪造一个「用户已付款」的通知**来白拿货？三道关：

#### 第一关：验签（确认「真的是微信发的」）

**生活比喻**：信封上的**火漆印**。任何人都能写信，但只有微信有那个印章。

微信用它的私钥在报文上盖一个签名，你用微信的**平台证书**（公钥）验。签名对不上 → 401。

#### 第二关：解密（确认内容没被看/被改）

报文体是**加密的**（AES-GCM 算法），密钥是你和微信之间约定的 `WX_API_V3_KEY`。

**AES-GCM 的好处**：它不只加密，还**自带防篡改** —— 内容被动过一个字节，解密直接失败。

#### 第三关：校验金额（最容易被漏掉的一关）

```python
if total != order.amount:
    return _fail(400, f"金额不符：回调 {total} 分，订单 {order.amount} 分")
```

**为什么必须校验？** 因为前两关只证明「这是微信发来的、关于某笔真实支付的通知」，**不证明这笔钱的数额对得上你的订单**。

> 攻击场景：商品 199 元，攻击者用另一个渠道付了 1 分钱，然后把那笔真实支付的通知**重放**到你的回调地址 —— 签名是真的、解密也成功，只有金额对不上。**这一行就是拦这个的。**

本项目商品金额是 `SHOP_PRODUCT_AMOUNT = 19900`，**单位是「分」**（¥199.00）——
这不是我推测的，`app/models.py` 里那一列的定义就写着
`amount: Mapped[int] = mapped_column(Integer)  # 金额，单位：分`，类型是**整数**。

> **为什么用「分」而不用「元」？** 因为 `0.1 + 0.2` 在计算机里**不等于** `0.3`（浮点数误差）。钱的计算一律用整数最小单位，这是行业铁律。

#### 三个「本地测不出来、上线才炸」的细节

`app/wechat_pay.py` 顶部记录了三个必须钉死的点，值得单独讲，因为它们**在本地怎么测都是对的**：

1. **参与签名的字节，必须和实际发出去的字节一模一样。** 所以代码先把数据序列化成字符串 → 用**这串**去签名 → 再把**同一串**发出去。中途任何一次重新序列化（键的顺序变了、空格多了、中文被转义了）都会让验签失败。
2. **参与签名的网址不含域名**，只有路径和参数。
3. **回调验签必须用「原始报文」**，不能先解析成对象再重新序列化 —— 理由同第 1 条。所以代码里用的是 `await request.body()` 取原文。

> 这三条是接第三方支付最典型的坑：**本地全绿，真机验签失败**。因为本地没有真正的微信服务器来挑你的刺。

### 3.7 下载：两重校验

拿到「已支付」只是第一步，下载还有两道闸：

| | 校验什么 | 防什么 |
| --- | --- | --- |
| **第一重** | 数据库里的订单状态（`paid → downloaded` 只能走一次） | 同一份资源被无限下载、转卖 |
| **第二重** | 下载链接的签名 + **5 分钟**过期（`DOWNLOAD_URL_TTL = 300`） | 链接被转发给别人用 |

**主力是第一重。** 第二重只是「缩小转发窗口」—— 因为链接一旦发出去，在那 5 分钟内谁拿到都能用。

#### 签名里为什么要把「文件名」也签进去

```python
hmac.new(secret, f"{key}\n{expires}", sha256)
```

如果只签过期时间，那么**拿到一个合法链接的人，把网址里的文件名改掉，就能下载别的文件**。把文件名一起签进去，改一个字签名就对不上了。

#### 一个细节：比较签名要用「防侧信道」的写法

```python
hmac.compare_digest(算出来的签名, 传进来的签名)
```

普通的 `==` 比较字符串时，**遇到第一个不同的字符就返回**。攻击者可以精确测量响应时间：猜对第一位比猜错的慢一点点……以此逐位试出正确签名。这叫**时序侧信道攻击**。`compare_digest` 不管对不对都比完全部再返回，时间恒定。

#### 一个诚实的取舍：「已下载」是在发链接时就标记的

代码注释说得很清楚：

> 标记为已下载发生在**发出链接时**，不是文件真的被下载时。云存储是客户端直连对象存储，应用根本看不到那次下载（TD-129）。

**后果**：如果链接发出去后用户网络断了、没下成，这一份额度也已经烧掉了。这是「用云存储省服务器带宽」必须付的代价。

### 3.8 没有商户号怎么开发：模拟支付开关

微信支付需要**六项凭据**（商户号、API 证书、密钥……）外加一个**公网 https 回调地址**。开发时两样都没有。

本项目的做法是一个开关：`SHOP_PAY_MODE`

| 值 | 行为 |
| --- | --- |
| `wechat`（默认，生产） | 调真微信下单；六项没配齐直接 **503** 拒绝，不发出注定失败的请求 |
| `mock` | 不调微信，二维码指向本站的模拟收银台页面 |

**两个关键设计**：

1. **生产环境下模拟端点一律 404。** 不是「返回错误」，是**根本不存在**。这样演示用的后门不可能被带上生产环境。
2. **模拟支付复用与真实回调完全相同的状态机**（都调 `mark_paid`）。

> 第 2 点特别重要：**演示走通的路径和上生产走的是同一条**。如果为演示单独写一套代码，那套代码永远不会被真实场景验证过，上线当天才第一次跑。

### 3.9 完整流程串起来

```text
① 用户点「下单」
   └→ 已有未支付单？没过期就复用（避免连点刷出一堆单）
                 过期了就关掉、另起一单
   └→ 先把订单落库，再去微信下单
      （微信那边付了、我们这边没单，比反过来难收拾得多）
   └→ 拿到 code_url → 前端画成二维码

② 用户扫码付款（微信 App 里完成，与本站无关）

③ 微信回调 POST /shop/pay/notify
   └→ 验签（平台证书）        不过 → 401
   └→ 解密（AES-GCM）         不过 → 400
   └→ 是支付成功通知吗？      不是 → 200（避免无限重推）
   └→ 订单存在吗？            不在 → 404
   └→ 金额对得上吗？          不符 → 400
   └→ mark_paid（幂等 + 原子）
   └→ 回 200

④ 用户点「下载」POST /shop/download/{order_no}
   └→ 是自己的单吗？          不是 → 404（不暴露是否存在）
   └→ 付过钱吗？              没有 → 403
   └→ 已经下过吗？            下过 → 403
   └→ 生成预签名链接（5 分钟）
   └→ mark_downloaded —— **看返回值**，抢不到就 403
   └→ 返回链接

⑤ 用户点链接 GET /shop/dl?key=...&expires=...&signature=...
   └→ 验签名与过期时间        不过 → 403
   └→ 吐文件
```

### 3.11 行业里管这些叫什么

| 本项目的做法 | 行业术语 |
| --- | --- |
| 重复通知不出事 | **幂等（idempotency）** |

| 链接签名 | **HMAC** |
| 比较密钥时用恒定时间 | **防时序侧信道（timing-safe comparison）** |
| 钱用整数最小单位 | **避免浮点误差** |
| 第三方主动通知你 | **Webhook / 回调** |

### 3.12 术语白皮书（第 3 课）

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **幂等** | 重复做多少次，结果都一样 | 电梯上行按钮：按十次也只来一部 |
| **CAS** | 「只有还是原样才改」，一步完成 | 「如果还有票就卖给我」，中间插不进人 |
| **并发** | 多件事同一瞬间发生 | 两个人同时问「还有票吗」 |
| **状态机** | 规定好的、只能按路线走的状态变化 | 地铁闸机：不刷卡进不去，进去了就不能再进 |
| **回调 / Webhook** | 别人办完事主动来通知你 | 快递到了驿站打电话给你 |
| **重推** | 你没确认收到，对方就再通知一次 | 打电话没人接，隔一会儿再打 |
| **验签** | 确认消息真的来自对方且没被改 | 信封上的火漆印 |
| **AES-GCM** | 一种加密方式，顺带能发现内容被改过 | 保险箱 + 封条，动过就知道 |
| **预签名 URL** | 带签名和有效期的下载链接 | 限时限次的取货码 |
| **HMAC** | 用共享密钥算出的防伪码 | 只有你俩知道的暗号 |
| **时序侧信道** | 靠「响应快慢」偷猜密钥 | 听保险箱「咔哒」声逐位试密码 |
| **重放攻击** | 把截获的真实请求再发一遍 | 录下你的语音去骗门禁 |
| **分（金额单位）** | 用整数存钱，避免小数误差 | 记账记「19900 分」而不是「199.00 元」 |
| **503 / 400 / 401 / 403 / 404 / 409** | 服务器回话的「状态码」，见下方补充 | 快递单上的处理结果代码 |

#### 补充：这一课出现的状态码

| 码 | 大白话 | 本课哪里用到 |
| --- | --- | --- |
| **200** | 办好了 | 回调处理成功（含「重试也没用」的情况） |
| **400** | 你给的东西不对 | 金额不符、报文解不开 |
| **401** | 我不知道你是谁 | 验签失败 |
| **403** | 我知道你是谁，但你不能做这件事 | 未支付、已下载过 |
| **404** | 没这东西 | 订单不存在（**别人的单也回这个**，不泄露它是否存在） |
| **409** | 状态冲突了 | 非法状态迁移 |
| **503** | 我现在没法服务 | 支付没配置、存储后端不可用 |

## 第 4 课：智能客服三层 —— 为什么高频问题不该用 AI 回答

### 4.1 先看清三个矛盾

「接个 AI 客服」听起来很简单，但它同时撞上三堵墙：

| 矛盾 | 具体表现 |
| --- | --- |
| **AI 会瞎编** | 你问「怎么退款」，它能编出一套根本不存在的退款流程，说得还很自信 |
| **AI 要花钱** | 每次调用都按字数计费。「多少钱」这种问题一天被问一百遍，每次都花钱 |
| **AI 很慢** | 一次调用几百毫秒到几秒。「你好」也要等两秒，体验很差 |

**所以这一课的核心结论是：能用规则和查表解决的，绝不动用 AI。**

这不是「技术保守」，而是把 AI 用在它**真正不可替代**的地方。

---

### 4.2 生活比喻：医院分诊台

大医院进门有个**分诊台**，护士看一眼就把你分去不同地方：

| 分诊台判断 | 客服的三层 | 代价 |
| --- | --- | --- |
| 「量体温这种小事，自助机就行」 | **第一层 FAQ**：库里已有标准答案，直接给 | 几乎为零 |
| 「普通感冒，去门诊找医生」 | **第二层 闲聊**：交给轻量 AI 自由发挥 | 花钱、慢一点 |
| 「疑难杂症，得找专家，还要调病历」 | **第三层 RAG**：先查资料，再让 AI **照着资料**回答 | 最贵 |
| 「这个我也说不准，你去找主任」 | **兜底 转人工** | 人工成本 |

**关键在于「分诊」本身要便宜。** 如果分诊也要挂一次专家号，那分诊就失去意义了 —— 这就是为什么第一层必须是纯查表。

### 4.3 第一层 FAQ：这是「检索」，不是「分类」

#### 一个必须纠正的直觉

很多人以为「判断用户想问什么」是个**分类**问题（像邮件分垃圾/非垃圾）。**但对于高频 FAQ，它其实是「找最像的那句话」。**

- **分类**：把输入塞进预先定义好的几个格子里。
- **检索**：在已有的问法库里，找一条**最像**的，把它的标准答案给你。

本项目 12 条 FAQ，每条都带一个「标准问法」和一组「其它说法」：

```python
Faq("毕业设计服务怎么收费", "按题目难度与工作量报价，本科毕设 199 元起……",
    ("价格", "多少钱", "报价", "费用", "贵吗"))
```

用户问「服务多少钱」，检索发现它和这条最像，于是直接返回那条答案。**全程没有 AI 参与。**

#### 为什么要两种算法一起用

单一算法各有死角，所以两路融合（`BM25_WEIGHT = 0.6`，即 BM25 占六成、余弦占四成）：

| 算法 | 擅长什么 | 生活比喻 |
| --- | --- | --- |
| **BM25** | 关键词命中。「发票」这个词在讲发票那条里出现得多，而且这个词在全库很稀有，所以权重高 | 图书馆按**书名关键词**找书 |
| **余弦相似度** | 换了说法也能认。「怎么开票」和「能否开发票」字面不同，但整体用词分布接近 | 按**书的内容气质**找书 |

BM25 的分数**没有上限**，而余弦是 0~1，两者不能直接相加。所以先用一个「饱和函数」把 BM25 压进 0~1：

```python
x / (x + 3.0)     # x 越大越接近 1，但永远到不了 1
```

那个 `3.0` 不是随手写的，是按现有语料的实测分布定的。

#### ⚠️ 一个真实的坑：`score` 和 `confidence` 不是一回事

代码里每个检索结果同时带这两个数，注释专门警告过：

- **`score`** 是**在这一批结果内部**归一化的 —— 排第一的那条**恒等于 1.0**。
- **`confidence`** 是用**未归一化的原始分**算的 —— 可以跨不同提问比较。

**如果拿 `score` 当「有多大把握」用，那么任何提问都会被判成「命中」**，因为 top1 永远是 1.0。代码注释里直接点名了这个后果：

> 那会让「python 部署 nginx 报错」也判成 FAQ 命中。

#### 阈值 0.40 是怎么来的：实测标定，不是拍脑袋

我把代码里记录的标定值**自己跑了一遍**验证：

| 用户提问 | 我实测的置信度 | 结果 |
| --- | --- | --- |
| 毕业设计服务怎么收费 | **0.537** | ✅ 命中 FAQ |
| 可以开发票吗 | **0.522** | ✅ 命中 FAQ |
| 服务多少钱 | **0.502** | ✅ 命中 FAQ（认出了「多少钱」= 收费那条） |
| 交付要多久 | **0.425** | ✅ 命中 FAQ |
| — | — | **阈值 0.40 在这里** |
| 这个能便宜点不 | **0.389** | ❌ 不命中 → 最终转人工 |
| 怎么退款 | **0.322** | ❌ 不命中（确实没有退款 FAQ） |
| python 部署 nginx 报错 | **0.316** | ❌ 不命中 → 判为专业问题 |

（代码注释里最后一条记的是 0.306，我实测 0.316 —— 有细微漂移，但两者都远低于阈值，不影响结论。）

**⚠️ 注意表里有两个不同的「置信度」，别搞混**（我把「这个能便宜点不」端到端跑了一遍）：

```text
FAQ 检索置信度 0.389  → 没过 0.40，不算命中
        ↓
路由兜底置信度 0.30   → 三种都不像，按闲聊兜底但故意给低分
        ↓
0.30 < 0.35（LOW_CONFIDENCE）→ 转人工
        ↓
最终 source = "human"，escalated = True
回复：「这个问题我暂时答不好，已为你转接人工客服，请稍等。」
```

**第一个数是「检索有多像」，第二个数是「路由有多大把握」。** 两条线、两个阈值（0.40 与 0.35），各管一段。

顺便看这个例子有多妙：用户在**砍价**。这种事 AI 答不好也不该答（答「可以便宜」就成了承诺），系统识别出自己没把握，直接甩给人工 —— **这正是兜底机制存在的意义**。

**看这个表能看出两件事**：

1. **阈值的位置是有依据的** —— 它落在「真的命中」（0.425）和「差一点」（0.389）之间。
2. **但它也很脆** —— 0.425 和 0.389 只差 0.036。代码注释自己也承认：

> 语料变大后必须重新标定，否则这个数没有意义（TD-151）。

> **这是一个很重要的工程观念：有些数字不是「算出来的」，是「量出来的」。它们只在特定的数据分布下有效，换了数据必须重新量。** 把它们当常量写死，是这类系统日后出错的头号原因。

### 4.4 第二层 意图路由：一个「没做」的诚实决定

#### ROADMAP 要求的 BERT，代码里明确写了没做

原始需求是「训练或微调一个 BERT 多分类模型」。`app/tools/intent.py` 顶部的注释是这么写的：

> **这部分没有做，也不该假装做了。** 训练 BERT 需要：标注数据（三类各上千条，本项目一条都没有）、GPU 或至少数小时 CPU、以及几百 MB 的预训练权重下载。沙箱里三样都不具备，写出来的「模型」无法验证，只会是个不能跑的摆设。

**我认为这是整个项目里最值得学的一段注释。** 它做了三件事：

1. 直说没做（不含糊过去）
2. 说清楚为什么做不了（三个具体障碍，不是「没时间」）
3. 说清楚「假装做了」的后果（**无法验证的摆设**）

#### 那实际做了什么：接口 + 可替换实现

```python
class IntentRouter(Protocol):          # ← 接口：只规定「要有一个 classify 方法」
    def classify(self, text: str) -> IntentResult: ...

class RuleIntentRouter:                # ← 当前实现：纯规则，完全确定
    def classify(self, text: str) -> IntentResult: ...
```

**生活比喻**：定义好一个**插座标准**，现在插的是「规则」这个插头；将来有了 BERT，做一个符合同样标准的插头换上就行，**墙里的电线（业务代码）一根都不用动**。

这就是行业里说的**面向接口编程**。它的价值在这里体现得特别清楚：

> 将来训练出 BERT 后，写一个 `BertIntentRouter` 实现同一个接口即可，`app/tools/support.py` 与路由层一行都不用改。

#### 判定顺序为什么是「先查 FAQ」

```text
① FAQ 检索有把握吗？  有 → 直接返回（不调 AI）
② 命中技术词吗？      有 → 判为专业问题
③ 命中寒暄词吗？      有 → 判为闲聊
④ 都不像            → 按闲聊兜底，但给低置信度
```

**第 ① 步必须放最前面**，因为 FAQ 命中是三种结果里唯一「答案已在库里、可以秒回」的 —— **优先判它，能省掉一次 AI 调用（既花钱又慢）**。

第 ④ 步也有讲究：它给的是 **0.3** 的低置信度，**故意低于**兜底线 0.35，好让上层有机会转人工。

还有一个细节：命中技术词时，置信度是 `0.5 + 0.15 × 命中个数`，但**封顶 0.9**：

> 词表判定不该给出「绝对确定」。

> **这是个很成熟的习惯：确定性的东西才敢给 1.0，靠规则猜的就留一点余地。**

### 4.5 第三层 RAG：不让 AI 生产事实，只让它组织事实

**RAG** 的全称是「检索增强生成」，说人话就是：**先查资料，再让 AI 照着资料回答。**

**为什么非这样不可？** 因为让 AI「凭记忆」回答专业问题，它会**杜撰**。而且它杜撰的时候语气非常肯定，外行根本分不出来。

本项目的做法分三步：

```text
① 从 sys_article 表里检索最相关的 3 篇文章（RAG_TOP_K = 3）
② 每篇截前 600 字（RAG_SNIPPET_CHARS），塞进提示词
③ 提示词里明确要求：「只依据下面提供的材料作答，材料里没有的内容
   要明确说『资料中没有提到』，不要凭记忆补充」
```

然后把**引用的文章标题一起返回给前端展示** —— 用户能自己点进去核对。

**这个原则在代码注释里被明确总结过**：

> 这和 S4-01 让 LLM 只指认选择器、正文由 BeautifulSoup 提取是同一个原则：**不让模型生产事实，只让它组织已有的事实**。

> **这是当前用 AI 最重要的一条工程纪律。** 模型擅长「改写、归纳、组织」，不擅长「提供事实」。把这两件事分开，AI 就从「不可信的信源」变成「有用的编辑器」。

---

### 4.6 兜底：六种情况一律转人工

这一层是整套设计的安全网。代码里的原则是：

> 任何一层出问题都退到「转人工」，不抛异常给用户。

| 触发情况 | `reason` 里会写什么 |
| --- | --- |
| 用户明说要人工（命中「人工」「投诉」「举报」等 5 个词） | `用户明确要求人工（命中 […]）` |
| 空提问 | `空提问` |
| 路由置信度 < 0.35 | `置信度 0.30 < 0.35（未命中 FAQ、无技术词、无寒暄词…）` |
| 判为 FAQ 但检索已无命中 | `路由判为 FAQ 但检索已无命中` |
| **AI 服务挂了** | `闲聊应答失败：…` / `RAG 生成失败：…` |
| 知识库不可用 / 无相关内容 | 见下方 |

**注意第五条**：AI 接口挂了，用户**不该看到 500 错误页**，而应该看到「已为你转接人工客服」。

> **生活比喻：医院的应急预案。** 停电了不能把病人赶出去，得有备用方案。系统里叫**优雅降级**。

#### 一个值得单独讲的细节：「没有」和「坏了」必须区分开

```python
async def _retrieve_articles(...) -> list | None:
    ...
    except SQLAlchemyError:
        return None      # ← None：知识库**不可用**（表不存在、连不上）
    if not rows:
        return []        # ← 空列表：库能查，但**没有相关内容**
```

**为什么不能用同一个返回值？** 因为排错时这两件事的处理方式完全不同：

- `None` → 数据库或迁移出问题了，要**叫工程师**
- `[]` → 内容库太薄，要**叫运营去补文章**

**而且这里藏着一个真实的陷阱**，注释里写得很清楚：

> `sys_article` 是 S4-01 才加的表，用旧版 `full_init.sql` 建的库、或没跑过迁移的库上它压根不存在，直接查会抛异常变成 500。**注意两个测试套件都发现不了这个问题：fixture 里 `create_all` 总会把表建出来，只有真起服务连真库才会暴露。**

> **这是一条对所有写测试的人都适用的教训：测试环境的「自动准备」常常会掩盖真实环境的缺失。** 你的测试里表总是存在，因为测试自己建了它 —— 但这恰恰让你测不到「表不存在时会怎样」。
>
> 本项目为此专门写了一条测试 `test_missing_article_table_degrades_to_human_not_500`，**故意把表删掉**再跑。

### 4.7 性能：一个 560 毫秒的坑

ROADMAP 要求客服响应 **< 80 毫秒**。这里有个陷阱：中文分词用的 `jieba` 库，**第一次**分词要加载词典，代码注释记录的实测值是 **约 560 毫秒**。

如果不处理，**第一个用户**就会等半秒以上 —— 指标当场不达标。

解决办法只有一行，放在模块导入时：

```python
jieba.initialize()   # 预热词典，别把 ~560ms 算进第一次请求
```

**代价**是应用启动慢一点。这笔交易很划算：**启动慢一次，好过每个冷启动后的第一个用户都慢。**

**实测**（我本地跑的，1000 次检索）：

```text
1000 次检索总耗时 42.1 ms → 单次 0.0421 ms
1000 次检索总耗时 37.2 ms → 单次 0.0372 ms
```

单次 **0.04 毫秒**，对 80 毫秒的指标有约 **2000 倍**余量。

> 顺带说明：这个 80ms 指标是**能安全写成断言**的，因为余量极大。对比第 3 课讲的那个 CI 偶发失败 —— 那条断言的余量只有 1.6 倍，所以它必然抖。**判断一个延迟断言该不该写，看的是余量倍数，不是「它现在过了没有」。**

## 第 5 课：性能与稳定性 —— 那些「看起来没问题，其实会雪崩」的设计

### 5.1 先把两种问题分开：「慢」和「雪崩」完全不是一回事

| | 慢 | 雪崩 |
| --- | --- | --- |
| 表现 | 用户多等两秒 | 一个小故障变成全站瘫痪 |
| 严重性 | 烦人 | 致命 |
| 起因 | 算法不好、机器不够 | **往往是「看起来是好设计」的东西** |

**本课讲的主要是第二种。** 它最阴险的地方在于：**引入它的人当时是在做一个负责任的决定。**

---

### 5.2 生活比喻：医院不能因为化验室停电就把医生全赶走

假设一家医院规定：「**每 10 秒检查一次化验室有没有电，没电就把当班医生全部遣散重招。**」

某天化验室跳闸了。会发生什么？

```text
化验室停电
  → 检查失败 → 遣散全部医生
  → 医生重新入职需要时间，这段时间**一个病人都看不了**
  → 病人堆积，化验室恢复后也处理不过来
  → 全院瘫痪
```

**原本只是「化验室暂时不能用」，最后变成「整个医院停摆」。**

正确的做法是分两种检查：

- 「**医生还在岗吗？**」—— 这个不该看化验室。医生在，医院就还活着。
- 「**现在能正常接诊吗？**」—— 这个可以看化验室。不能接诊就**暂停挂号**，等恢复了再开，**但别把医生赶走**。

---

### 5.3 存活探针 vs 就绪探针：一字之差，后果相反

上面那个比喻，在服务器世界里就是两个网址。本项目两个都有（`app/routers/health.py`）：

| 端点 | 回答什么问题 | 查数据库吗 | 失败时运维系统会做什么 |
| --- | --- | --- | --- |
| `/healthz` **存活探针** | 「进程还活着吗？」 | **绝不查** | **重启这个实例** |
| `/readyz` **就绪探针** | 「现在能接流量吗？」 | 真的执行一次 `SELECT 1` | **把它从负载均衡摘掉**，等它恢复，不重启 |

代码注释把雪崩链条写得很清楚：

> 这里如果去查数据库，那么数据库一抖，编排器就会把**健康的**应用实例全部重启，把一次数据库故障放大成全站雪崩 —— 这是存活探针最经典的误用。

**对照一下 5.2 的比喻**：

- 存活探针 = 「医生还在岗吗」→ 不该看化验室
- 就绪探针 = 「能接诊吗」→ 可以看化验室，但处理方式是**暂停挂号**，不是赶走医生

> **这是一条通用的运维铁律：存活探针只检查「自己」，绝不检查「依赖」。**
>
> 因为存活探针失败的处置是**重启**，而重启对「依赖坏了」这种问题毫无帮助 —— 它只会让情况更糟。

#### 一个容易忽略的细节：探针自己不能变成故障源

```python
try:
    await db.execute(text("SELECT 1"))
except Exception as e:
    return Response(..., status_code=503)   # 吞掉异常，返回 503
```

注释说明了为什么必须 `try`：

> 探针必须吞掉异常，否则探针自己会变成 500。

**503 是「我暂时不能服务」（预期内的状态），500 是「我出错了」（意外）。** 数据库连不上是前者，必须如实报 503，不能让探针自己抛异常变成后者 —— 否则监控会把它误报成程序 bug。

---

### 5.4 异步省的是什么：托盘只有 15 个

第 1 课讲过异步是「一个服务员照看十桌」。这一课讲它的另一半：**资源是有限的。**

本项目数据库连接池的实测配置：

```text
常驻 5 个连接 + 最多临时多开 10 个 = 同时最多 15 个
```

**生活比喻：餐厅只有 15 个托盘。**

- **同步写法**：一个客人从点菜到吃完，**全程占着一个托盘**。15 个客人坐下，第 16 个就只能站在门口等 —— 哪怕前 15 个都在低头玩手机（等数据库回话），托盘也拿不回来。
- **异步写法**：客人点完菜（发出数据库请求）就**把托盘还回去**，菜好了再拿一个新托盘上菜。同样 15 个托盘能同时服务几百桌。

**所以异步和有限连接池是搭配使用的**：异步负责「不空等」，连接池负责「不把数据库压垮」。

> **如果不限制连接数会怎样？** 每个请求都新建一条数据库连接。数据库的连接是有成本的（内存、文件句柄），几百条同时涌过去，**数据库会先于应用挂掉**。
>
> 这就是为什么「无限制」不是「更强大」，而是「更脆弱」。

### 5.5 重活必须移出事件循环（第 1 课的深化）

第 1 课讲过：Python 的 **GIL** 让「同一时刻只有一个线程执行 Python 代码」，所以几百毫秒的纯计算必须丢到**另一个进程**里，线程池不够。

这里要补一个**更重要的方法论教训**，它记在 `app/routers/tools.py` 的注释里：

> **注意「并发 p95 更快」不是选进程池的依据** —— 本机 2 核实测线程池 58~106ms、进程池 60~77ms，**分布完全重叠**，延迟量不出差别（TD-183/186）。

**什么意思？** 当初有人试图用「测一下哪个更快」来决定用线程池还是进程池。结果是：

| 实现 | 并发时其他请求的 p95 延迟 |
| --- | --- |
| 线程池 | 58 ~ 106 ms |
| 进程池 | 60 ~ 77 ms |

**两个区间大面积重叠。** 也就是说，测出来的「谁快」完全取决于当时机器的状态 —— 今天测线程池快，明天测进程池快。**用这种数据做决策，等于掷骰子。**

**真正的依据换成了确定性判据**：直接查这段重活**跑在哪个进程里**（第 1 课 1.4 ②、以及 TD-193）。

> **这是一条很有价值的工程经验：当两组数据的分布重叠时，「谁的平均值更高」不是证据。要么加大差异，要么换一个不依赖测量的判据。**

### 5.6 限流：一个容易被忽略的安全陷阱

#### 为什么要限流

因为 `/tools/*` 这些端点是**刻意不设登录**的（要 SEO 收录、要游客能直接用）。于是任何人都能无限调用，而其中：

- DDL 解析和 Word 导出**吃 CPU**
- `/tools/mermaid` 每次调用**直接花钱**（要调 AI）
- `/auth/login` 不限流就能被**在线爆破密码**

实测配置（滑动窗口，窗口 60 秒）：

| 档位 | 每 60 秒最多 | 为什么是这个数 |
| --- | --- | --- |
| 工具类 | **30 次** | 正常人画图用不了这么多 |
| AI 类（客服、Mermaid） | **10 次** | 每次调用都花钱，管得更严 |
| 认证类（注册、登录、改密码） | **10 次** | 防爆破 |

#### 为什么用「内存计数」而不是 Redis

代码注释的理由很直接：

> 本项目是单进程部署，为一个限流引入 Redis 属于过度设计。

**代价也如实记着**（TD-141）：

> 多进程 / 多实例部署时每个进程各算各的，实际配额会变成 N 倍。

> **这是很成熟的写法：做了取舍，就把代价和「什么时候该回头改」一起写下来。** 不写代价的取舍，半年后没人记得它是取舍，只当它是设计。

#### ⚠️ 安全陷阱：绝不能无条件相信 `X-Forwarded-For`

服务器看到的「客户端 IP」有两种来源：

1. **网络连接的对端地址** —— 伪造不了。
2. **请求头 `X-Forwarded-For`（简称 XFF）** —— 这是**客户端自己填的一行字**，随便写。

正常情况下，网站部署在反向代理（如 Nginx）后面，代理会把真实 IP 写进 XFF，应用读它是合理的。

**但如果无条件信任它：**

> 每次换一个 XFF 就是无限配额。

攻击者只要在每个请求里编一个不同的假 IP，限流就形同虚设 —— **等于把限流的控制权交给了攻击者**。

本项目的做法：

```python
def client_key(request):
    if settings.TRUST_PROXY_HEADERS:      # 默认 False
        ... 读 XFF ...
    return request.client.host            # 默认走这条：socket 对端地址
```

**默认关闭**，只有明确部署在**可信**反向代理之后才打开。

> **通用原则：凡是客户端能控制的数据，都不能直接当作安全决策的依据。** 这条原则在第 2 课（凭证内容可读）、第 3 课（回调金额校验）都出现过。

#### 一个实现细节里的坑

限流器要定期清理不再活跃的 IP，否则内存会随不同 IP 无限增长。代码注释警告：

> 不能只删空 deque —— `allow` 弹出旧命中后紧接着就会 append，deque 在实践中永远非空，那样删等于什么都没删。要按「最后一次命中的时间」判断。

**这种 bug 特别阴险**：代码看起来完全合理，测试也能过，只有长期运行、内存慢慢涨上去才会暴露。

### 5.7 性能测试怎么写才不抖（本课方法论总结）

前面几课零散提到过一些性能测试的坑，这里收成一张表。

#### 三种「能用」的判据

| 判据 | 例子 | 为什么稳 |
| --- | --- | --- |
| **比值** | 「有干扰的延迟 / 无干扰的延迟」 | 机器慢则两边一起慢，比值不变 |
| **增长阶** | 规模 ×4，耗时应 ×4 | 抓的是算法复杂度退化，与机器快慢无关 |
| **确定性位置** | 这段代码跑在哪个线程/进程 | 根本不测量时间 |

#### 一种「不能用」的判据：绝对延迟

**判断标准不是「它现在过了没有」，而是余量倍数。**

| 断言 | 正确实现的实测 | 阈值 | 余量 | 结论 |
| --- | --- | --- | --- | --- |
| FAQ 检索 < 80 ms | **约 0.02~0.04 ms** | 80 ms | **上千倍** | ✅ 可以写 |
| 事件循环停顿 < 20 ms | 本机 10.4 ms，**CI 实测 74.7 ms** | 20 ms | **1.6 倍**（本机） | ❌ 必然抖 |

第一行我故意写成**区间而不是单个数**：同一台机器重测会在 0.021~0.042 ms 之间漂，写死一个值下次就对不上。但这不影响结论 —— 不管取哪个，余量都是**三个数量级**，断言永远不会因为机器忙而误报。第二行的 CI 数字不是本机测的，而是**某次真实 CI run 的记录**（TD-192，`assert 0.0747 < 0.02`），它属于历史事实，可查不可复现 —— 这类数字要标明来源。

第二条就是第 3 课之前那个 CI 偶发失败的真身（TD-192/193）。它最终被换成了「查跑在哪个进程」。

> **所以：写延迟断言之前，先算余量。余量小于一个数量级的延迟断言，迟早会变成随机红灯 —— 而随机红灯比没有测试更糟，因为它会训练所有人「看到红灯就重跑」，真正的故障也就被一起忽略了。**

#### 增长阶测试长什么样

```python
small, big = best_of(20), best_of(80)   # 规模 ×4
growth = big / small
assert growth < 8.0                      # 线性应≈4，平方是 16，8 卡在中间
```

我本机实测（同一份代码连续跑多轮，每轮取 `rounds` 次的最小值）：**20→80 表稳定在 ×4.0~4.1**。

**干净的线性。** 如果哪天有人把解析器改成对每张表都全表扫一遍，这里会变成 ×16，测试当场红。

注意我**没有**在这里写「20 表 12.68 ms」这样的绝对值 —— 下一小节会讲为什么。

#### 一个元教训：文档里的实测数字会腐烂

写这一课时我在上面那条测试里连踩了两次同一个坑，两次都值得记下来。

**第一次踩：测试注释和代码不符。** 注释写「规模翻倍…实测环比 2.01x / 2.00x / 1.98x」，但代码是 `best_of(20), best_of(80)` —— **4 倍规模**，线性应该是 ×4 而不是 ×2。我复测确认 `20→40` 确实是 ×2.09（对上注释），`20→80` 是 ×4.04（对上代码）。也就是说：有人把测试从 2 倍改成了 4 倍，**但忘了更新注释里记录的实测数字**。断言一直是对的（`< 8.0` 对 4 倍规模依然能抓住平方退化），但**证据过期了**，会误导后来的人。

**第二次踩：我自己又写了一遍会腐烂的数字。** 我改注释时，把当时的绝对耗时（`20 表 12.68 ms → 80 表 50.97 ms`）当成"实测证据"记了进去。等要提交时我重跑了一遍同样的命令：

```text
rounds=3: 20=16.06ms 80=64.88ms x4.04 | 40=34.78ms 160=136.89ms x3.94
rounds=5: 20=15.59ms 80=63.84ms x4.10 | 40=33.11ms 160=116.66ms x3.52
```

**绝对毫秒全对不上** —— 同一台机器、同一份代码，20 表在 12~16 ms 之间漂，因为 CPU 在跑别的东西。而**比值稳定在 ×4.0~4.1**，因为它把机器快慢约掉了。

**结论**：注释里只能留**在这个环境下可复现**的东西。绝对耗时不可复现，就不要写；比值可复现，就写比值。这也正是那条断言用 `growth < 8.0` 而不是 `big < 60` 的原因 —— **测试本身早就做对了，是我写注释时没跟上**。

> **这就是为什么本笔记的每一条数字都附上复算方式。** 文档里的实测值不会自动更新，代码一改它就过期 —— 而**过期的数字比没有数字更危险**，因为它是「看起来很可信的错信息」。判据很简单：**这个数字在下一次运行时还成立吗？** 成立的（路由条数、表数、阈值、比值）才配写进来。

## 第 6 课：内容抓取 —— 让服务器去访问「别人给的网址」

### 6.1 一句话说清这个功能

管理员在后台填一个网址，服务器去把那个网页抓回来，**自动挑出标题、作者、发布时间、正文**，存进数据库，变成站内的一篇文章。

用途是**内容冷启动**：一个新站没文章，用户进来看到空空荡荡就走了。所以先抓一批毕设相关的技术文章把架子撑起来。

听起来是个很普通的功能。**但它是整个项目里最危险的一个**，危险到我在 `app/routers/admin.py` 的第一行注释就写了警告。原因下一节讲。

---

### 6.2 生活比喻：一个有全公司门禁卡的秘书

想象公司里有个**秘书**（= 我们的服务器），他有一张**能开所有门的门禁卡**：机房、财务室、老板办公室，全都能进。

你（= 外部用户）只能待在**接待区**，一张门都开不了。

现在你填了一张单子：「麻烦去 **XX 房间** 帮我取一份文件。」秘书看了一眼就去了。

**问题来了**：如果你在单子上写的是「财务室第三个柜子」，秘书照样会去 —— 因为**他有钥匙，而他没有检查你要他去的是哪儿**。他把文件取回来递给你，你就拿到了本来永远拿不到的东西。

**这就是 SSRF（服务端请求伪造）的全部原理。** 危险的从来不是「用户能填网址」，而是**服务器所处的网络位置比用户能到达的位置深得多**：

| 用户自己能不能访问 | 服务器能不能访问 | 所以 |
| --- | --- | --- |
| 公网网站 | 能 | 没问题，这是功能本身 |
| `127.0.0.1`（服务器自己） | 能 | ⚠️ 用户能摸到服务器的内部管理端口 |
| `10.x` / `192.168.x`（内网） | 能 | ⚠️ 用户能扫内网、读数据库管理台 |
| `169.254.169.254` | 能 | 🔴 **能读走云主机的身份凭证** |

> **`169.254.169.254` 是什么？** 云厂商（阿里云、腾讯云、AWS）都约定：机器内部访问这个特殊地址，能拿到「这台机器是谁」的**临时身份凭证**。拿到它，攻击者就能直接操作你的云账号 —— 建机器、删数据库、翻对象存储。**这是 SSRF 最值钱的战利品**，所以它是每一个 SSRF 教程的第一个例子。
>
> 这个地址属于「链路本地地址」段，**不在公网路由表里**，只有机器自己能访问 —— 这恰恰是它危险的原因：外部打不进来，但**我们的服务器会替攻击者去打**。

**其余几个比喻：**

| 生活场景 | 代码里对应什么 |
| --- | --- |
| 人家院门口的「谢绝推销」牌子 | **robots.txt** |
| 牌子上写「请间隔 5 分钟再来」 | **`Crawl-delay`** |
| 去之前先看牌子，别硬闯 | **`politeness.check_allowed()`** |
| 同一个院子不用每次去都重读一遍牌子 | **robots 结果缓存 1 小时** |
| 把一本书的**目录和每页标题**抄给专家，而不是把整本书搬过去 | **DOM 骨架 `to_skeleton()`** |
| 专家在目录上画圈：「标题在第 3 项、正文在第 7 项」，然后**我们自己**按圈去取原文 | **LLM 指认选择器 + BeautifulSoup 提取** |
| 有些网页是「一张空白纸 + 一台自动写字机」，光看纸是空的，得把写字机跑一遍 | **SPA 站点 → 无头浏览器渲染（TD-191）** |

### 6.3 一次抓取在电脑里走的完整路径

```text
管理员 POST /admin/articles/ingest  {"url": "...", "dynamic": false}
        │
        ├─① require_admin          没有管理员令牌 → 401（第 2 课）
        ├─② rate_limit("ingest")   挂在 LLM 档限流下（第 5 课）：这端点会烧钱
        │
        ▼
   ┌────────────────── 抓取阶段 ──────────────────┐
   │ ③ assert_public_url(url)   ← SSRF 闸门        │
   │      · 只许 http/https                        │
   │      · 域名解析出的【每一个】IP 都必须是公网   │
   │ ④ politeness.check_allowed() ← robots.txt     │
   │      · 缓存 1h，同域只拉一次                   │
   │      · 不许抓 → RobotsDisallowed              │
   │ ⑤ 全局并发闸（最多 4 个在飞）                  │
   │ ⑥ throttle()  按域排队，尊重 Crawl-delay       │
   └───────────────────────────────────────────────┘
        │
        ├─ dynamic=false → httpx 直接抓 HTML
        └─ dynamic=true  → 启动无头浏览器渲染后再取 HTML
        │
        ▼
   ┌────────────────── 解析阶段 ──────────────────┐
   │ ⑦ to_skeleton(html)   压成 DOM 骨架（≤400 行） │
   │ ⑧ LLM 在骨架上指认 CSS 选择器                  │
   │ ⑨ BeautifulSoup 按选择器提取【真实字节】       │
   │ ⑩ title / content 为空 → ExtractError         │
   └───────────────────────────────────────────────┘
        │
        ▼
   ⑪ save_article()  同一 URL 已存在则【更新】而非新增
```

**注意 ③④⑤⑥ 全部在启动浏览器之前**。这个顺序是本课最重要的设计决定，6.7 会讲为什么。

### 6.4 SSRF 闸门：`assert_public_url`

代码只有二十来行，但每一行都在挡一种攻击：

```python
async def assert_public_url(url: str) -> None:
    parsed = urlparse(url)
    if parsed.scheme not in ("http", "https"):        # 挡 file:// ftp:// gopher://
        raise CrawlError(...)
    host = parsed.hostname
    if not host:
        raise CrawlError("URL 里没有主机名")
    port = parsed.port or (443 if parsed.scheme == "https" else 80)
    infos = await asyncio.to_thread(socket.getaddrinfo, host, port)   # 真的去解析域名
    for info in infos:                                 # ← 注意是 for，不是取第一个
        ip = ipaddress.ip_address(info[4][0])
        if not ip.is_global:                           # ← 一个判断覆盖五大类
            raise CrawlError(f"目标不是公网地址：{host} -> {ip}")
```

**三个设计要点：**

**① `is_global` 一个属性覆盖五大类地址。** Python 标准库的 `ipaddress` 已经知道什么是私网、环回、链路本地、组播、保留段。自己写 `if ip.startswith("10.")` 这种字符串判断必然漏 —— IPv6、`172.16/12` 的边界、八进制 IP 表示法都是坑。

**② 必须逐个检查解析结果。** 一个域名可以解析出**多个** IP。攻击者可以注册一个域名，解析结果里既有公网 IP 也有 `127.0.0.1`（这叫 **DNS rebinding** 的雏形）。只看第一个就是漏的。

**③ 校验发生在「解析之后、请求之前」。** 只校验用户填的字符串是没用的 —— 用户填 `http://innocent.com`，而 `innocent.com` 解析到 `10.0.0.5`，照样进内网。

**我实测了 10 个地址（本机直接调 `assert_public_url`）：**

| 输入 | 类型 | 结果 |
| --- | --- | --- |
| `http://169.254.169.254/latest/meta-data/` | 云厂商元数据 | 🛡️ 拦截 |
| `http://127.0.0.1:8000/admin` | 本机服务 | 🛡️ 拦截 |
| `http://10.0.0.5/internal` | 私网 10/8 | 🛡️ 拦截 |
| `http://192.168.1.1/router` | 私网 192.168/16 | 🛡️ 拦截 |
| `http://172.16.0.9/x` | 私网 172.16/12 | 🛡️ 拦截 |
| `http://[::1]/x` | IPv6 环回 | 🛡️ 拦截 |
| `file:///etc/passwd` | 换协议读本地文件 | 🛡️ 拦截（只支持 http/https） |
| `ftp://example.com/x` | 非 http 协议 | 🛡️ 拦截 |
| `http://example.com/a` | 正常公网域名 | ✅ 放行 |
| `http://8.8.8.8/` | 公网字面量 IP | ✅ 放行 |

**8 拦 2 放，全部符合预期。**

> **测试里的向量比我这里列的更全。** `tests/test_crawler.py::test_fetch_rejects_non_public_targets` 参数化了 **13 个**非公网输入，除了上表那些还包括 `gopher://`、没写协议的 `93.184.216.34/article`、`http://localhost:8000/`、`http://0.0.0.0/`、以及空主机名 `http://`。跑 `python -m pytest tests/test_crawler.py -q -k public` 可复算：**14 passed, 14 deselected**（14 = 13 个拒 + 1 个放；deselected 是该文件其余 14 条）。
>
> **注意 `localhost` 和 `0.0.0.0` 也在名单里** —— 它们不是「私网段」，靠字符串前缀判断必然漏掉，而 `is_global` 能一次认出来。这就是上面说的「别自己写 IP 判断」的具体含义。

> **这个闸门必须在两条抓取路径上都装。** `httpx` 路径装在 `crawler._request()`；无头浏览器路径装在 `browser.render()` 的第一步。少装后者，`dynamic=true` 就等于开了一个能直达 `169.254.169.254` 的口子 —— **浏览器不会替你做这个判断，它只会老老实实去访问你给的地址。**

### 6.5 爬虫礼仪：robots.txt（TD-133）

`robots.txt` 是网站根目录下的一个纯文本文件，写的是「哪些路径不希望被抓」。它是**君子协定，不是技术强制** —— 谁都可以无视它。但无视它的后果很实在：**被封 IP**，而且确实有合规风险。

**为什么 robots 和限速必须一起做**（写在 `politeness.py` 模块注释里）：

> 只加 robots 而不加限速，等于「打了招呼然后使劲刷」；只限速不读 robots，等于「慢慢刷人家明确说了不让抓的东西」。

#### 五档状态码判定

拿不到 robots.txt 时该怎么办？这是最容易做错的地方。项目按业界通行约定分五档：

| robots.txt 返回 | 判定 | 为什么 |
| --- | --- | --- |
| **200** | 按内容判定 | 正常情况，交给 `urllib.robotparser` 解析 |
| **404 / 410** | **放行** | 没有 robots 文件是**绝大多数站点的常态**，不是拒绝 |
| **401 / 403** | **全站拒抓** | 站方用鉴权把 robots 挡起来，意图很明确 |
| **5xx** | **本次拒抓** | 规则**不可知** —— 宁可漏抓一篇，不在规则未知时硬闯 |
| 超时 / 连接失败 | **本次拒抓** | 同上 |

**最后两档是最保守的选择**，代价是目标站抽风时会漏抓。取舍理由写在注释里：**对一个内容冷启动爬虫来说，漏抓可以重跑，被封 IP 不行。**

**我逐档实测了真实代码的行为**（用假 `fetch_text` 喂各种状态码）：

```text
HTTP 200  规则未命中该路径        → 放行
HTTP 200  Disallow: / 命中        → 拒抓
HTTP 404  没有 robots 文件        → 放行
HTTP 410  已永久删除              → 放行
HTTP 401  鉴权挡住 robots         → 拒抓
HTTP 403  禁止访问 robots         → 拒抓
HTTP 500  目标站故障              → 拒抓
HTTP 503  服务不可用              → 拒抓
HTTP 302  重定向（规则未知）       → 拒抓
异常      连接失败/超时            → 拒抓
```

**10 条全部与注释一致。**

#### 缓存：同一批文章只读一次牌子

冷启动往往要抓同一个站的几十篇文章。如果每篇都先拉一次 robots.txt，**那本身就变成了对目标站的额外压力** —— 违背这个模块的初衷。所以结果按 `(scheme, netloc)` 缓存 1 小时（`ROBOTS_TTL = 3600.0`）。

实测：

```text
[缓存] 同域 5 个 URL → robots.txt 实际拉取 1 次  ['http://93.184.216.34/robots.txt']
[缓存] 2 个不同域    → robots.txt 实际拉取 2 次
```

#### 限速：按域排队，不是全局

`Crawl-delay` 是**每个站各自**的要求。A 站要 5 秒、B 站没要求 —— 用全局间隔会让抓 B 站时无谓地慢，抓 A 站时又不够礼貌。所以间隔按域算：优先听站方的 `Crawl-delay`，没写就用默认 `DEFAULT_MIN_INTERVAL = 2.0` 秒。

实测（站方声明 `Crawl-delay: 7` → 间隔取 7.0 s；未声明 → 取 2.0 s）。

**这里有个容易写错的并发细节。** `throttle()` 必须在**锁内**把「预定发出时刻」写回去：

```python
async with state.lock:
    now = time.monotonic()
    wait = state.last_request + interval - now
    state.last_request = now + max(wait, 0.0)   # ← 先记账，再睡
if wait > 0:
    await asyncio.sleep(wait)
```

如果不在锁内记账，5 个并发协程会**算出同一个 wait、然后同时醒来一起发出去** —— 限速就白做了。实测（`Crawl-delay=0.5s`，5 个协程同时抢同一域）：

```text
发出时刻 = ['0.00s', '0.50s', '1.00s', '1.50s', '2.00s']
```

**间隔精确 0.5 s，一个都没挤在一起。** 锁真的在起作用。

#### 一个递归陷阱

**robots.txt 自己的抓取必须过 SSRF 校验，但绝不能再过 `check_allowed`** —— 否则就变成「为了判断能不能抓 robots.txt 而去读 robots.txt」的无限递归。

所以 `crawler.py` 拆成两层：

| 函数 | 做什么 | 给谁用 |
| --- | --- | --- |
| `_request()` | 只做 SSRF 校验 + 发请求 | 抓 robots.txt 本身 |
| `fetch()` | `_request()` + robots 判定 + 限速 | 抓正文页面 |

**这种「为了做安全检查而触发的请求，自己不能再做同一个安全检查」的分层，在所有涉及策略文件的系统里都会出现**（防火墙规则、权限配置文件、CDN 回源规则）。

### 6.6 为什么不让 LLM 直接吐正文（TD-135）

抓回 HTML 之后，要从里面挑出标题和正文。最直觉的做法是把 HTML 丢给大模型说「把正文提取出来」。**项目刻意不这么做**，理由有三条：

1. **模型会改写原文。** 让它「提取」，它会顺手润色、删节，甚至杜撰。而内容冷启动要的恰恰是**原文字节**。
2. **每次结果都不一样，没法写回归测试。** 今天测过了，明天同样的输入可能给出不同输出。
3. **整页 HTML 太大。** 一篇博客的 HTML 动辄上百 KB，直接喂会撑爆 token 预算，而其中绝大部分是脚本、样式、导航噪声。

**所以分工是这样的：**

```text
      整页 HTML ──to_skeleton()──▶ DOM 骨架（只留标签名/id/class/截断文本）
                                        │
                                        ▼
                                 LLM 看骨架，只回答：
                                 {"title": "article.post h1",
                                  "content": ".entry-content", ...}
                                        │
                                        ▼
      整页 HTML ──BeautifulSoup.select_one(选择器)──▶ 页面上的【真实字节】
```

**LLM 只负责「指认在哪」，不负责「搬运内容」。** 于是两个好处同时成立：入库的是原文（可复现、可测），而目标网站改版后**代码一行不用改** —— 页面结构变了 → 骨架变了 → LLM 重新指认 → 提取逻辑照旧。这就是 ROADMAP 里 S4-01-4「自适应目标网站前端结构变更」的实现方式。

骨架长这样（缩进表示层级）：

```text
article.post.post--single#post-1234
  h1
    "文章标题"
  div.meta
    span.author
      "作者名"
```

#### 骨架的真正保证是「有界」，不是「压缩比」

`crawler.py` 里原本写着一句注释：「体积通常只有原 HTML 的**几十分之一**」。

**我实测后发现这句话站不住**，已经改掉了。实测（本机构造页面）：

| 页面形态 | 原始 HTML | 骨架 | 压缩比 |
| --- | --- | --- | --- |
| 文本密集（极简页面，30 段） | 5 150 字符 | 1 847 字符 | **1/2.8** |
| markup 密集（真实博客形态，30 段） | 8 760 字符 | 4 477 字符 | **1/2.0** |
| markup 密集 + 300 段（触发截断） | 53 371 字符 | 14 551 字符 | **1/3.7** |
| 病态页面（10 000 节点，每节点 500 字） | 2 658 916 字符 | 13 198 字符 | **1/201** |

**压缩比在 1/1.5 ~ 1/201 之间剧烈摆动** —— 完全取决于源页面「标记 vs 文本」的比例。文本密集的页面几乎压不动。

**但真正重要的不变量是**：不管输入多大，骨架**恒定封顶**在 `MAX_NODES = 400` 行、每个文本节点截断到 `MAX_TEXT = 80` 字符。上面那个 2.66 MB 的输入，骨架是 **13 198 字符 / 恰好 400 行 / 最长一行 86 字符**（缩进 + 引号 + 80 截断）。

> **这才是 token 预算可控的真正原因 —— 是「输出有上界」，不是「压缩率高」。** 我把这条注释改了，因为拿一个会摆动的比值当设计依据，迟早会误导后来的人。（这是第 5 课 5.7 那条教训的又一次现身：**写在注释里的数字也是会腐烂的**。）

另外，`to_skeleton` 会先丢掉 11 类标签：`script / style / noscript / template / svg / iframe / nav / footer / header / form / aside` —— 它们对「识别文章结构」没有帮助，既减体积也减噪声。

### 6.7 动态页面与无头浏览器（TD-191）

有些网站是 **SPA（单页应用）**：服务器返回的 HTML 几乎是空的，正文由浏览器执行 JavaScript 之后才「长」出来。`httpx` 不执行 JS，所以只能拿到一张白纸。

**解决办法是真开一个浏览器**，让它把 JS 跑完，再把渲染后的 DOM 取出来。「无头」就是**没有窗口**的浏览器 —— 该干的活一样干，只是不显示。

#### 顺序是本模块可测的关键

`browser.render()` 的执行顺序：

```text
① assert_public_url(url)      ← SSRF，不碰浏览器
② politeness.check_allowed()  ← robots，不碰浏览器
③ 并发闸 + throttle()          ← 限速，不碰浏览器
④ _goto(url)                  ← 到这里才启动浏览器
```

**为什么这个顺序值得专门讲？** 因为 ①②③ 不需要浏览器就能真跑真测。**本项目所在的沙箱环境下载不到浏览器二进制**（`cdn.playwright.dev` 与 `playwright.azureedge.net` 实测均 HTTP=000），如果把安全检查放在浏览器之后，**这些安全测试在沙箱里一条都跑不了**。把它们提到前面，安全逻辑就有了真实的测试覆盖，只有最后一步 `_goto()` 依赖浏览器。

**这是「为了让测试能跑而调整代码顺序」的一个正面例子** —— 不是为了测试而改设计，而是**好的分层顺序恰好也让测试可行**。

#### 顺手记一条实测结论：不需要单独装 Node.js

Python 版 Playwright 的 wheel（47 MB）里**自带** `playwright/driver/node`（123.7 MB，权限 `100755`），`_impl/_driver.py` 用
`os.getenv("PLAYWRIGHT_NODEJS_PATH", str(driver_path / "node"))` 默认就调它。**在空 PATH 下（`env -i`）实测能独立运行，版本 v24.18.1。** 所以 `pip install playwright` 之后不需要另外安装 Node.js。

但**浏览器二进制不在 wheel 里**，要另外 `playwright install chromium`（约 150 MB）。因此项目**没把 playwright 放进 `requirements.txt`** —— 绝大多数目标站 `httpx` 就够了。没装时端点返回 **503 并直接给出安装命令**，而不是在启动时炸掉整个应用。

### 6.8 错误映射：五种异常对应五种责任方

抓取会失败，而且失败的原因**责任方各不相同**。项目把它们映射成不同的 HTTP 状态码 —— 这不是形式主义，**状态码是在告诉调用方「该不该重试、该找谁」**：

| 状态码 | 什么情况 | 责任方 | 调用方该怎么做 |
| --- | --- | --- | --- |
| **400** | URL 抓不了：非 http/https、内网地址、DNS 失败、目标非 200、页面过大、robots 不允许 | **调用方**给的地址有问题 | 换个 URL，别重试 |
| **422** | 抓到了但提不出正文（选择器匹配不到、必需字段为空） | 页面结构不适合 | 换 URL 或改提示词 |
| **502** | 上游大模型不可用 | **第三方**挂了 | 稍后重试，但别猛打本站 |
| **503** | `dynamic=true` 但服务端没装 playwright / 没下浏览器 | **本站**能力缺失 | 用 `dynamic=false`，或联系运维 |
| **500** | 以上都不是 | 本站代码有 bug | 报警 |

**注意 400 和 503 的区分**：「你给的 URL 不行」和「我这边做不到」是两件完全不同的事，混成一个 500 会让排障彻底失去方向。

#### 一个真实的死分支陷阱

`admin.py` 的 docstring 里专门记了一条：502 这一档**不能**写成 `except LLMError`。原因是 `extract.identify_selectors` 会把 `LLMError` 包成 `ExtractError` 再抛：

```python
try:
    reply = await llm.chat(SYSTEM_PROMPT, skeleton)
except LLMError as e:
    raise ExtractError(str(e)) from e     # ← 换了类型
```

**我实测确认了这个链条：**

```text
identify_selectors 实际抛出的类型 : ExtractError
是不是 LLMError?                  False
__cause__ 的类型                  : LLMError
→ 所以 `except LLMError` 在这条路径上永不可达（死分支）
```

写成 `except LLMError` 的话，「未配置 `LLM_API_KEY`」会被报成「内容提取失败」（422）—— **诊断信息和状态码都是错的**。正确写法是顺着 `__cause__` 认回去：

```python
except ExtractError as e:
    if isinstance(e.__cause__, LLMError):
        raise HTTPException(502, ...)
    raise HTTPException(422, ...)
```

> **通用教训：当一个函数会把异常「换包装」再抛，上游所有 `except 原类型` 都成了死代码。** 而死分支的危险在于**它永远不报错** —— 它只是安静地把错误分类搞错，直到某天线上排障时你才发现日志说的和实际发生的不是一回事。（第 4 课也踩过一次同类问题。）

### 6.10 行业里管这叫什么

| 本文说法 | 行业标准术语 |
| --- | --- |
| 挡内网/环回/元数据地址 | **SSRF 防护**（OWASP Top 10 2021 的 **A10: Server-Side Request Forgery**，独立成项就是从这一版开始的） |
| `169.254.169.254` | **Cloud Metadata Service / IMDS**（AWS 的 IMDSv2 就是为缓解这类攻击而设计的，要求带 token） |
| 域名解析出多个 IP，逐个检查 | 防 **DNS rebinding** |
| 遵守 robots.txt | **Robots Exclusion Protocol**（RFC 9309，2022 年才正式成为 RFC） |
| `Crawl-delay` / 按域限速 | **Politeness policy / crawl rate limiting** |
| 只留结构的 HTML 摘要 | **DOM skeleton / content extraction boilerplate removal**（同类工具：Readability、trafilatura） |
| 模型只指认位置不搬运内容 | **LLM-as-locator**，反义是 **LLM-as-extractor**（后者不可复现，业界普遍认为不该用于要求原文的场景） |
| 无窗口浏览器 | **Headless browser**（Playwright / Puppeteer / Selenium） |
| 抓回来的页面数据结构统一 | 两条路径共用同一个 `Page` dataclass —— **统一的中间表示（IR）** |

## 第 7 课（收官）：工程实践 —— 怎么让「改坏了」当场被发现

### 7.1 这一课要回答一个问题

> **测试全绿了，代码就没问题吗？**

**没有。** 这一课讲的全部事情，都是为了缩小「测试说没问题」和「真的没问题」之间的那道缝。

前六课讲的是**功能怎么搭**。这一课讲的是**怎么知道它没坏** —— 而这件事比搭功能更难，因为「坏了」不会主动举手告诉你。

---

### 7.2 生活比喻：灭火器上的压力表

办公室墙上挂着灭火器，十年没人动过，看着崭新。**它还能用吗？**

看着新不代表能喷。里面的压力可能早就漏光了。

**这就是「测试全绿」的处境** —— 测试挂在那儿一直是绿的，但你**怎么知道它真的会在出事的时候变红**？

有两个办法：

| 做法 | 对应到软件里 |
| --- | --- |
| 看压力表指针在不在绿区 | 看测试跑过没有（**弱**：指针可能卡住了） |
| **真的按一次喷射把手** | **变异测试**：故意把代码改坏，看测试红不红 |

**变异测试（mutation testing）就是"真的喷一下"。** 逻辑很直接：

> 如果我把这行代码改坏了，测试**应该**变红。如果测试还是绿的 —— 说明**这行代码根本没人看守**。

再补两个比喻：

| 生活场景 | 代码里对应什么 |
| --- | --- |
| 安检门只对金属响；你带陶瓷刀过去它不响 —— **不响不代表你没带刀** | 测试通过不代表没有 bug，只代表**测试查的那几项**没问题 |
| 体检报告全部正常，但**没查的项目**照样可能有病 | 测试覆盖率之外的代码路径 |
| 每次改完自动去做一遍体检 | **CI（持续集成）** |
| 同一台仪器受温度影响，同一个人今天正常明天超标 | **CI 抖动（flaky test）** |
| 病历本：记的不只是"吃了什么药"，更是"为什么不用另一种药" | **`TECH_DECISIONS.md` 决策台账** |

### 7.3 我真的把代码改坏了：四个变异实测

写这一课时，我在本机**真的**把代码改了四处，每处改完跑测试，然后还原。结果如下：

| # | 改坏了什么 | 测试结果 | 变异体 |
| --- | --- | --- | --- |
| 1 | 删掉 `browser.render()` 里的 `assert_public_url(url)` | **2 failed**, 61 passed | ✅ 被杀 |
| 2 | 把 `assert_public_url` 的 `if not ip.is_global` 改成 `if False` | **19 failed**, 60 passed | ✅ 被杀 |
| 3 | 砍掉 `admin.py` 里 `if isinstance(e.__cause__, LLMError)` 这个 502 分支 | **2 failed**, 16 passed | ✅ 被杀 |
| 4 | 把 `MAX_BYTES` 从 `2_000_000` 改成 `20_000_000`（放大 10 倍） | **417 passed, 2 skipped —— 全绿** | 🔴 **存活** |

第 4 个就是重点。**全量测试一条不红，而单页内存预算被放大了 10 倍。**

（每次变异都用快照 + `diff -q` 确认还原，工作树最终干净 —— 变异测试最怕的是"改坏了忘了改回来"。）

### 7.4 两个「存活变异体」的故事

这两个例子都真实发生过，而且**都不是"忘了写测试"，是测试写了但守不住**。

#### 故事一：巧合性的防御

**把 `render()` 里的 SSRF 校验删掉，测试居然全过。** 为什么？

因为 `politeness.check_allowed()` 会去抓 robots.txt，而抓 robots.txt 走的是 `_request()`，**`_request()` 内部也做 SSRF 校验**。于是拦截"碰巧"还是发生了。

```text
render(url)
   ├─ assert_public_url(url)        ← 删掉这一行
   └─ politeness.check_allowed()
          └─ _request(robots_url)
                 └─ assert_public_url(robots_url)   ← 这里"顺手"也拦了一次
```

**这叫巧合性防御（incidental defense）**：安全是靠**别人顺便做的**，不是自己做的。危险在于它**随时会静默消失** —— 将来谁给 robots 加了缓存预热、或让某个域跳过 robots 检查，SSRF 防护就没了，而**测试一句话都不会说**。

**修法**：加一条测试，**把 robots 那一层整个换成空操作**，专门钉住 `render` 自己那一行：

```python
async def noop(*a, **k):
    return None

monkeypatch.setattr(politeness, "check_allowed", noop)   # ← 把"顺带帮忙"的那层拆掉
with pytest.raises(CrawlError):
    await render(url)
```

这条测试的名字就叫 `test_render_ssrf_does_not_depend_on_robots_layer`。**我这次重跑变异 1，它确实把变异体杀掉了**（2 failed）。

> **通用规律：要钉住某一层的校验，必须把其它层换成空操作再测。** 否则你测到的可能只是"别的地方恰好也拦了"。这类测试还得带一条守卫 —— 上面例子里的 `assert no_browser == []`，它在说「浏览器压根没被启动过」，少了它，测试可能因为别的原因通过。

#### 故事二：相对断言抓不住常量

变异 4（`MAX_BYTES` 放大 10 倍）为什么全绿？因为**两条相关测试都用相对值**：

```python
# tests/test_crawler.py —— 注入一个小值测「闸门存在」
await fetch(url, transport=..., max_bytes=1000)

# tests/test_dynamic_crawl.py —— 造一个刚好超限的页面
html = "x" * (MAX_BYTES + 1)      # ← MAX_BYTES 取任何值，这行都成立
```

第一条测的是**机制**（这个闸门会不会拦），第二条是**相对断言**（超过上限就报错）。**两条都对，但没有任何一条在乎上限具体是多少。**

于是「2MB」这个数就成了没人看守的策略值。它不是随便定的：这是**单页内存预算**，配合 `MAX_CONCURRENCY = 4` 决定抓取最坏情况占多少内存（4 × 2MB ≈ 8MB）。放大 10 倍就是 80MB，而 CI 一片绿。

**修法**：写第 7 课时补了一条 `test_max_bytes_budget_is_pinned_at_2mb`，直接钉住数值。**重跑变异 4 验证过：注入变异后 1 failed，还原后 28 passed。**

> **通用规律：相对断言抓不住常量本身的改动。** 机制用相对值测（快、稳），但**关键策略值必须用绝对值钉一条**。这类测试看着像"废话断言"，它的价值恰恰在于：**谁改了这个数，CI 会当场拦下来并要求他解释。**

### 7.5 「测试全绿 ≠ 没问题」的三种真实形态

前六课里各出现了一次，凑在一起看：

| 形态 | 项目里的例子 | 为什么全绿还是有问题 |
| --- | --- | --- |
| **巧合性防御** | `render` 的 SSRF 靠 robots 层顺带拦 | 防护是真的，但**不是它自己做的**，随时会静默消失 |
| **相对断言** | `MAX_BYTES + 1` | 机制有测试，**数值**没测试 |
| **死分支** | `except LLMError`（第 6 课 6.8） | 这段代码**永远执行不到**，测试当然不红 —— 但它把「大模型挂了」错报成「内容提取失败」 |

**共同点：三种都不是"漏了测试"，是"测试测错了对象"。** 这也是为什么只看覆盖率数字会骗人 —— 覆盖率会告诉你"这行执行过了"，但不会告诉你"这行改坏了会不会被发现"。

> **变异测试补的正是这个缺口。它问的不是「代码跑过了吗」，而是「改坏了会被发现吗」。**

### 7.6 CI：每次提交自动体检一遍

`.github/workflows/ci.yml` 每次 push 和每次 PR 都跑，**三个 job 并行**：

| job | 干什么 |
| --- | --- |
| **静态检查（ruff）** | 不跑代码，只查写法：未用变量、可疑比较、时区裸用、async 里的阻塞调用等 |
| **测试（SQLite 后端）** | 全量 565 条测试，用内存库，快 |
| **测试（真 PostgreSQL 16）** | 同一套测试跑真库，另起 service 容器；还会把建表脚本**连跑两遍**验证幂等 |

**为什么要跑两遍数据库？** SQLite 和真 PostgreSQL 的行为不一样（事务隔离、类型严格程度、`ALTER TABLE` 支持度）。只在 SQLite 上绿的测试，上了真库可能红 —— 项目早期就吃过这个亏（TD-80）。

**本机实测的历史统计（98 条已完成的 run）：**

```text
success:    87
failure:     7
cancelled:   4
按事件：pull_request 49 / push 49
```

> ⚠️ **同一个 commit 会有两条 run**（一条 push、一条 pull_request）。**只盯其中一条就宣布"CI 全绿"是错的** —— 我踩过这个坑。要两条都看，而且要 `gh run view <id> --json jobs` 逐个 job 看，不能只看 run 的总结论。

那 **7 条 failure** 是什么？逐条查过：

| run | commit | 性质 |
| --- | --- | --- |
| `33792680165` | `14b0910` | **唯一一条真失败**（TD-192，见下节） |
| `33811893816` / `33811898659` | `3cba5e6` | 故意金丝雀（push + PR） |
| `33812606305` / `33812612241` | `9614172` | 故意金丝雀 |
| `33813284327` / `33813287809` | `a48da43` | 故意金丝雀 |

**1 条真失败 + 6 条故意失败。** 故意失败的是干什么的？下一节。

### 7.7 那次真失败：一次误诊和它的修法（TD-192/193/194）

#### 误诊

CI 红了。查 `run 33792680165` 的三个 job：

```text
100772798091  测试（SQLite 后端）        success
100772798400  测试（真 PostgreSQL 16）   failure   ← 只有这条红
100772798409  静态检查（ruff）           success
```

失败的是 `tests/test_perf.py::test_event_loop_stays_responsive_during_big_ddl`，报错 `assert 0.0747 < 0.02`。

**第一反应很自然**：只有真 PostgreSQL 那个 job 红了，所以问题跟 PostgreSQL 有关。

**这个推论是错的。** 那条测试用的是**内存 SQLite**，跟 PostgreSQL 一点关系都没有。job 的名字告诉你"这个 job 配的是哪种数据库"，**但没告诉你"失败的这条测试用的是哪种数据库"** —— 这是个很容易上当的误导。

> **教训：看到 job 名字就归因，是排障里最常见的一类错误。要去看失败的那条测试自己用了什么。**

#### 真因

真正的失败原因是**调度抖动**。判据是拿同一份 CI 日志里的 warmup 请求耗时对比：

| 环境 | warmup 请求耗时 |
| --- | --- |
| 本机 | 35.7 ~ 45.3 ms |
| CI 那次 | 39.8 ms |

**CPU 速度是一样的** —— 所以不是"CI 机器慢"，而是**协程被调度器晾了一会儿**。共享 runner 上这种事必然发生。

而那条断言是 `assert 停顿 < 20 ms`，**余量只有 1.6 倍**（第 5 课 5.7 讲过：余量小于一个数量级的延迟断言迟早变成随机红灯）。

#### 修法：把「测时间」换成「测位置」

比值阈值也救不了 —— 本机比值 0.30，CI 那次 2.1，噪声比信号还大。所以 TD-193 直接**换掉判据**：不再问"停了多久"，改问"这段重活**跑在哪个线程/哪个进程**"。

现在 `tests/test_perf.py` 里的两条替代测试是：

- `test_parse_ddl_runs_off_the_event_loop_thread`
- `test_build_data_dictionary_runs_in_a_separate_process`

**这两条永远不会抖** —— 它们不测量时间，只检查位置。原来那条测试名现在已经不在文件里了。

> **这是第 5 课那条方法论的完整闭环：绝对延迟不可用 → 比值也不可用（噪声太大）→ 换成不依赖测量的确定性判据。**

#### 附带解决的一个障碍

排障时发现**沙箱里下载不到 CI 日志正文**。这次又实测确认了一遍：日志下载被重定向到
`productionresultssa18.blob.core.windows.net`，取内容直接 **EOF**；而同一时刻 `api.github.com` 返回 **200** —— 说明是出口被墙，不是权限问题。

所以 TD-194 的做法是：**失败时把 pytest 输出摘要发到 PR 评论上**（评论走 `api.github.com`，读得到）。workflow 里那两个 `if: failure() && github.event_name == 'pull_request'` 的步骤就是干这个的。

> ⚠️ **一条必须如实交代的现状**：这个通道在**建它的时候**验证过能用（那 6 条金丝雀 run 就是验证用的）。但**我这次去查，PR #3 上的评论是 0 条** —— 当时留下的金丝雀评论已经不在了，所以我**无法在本轮复现当时的评论正文**。workflow 里的步骤还在，前提（日志下载不通）也还在，但"评论可读"这件事**现在没有现场证据**。

### 7.8 一条血泪经验：`if: failure()` 的步骤必须故意失败一次

那 6 条金丝雀 run 不是浪费，它们暴露了一个**只有真失败才能发现的模板缺陷**：

GitHub Actions 里，`${{ job.name }}` 和 `${{ github.job }}` 在 `run:` 步骤里**都渲染成空字符串**（而同一个表达式里 `${{ github.sha }}` 是正常的）。也就是说，评论里本该显示 job 名的地方是一片空白。

**这种缺陷在正常通过的 run 上永远看不出来** —— 步骤被 `if: failure()` 跳过了，压根没执行。

**所以修法是把 job 名写死在每个 job 自己的脚本里**：

```yaml
- name: 失败时把 pytest 输出发到 PR 评论
  if: failure() && github.event_name == 'pull_request'
  run: |
    echo "### ❌ 测试（SQLite 后端） 失败"      # ← 写死，不用 ${{ job.name }}
```

> **通用规律：任何只在失败路径上执行的代码，都必须被故意触发一次才算验证过。** 这跟变异测试是同一条道理的两面 —— **没被触发过的分支，等于没有代码。**

### 7.9 `TECH_DECISIONS.md`：160 条编号取舍

这是本项目最值钱的一份文档，304 行。**本机实测统计：**

```text
唯一 TD 编号: 160 条   范围 TD-1 ~ TD-195   区间内缺号 35 个
已解决（划掉）: 20 条
未解决: 140 条
上线阻塞项中仍未解决的: TD-113（微信支付未真机联调）、TD-124（模拟支付通道）
```

**它记的不是"怎么做的"，而是"为什么不那么做"。** 每条都是四列：编号 / 当时的问题 / 权衡 / 残留风险。

**为什么这比"怎么做"值钱？** 因为代码本身已经说明了"怎么做" —— 你读代码就知道。但代码**说不出**：

- 当初还考虑过哪些方案，为什么否掉
- 这个选择**牺牲了什么**（残留风险那一列）
- 什么条件下应该重新考虑

**没有这份台账，下一个人看到"奇怪"的设计只会觉得"写得不好"，然后热心地改回那个已经被否决过的方案。**

几个真实例子：

| 编号 | 记的是什么 |
| --- | --- |
| TD-124 | 模拟支付通道**开着就等于免费发货** → 已列入上线阻塞项；缓解方式是 `ENV=production` 时启动自检直接拒绝启动 |
| TD-162 | 压测的 `t0` 必须在 `asyncio.gather` **之前**取 —— 第一版基准就写错了，一度得出「没有阻塞」的**错误结论** |
| TD-133 | robots 的 5xx 判定为什么选"保守不抓"：漏抓可重跑，被封 IP 不行 |

> **TD-162 那条尤其值得看：它记录的不是一个决定，而是一次「我们曾经被自己的测量骗了」。** 这种记录在任何代码注释里都留不住。

### 7.10 最后一条规矩：文档里的数字也会腐烂

这一课本身又演了一遍。我为了讲变异测试，**加了 1 条测试**（`test_max_bytes_budget_is_pinned_at_2mb`）。结果**全仓 13 处数字同时过期**：

**加 1 条测试，最终查出的过期处共 24 处测试条数，散落在 11 个文件里**（另有 4 处 TD 条数是早就过期的旧账：写着「111 条 / 8 条待处理」，当时实际 159 条 / 2 条阻塞；本节写作过程中又入账了 TD-195，故现为 160 条 —— **又一次当场演示**）。真库那个 419 是**重新起 PostgreSQL 实测的，不是"417+1"推算的** —— 推算数字正是要避免的那类错误。

#### 但我第一轮漏了一半，而且漏的方式值得单独记下来

改完那 13 处后，我跑了一条自查命令，它输出「✅ 文档中已无 417」。**这个结论是错的。** 命令长这样：

```bash
grep -rn "417 passed" --include="*.md" . | grep -v "\.venv"
```

那个 `grep -v "\.venv"` 本意是排除虚拟环境目录。但**我要找的每一行本身就含 `.venv/bin/python -m pytest -q`** —— 于是过滤器把目标行**全部**滤掉了，grep 返回空，我就以为干净了。

实际上还漏着 **11 处**，分布在 6 个文件：4 个 `.claude/skills/*/SKILL.md`、`AGENTS.md`、`HANDOVER.md`、`TECH_DECISIONS.md`。

> **教训：用来"证明没问题"的那条命令，本身也需要被验证。** 具体到这里有两条可操作的做法：
> 1. 排除目录用 `--exclude-dir=.venv`，**不要**用管道 `grep -v` —— 后者按**行内容**过滤，会误伤正文里提到该路径的行。
> 2. **先确认扫描命令能扫到已知存在的目标**：故意留一处不改，看命令报不报。报不出来就是命令坏了。
>
> 这和 7.3 的变异测试是同一条道理的第三次现身 —— **验证工具本身也要被验证。**

**这条已经写进约定**：`AGENTS.md` 的 ALWAYS 段与「做完」的定义第 7 条，以及 `finish-subitem` 技能的第 3 步，都要求新实现同步更新本笔记、并用 `--exclude-dir` 扫全仓数字。

但如果没有人改，它们就会安静地烂在那里，变成「看起来很可信的错信息」。

**所以本笔记从头到尾守一条判据：**

> **这个数字在下一次运行时还成立吗？**
> 成立的（路由条数、表数、阈值、比值、位置判据）才写进来，并附复算命令。
> 不成立的（绝对毫秒、某次 CI 的具体耗时）只标成「某次实测」，并说明来源。

### 7.12 行业里管这叫什么

| 本文说法 | 行业标准术语 |
| --- | --- |
| 故意把代码改坏看测试红不红 | **Mutation testing**（工具：`mutmut`、`cosmic-ray`、Java 的 PIT）；存活的叫 **survived mutant**，被杀的叫 **killed** |
| 改坏了没人发现 | **Equivalent mutant** 之外的 **survived mutant** —— 测试套件的漏洞指标 |
| 测试通过但其实没保护 | 覆盖率之外的 **测试有效性（test effectiveness）**；相关指标 **mutation score** |
| 每次提交自动跑测试 | **CI（Continuous Integration）** |
| 随机红绿 | **Flaky test**；业界共识是「必须修或删，不能靠重跑掩盖」 |
| 只在失败路径执行的代码要故意触发 | **Negative path testing / fault injection** |
| 记录为什么不这么做 | **ADR（Architecture Decision Record）**；`TECH_DECISIONS.md` 是一份带编号与残留风险列的 ADR 集 |
| 上线前必须处理的事项 | **Release blocker** |

### 7.13 术语白皮书

| 术语 | 大白话 |
| --- | --- |
| **变异测试** | 真的按一次灭火器把手，看它喷不喷 |
| **存活变异体** | 按了把手没喷 —— 说明这地方没人看守 |
| **巧合性防御** | 安全是靠别人顺便做的，随时会静默消失 |
| **相对断言** | 「超过上限就报错」—— 上限是多少它不管 |
| **死分支** | 永远执行不到的代码，不报错，只是安静地把事情搞错 |
| **CI** | 每次改完自动做一遍体检 |
| **flaky** | 同一份代码，今天绿明天红 |
| **金丝雀 run** | 故意让 CI 失败一次，用来验证"失败时会发生什么" |
| **ADR** | 病历本：记的是"为什么不用另一种药" |
| **release blocker** | 上线前必须处理、不是可选项的事 |

### 7.14 全系列收尾

七课走完，回头看这个项目真正值得学的不是某个功能，而是**四条一以贯之的做法**：

1. **每层校验自己站得住** —— 不靠别人顺带做（第 6 课 SSRF、第 2 课鉴权）
2. **判据要选不会抖的** —— 位置优于比值，比值优于绝对值（第 5、7 课）
3. **错误分类要对应责任方** —— 400/422/502/503 各说各的事（第 3、6 课）
4. **写下"为什么不那么做"** —— 代码说不出口的那一半（`TECH_DECISIONS.md`）

而这一课加的是第 5 条，也是最容易被跳过的一条：

> **5. 定期验证"你的测试还管用吗"** —— 因为测试会腐烂，而且**腐烂的方式是保持绿色**。

## 第 8 课：从「免费试用」到「付钱」—— 转化路径为什么比功能更难

> 对应 ROADMAP `S2-02-2`；取舍见 TD-55（已解决）、TD-203、TD-204。

### 8.1 大白话：这一课解决的不是"加个按钮"

做这一课之前先去数了一遍，结果比 ROADMAP 上写的严重得多：

| 后端接口 | 有吗 | 前端有入口吗 |
| --- | --- | --- |
| `POST /shop/orders`（下单） | ✅ | ❌ **零调用者** |
| `POST /auth/register`（注册） | ✅ | ❌ **没有任何页面能注册** |

也就是说：**收银台和开户窗口都建好了，但都没开门。** 用户从搜索进来免费用完工具，
页面到此为止 —— 没有登录入口、没有页脚、没有"了解更多"。他就算想买 ¥199 的服务，
也只能自己猜网址，或者翻 `/docs` 里的 Swagger 手敲接口。

库里唯一的账号是 `database init/full_init.sql:63-64` 预置的 `admin`。

**所以这一课的第一步不是设计话术，是把门开出来。**

### 8.2 比喻：试吃摊与锁在仓库里的收银台

现在的状态是「路口摆免费试吃摊，试吃的人很多，但收银台锁在仓库里，
而且没人告诉顾客仓库在哪，连个指路牌都没有」。

转化路径设计得再漂亮，顾客走不到收银台。所以顺序必须是：
**① 先修路**（`/shop` 页 + 顶栏入口 + 页脚）→ **② 再立牌**（在恰当位置提示）→
**③ 最后才谈话术优化**（那需要数据）。

顺带说一个反面教材：drawio 页原先一进来就是**常驻的用户名/密码输入框**。
那是把登录成本前置给了所有游客，包括只想画图不想存图的人 ——
而工具页的定位恰恰是"免费、无需注册"（TD-15、TD-54）。现在收敛成点"保存到云端"时才唤起浮层。

### 8.3 落到代码：三个必须知道的坑

**① 下载是一次性的，前端绝不能自动调。**

`app/routers/shop.py:218` 用 CAS 保证只有一个请求能拿到链接：

```python
won = await mark_downloaded(db, order)
...
if not won:
    raise HTTPException(403, "该订单已下载过：一次性下载，防止资源被转卖")
```

只要成功调用一次，这单就**永久**不能再下载。所以下单页轮询状态**必须**走只读的
`GET /shop/orders/{order_no}`，下载只能由用户主动点按钮触发。
拿 download 当状态查询 = 把用户的货烧掉，现象是"付了钱下载不了"，极难排查。
`tests/test_shop_page.py::test_status_polling_does_not_burn_the_one_time_download` 钉住这条。

**② 为什么必须新增一个只读的状态接口。**

微信 Native 支付的流程是：用户扫码付钱 → 微信回调 `POST /shop/pay/notify` → 订单变 `paid`。
**浏览器那边完全不知道这件事发生了**（回调是微信打到服务端的）。所以页面只能轮询。
这个接口刻意**不写库** —— 轮询每 3 秒一次，连"顺手关掉过期单"都不做，
过期只在 `create_order` 里关（那是用户主动重新下单时的一次性动作）。

**③ 共享脚本的位置与形态，都被一条安全不变式约束着。**

登录模块要全站共用，最省事的写法是塞进 `base.html` 的内联 `<script>`。但 `base.html`
也是 **OAuth 同意页**的父模板，而那页必须**一个脚本都没有**
（发放授权码的安全关键页，`tests/test_oauth_consent.py` 断言 `"<script" not in html`）。

两个约束叠加，结果是：

- 做成**外部文件** `app/frontend/auth.js`（构建产物 `app/static/js/auth.js`） —— 由 CSP 的 `script-src 'self'` 覆盖，
  连 `'unsafe-inline'` 都不需要（TD-163 的方向）
- `base.html` 加 `{% if auth_ui %}` 开关，同意页传 `auth_ui=False`，整套 UI 与脚本都不渲染
- 脚本必须放在 `<main>` **之前** —— 页面脚本在文档顺序上先执行，
  否则 `CodeMaxAuth is not defined`（这个 bug 是 node 真跑测试抓出来的）

二维码选 `segno`（纯 Python、零依赖、实测 **0.07 MB**）而不是 `qrcode[pil]`
（要拖 **Pillow 6.61 MB** 二进制），输出纯 `<path>` 内联 SVG，不受 CSP `img-src` 约束（TD-203）。

### 8.4 行业术语对照

| 本文做法 | 行业术语 |
| --- | --- |
| 免费工具完全不设墙 | **Product-Led Growth (PLG)** / freemium |
| 用户真需要更多时才要求登录 | **"Value first, ask later"** |
| 单页承载商品说明 + 下单 + 支付态 | **Landing page / Checkout funnel** |
| 页脚统一放商业入口 | **Global footer navigation** |
| 轮询订单状态 | **Polling**（进阶是 SSE / WebSocket） |
| 一次性下载链接 | **Single-use signed URL** |

**为什么埋点暂缓**（TD-203）：现有 CSP 的 `connect-src 'self'` 会直接拦掉任何往第三方域
发数据的统计脚本，放通属于安全策略变更；而且毕设场景没有真实流量，
埋点也读不出统计显著的结论 —— 那会变成"装了但没用"的配置。

## 附：本文数字的统计方式

所有数字都可以自己复算，不依赖任何人的记忆：

```bash
# 路由条数
python -c "import main; rs=[r for r in main.app.routes if getattr(r,'path','').startswith('/')]; print(len(rs))"

# 配置项条数
python -c "from app.config import settings; print(len(settings.model_fields))"

# 测试条数
python -m pytest -q

# 抓取那条线的测试条数（第 6 课 6.9：101 passed, 1 skipped）
python -m pytest tests/test_crawler.py tests/test_politeness.py tests/test_extract.py tests/test_admin_ingest.py tests/test_dynamic_crawl.py -q

# SSRF 闸门（第 6 课 6.4：13 个非公网向量全拦 + 1 个公网放行 = 14 passed）
python -m pytest tests/test_crawler.py -q -k public

# parse_ddl 的增长阶（第 5 课 5.7：比值稳定，绝对毫秒会漂）
# 本机实测输出：20=14.49ms 80=58.86ms x4.06
python -c "import timeit,sys; sys.path.insert(0,'tests'); from test_perf import make_ddl; from app.tools.sql_ddl import parse_ddl as p; g=lambda n: min(timeit.repeat(lambda: p(make_ddl(n)), number=1, repeat=3)); a,b=g(20),g(80); print(f'20={a*1000:.2f}ms 80={b*1000:.2f}ms x{b/a:.2f}')"
```

（最后这条会先打印几行 jieba 加载日志，看最后一行的 `x` 值就行。）

> 上面最后一条命令是**故意写得很丑**的单行版 —— 因为附录里的命令必须能直接粘进终端跑。想看清爽版就读 `tests/test_perf.py::test_parse_ddl_scales_linearly_not_quadratically`，它才是这条判据的真身；**文档里的复算命令只是它的投影，代码改了请以测试为准。**
