## 第 1 课：整体架构 —— 一个请求在电脑里走了什么路

### 1.1 这个项目到底在做什么生意

一句话：**这是一个「毕设服务平台」，靠免费工具引流、靠付费服务赚钱。**

它由两个平台拼成，共用一套账号：

| 平台 | 给用户什么 | 怎么赚钱 |
| --- | --- | --- |
| **免费工具平台** | 画 ER 图（数据库结构图）、画流程图、自然语言生成图 | 不赚钱，负责把人吸引进来 |
| **商业平台** | 导出数据字典 Word 文档等付费服务 | 微信支付下单 → 付款 → 下载 |

再加三块基础设施：**统一登录**（一次注册，两个平台通用）、**智能客服**（自动答疑，减少人工）、**内容抓取**（自动收集毕设相关文章充实站内内容）。

> **为什么不拆成两个独立网站？** 因为「引流」和「变现」必须共用同一个身份。用户在免费工具里画好了图，想导出 Word 时如果还要再注册一次，绝大多数人就走了。这就是代码里反复出现的 **SSO（单点登录）** 的商业理由。

### 1.3 一次请求的完整旅程

假设你在浏览器里点了「导出 Word」，接下来发生的事：

```
你的浏览器
   │  ① 发出请求 POST /tools/word-export
   ▼
┌─────────────────────────────────────────────────┐
│ ② 登记台（RequestLoggingMiddleware）             │
│    给这次请求发一个「快递单号」X-Request-ID       │
│    记下：谁、什么时候、花了多少毫秒               │
├─────────────────────────────────────────────────┤
│ ③ 安检（SecurityHeadersMiddleware）              │
│    在回执上贴安全标签，告诉浏览器哪些东西不许加载 │
├─────────────────────────────────────────────────┤
│ ④ 楼层指引（路由匹配 /tools/word-export）         │
│    → 交给 app/routers/tools.py 的 word_export()  │
├─────────────────────────────────────────────────┤
│ ⑤ 检查申请表（schemas.ErDiagramIn）               │
│    DDL 太长？格式不对？当场退回，不用惊动后厨     │
├─────────────────────────────────────────────────┤
│ ⑥ 限流闸门（rate_limit）                          │
│    这一分钟你已经来过太多次了？请先等等           │
├─────────────────────────────────────────────────┤
│ ⑦ 后场工坊                                        │
│    parse_ddl（解析建表语句）→ 丢到**线程**里      │
│    build_data_dictionary（生成文档）→ 丢到**进程**里│
├─────────────────────────────────────────────────┤
│ ⑧ 打包出餐（Response，带文件名与类型）            │
└─────────────────────────────────────────────────┘
   │
   ▼
浏览器收到 .docx 文件，同时回执上带着 X-Request-ID
```

**那个「快递单号」是干嘛的？** 将来你打电话报障说「我刚才导出失败了」，客服让你报出浏览器里那串 ID，工程师就能在成千上万行日志里**精确捞出你那一次请求**。没有它，线上排障只能靠时间戳猜 —— 这是 `app/middleware.py` 注释里写明的设计意图。

### 1.4 五个「为什么非要这样设计」

这一节是本笔记的重点。**只看「代码怎么写」学不到东西，看「不这样会出什么事」才行。**

#### ① 为什么用「异步」？—— 一个服务员照看十桌

**大白话**：普通写法（同步）是「服务员给 A 桌上完菜，站在旁边等 A 桌吃完，再去 B 桌」。异步是「给 A 桌下单后转身去招呼 B 桌，A 桌菜好了再回来」。

**为什么这个项目非用不可**：它大量时间在**等别人** —— 等数据库回话、等微信服务器回话、等 AI 接口回话。这些等待动辄几十上百毫秒，如果用同步写法，这段时间整个服务器就干等着，别的用户全部卡住。

**不这样会怎样**：10 个人同时用，第 10 个人要等前 9 个人全部办完。

#### ② 为什么「重活」要丢到另一个进程里？—— 收银员不能自己跑去炒菜

这是本项目最深的一个坑，代码里 `app/cpu_pool.py` 的注释记录了完整过程。

**大白话**：生成 Word 文档要**纯算**约 470~500 毫秒（本机实测）。这种「算」和「等」不一样 —— 它在抢 CPU。

Python 有一条规矩叫 **GIL（全局解释器锁）**：**同一时刻只允许一个线程执行 Python 代码**。

- 把重活丢到**线程**里：收银员虽然走开了，但**厨房钥匙只有一把**，后厨炒菜时前台照样开不了收银机。
- 把重活丢到**进程**里：相当于**另开一间厨房、另配一套钥匙**，前台完全不受影响。

**代价**：开进程比开线程贵得多（内存、启动时间）。所以代码里做了兜底 —— 进程池万一坏了，自动退回线程池，「慢但不坏」，而不是让用户看到报错页。

> **这个设计怎么被守住的？** 有一条测试专门检查这段重活**跑在哪个进程里**。曾经它是靠「测卡顿了多少毫秒」来判断的，但在 CI 服务器上误报过（机器调度抖动，不是代码变慢），后来改成直接查进程号 —— 详见 `TECH_DECISIONS.md` 的 TD-193。

#### ③ 为什么网页是「后端直接生成 HTML」，而不是用 Vue/React？

**大白话对比**：

- **前端框架（Vue/React）** = 餐厅给你食材、菜谱和一口锅，让你自己在餐桌上做菜。好处是菜能做花样，坏处是你得先有厨房（要装 Node.js、要打包、要构建）。
- **Jinja2 SSR（本项目）** = 餐厅直接把做好的菜端上来。浏览器拿到就是能看的页面。

**为什么这个项目选后者**：这是个**要上搜索引擎**的平台。搜索引擎的爬虫不喜欢「先下载一堆 JavaScript 再慢慢渲染」的页面。后端直接吐 HTML，爬虫一眼就能读到内容。

**不这样会怎样**：免费工具页搜不到 → 引流失败 → 整个商业模式的第一环断掉。

#### ④ 为什么「安检」要写得这么绕？—— 盖章 vs 重新填表

`app/middleware.py` 顶部有一段很坦诚的注释，记录了第一版的失败：

> 第一版用了框架提供的便捷写法（`BaseHTTPMiddleware`），功能全对，但客服接口从 14 毫秒涨到 **21 毫秒**，两条性能测试当场变红。

**比喻**：便捷写法相当于「每个客人进门，安检员都让他把入场表重新填一遍再核对」；现在的写法是「安检员只在原有表格上盖个章」。功能一样，开销差一大截。

**代价**：代码啰嗦、难读，所以那个文件里注释特别多。**这是典型的「用可读性换性能」，而且换的过程被记录了下来** —— 商业项目里这种记录比代码本身更值钱。

#### ⑤ 为什么「管理员权限」每次都查数据库，不写进登录凭证里？

**大白话**：登录凭证（JWT）像**演唱会手环** —— 上面写着你是谁、什么时候进的场，撕不下来也改不了，所以不用每次进门都查身份证。

但如果把「他是管理员」也印在手环上，就会出问题：**你把某人降权了，他手上那只旧手环还印着「管理员」，在过期前照样能进后台。**

所以本项目的做法是：手环上**只写你是谁**，「你是不是管理员」**每次刷卡都实时问人事部（数据库）**。

**效果**：降权**立刻生效**，不用等凭证过期。代价是每个请求多一次数据库查询 —— 用一点点性能换「权限变更即时生效」，在管理后台这种地方绝对划算。

### 1.6 行业里管这些叫什么

| 本项目的做法 | 行业术语 | 为什么是「标准做法」 |
| --- | --- | --- |
| 楼层（routers）/ 工坊（tools）/ 账本（models）分开 | **分层架构** | 改一处不会牵动全身；换数据库不用改页面 |
| 「申请表」和「账本」是两套定义 | **DTO（数据传输对象）** | 数据库里有的字段（比如密码）绝不能原样返回给用户 |
| 安检→登记→楼层，一层套一层 | **中间件洋葱模型** | 加新功能不用改老代码，套一层就行 |
| 38 项配置全放 `.env` 文件 | **12-Factor App 的第 3 条** | 同一份代码，测试环境和生产环境只换配置 |
| `/healthz` 与 `/readyz` 分开 | **存活探针 / 就绪探针** | 「活着」和「能接客」是两件事（见 1.7） |
| 417 条自动化测试 + 每次提交都跑 | **CI 持续集成** | 改坏了当场发现，不是上线后用户发现 |
| 每个取舍都编号记录在 `TECH_DECISIONS.md` | **ADR（架构决策记录）** | 半年后接手的人不用猜「当初为什么这么写」 |

## 第 2 课：登录与权限 —— 服务器是怎么认得你的

### 2.1 先说清楚登录在解决什么问题

HTTP 有个天生的毛病：**它没有记性**。你这一次请求告诉服务器「我是张三」，下一次请求服务器完全不记得你是谁 —— 就像每天去同一家便利店，店员每天都把你当新客人。

所以「登录」这件事的本质是：**给你一个随身携带、难以伪造的身份证明**，之后每次请求你都出示它。

整个流程只有两步：

```
① 你输入账号密码  →  服务器核对  →  发你一张「凭证」
② 之后每次请求，你都带上这张凭证，服务器验一下真伪就放行
```

难点全在第 ① 步发的那张凭证上。

---

### 2.2 生活比喻：演唱会手环

进场时工作人员核对你的票，然后给你**戴上一个一次性手环**。之后你在场内买饮料、进 VIP 区，都只看手环，不用再翻票。

这个比喻很准，但要看清它的四个细节：

| 手环的特点 | 对应到代码 |
| --- | --- |
| 上面印着你的名字和场次 | 凭证里写着「你是谁」和「什么时候过期」 |
| **戴上就撕不下来**，也没法自己画一个 | 凭证有防伪签名，改一个字符就作废 |
| 上面印的字**谁都能看** | ⚠️ 凭证内容**没有加密**，任何人都能读（见 2.4） |
| 手环有截止日期 | 默认 30 分钟后过期 |

---

### 2.3 密码：为什么数据库里根本看不到你的密码

**大白话**：数据库里存的**不是你的密码**，而是密码的「单向指纹」。

**实测**（在本地真的跑了一遍 `hash_password('123456')` 两次）：

```
第一次：$2b$12$e7yh1lzgog/aNC2Z4G72vuW.2r6DhVGdg7Fa8/8P9EMvpjfInfF.G
第二次：$2b$12$KxfhrIWXfBpFT0poda40/uG49O9uA4m5lhtkBTJLHPqQp62HFh1mS
```

**同一个密码，两次结果完全不同** —— 这不是 bug，这是设计。

**为什么要故意不一样？** 假设两个用户都用 `123456`，如果加密结果固定，攻击者拖走数据库后一眼就能看出「这两人密码相同」，还能拿一张预先算好的「密码 → 指纹」对照表（叫**彩虹表**）批量反查。每次都掺一点随机料（叫**盐**），这张表就废了。

**关键点：这个过程不可逆。** 你没法从 `$2b$12$e7yh...` 算回 `123456`。那服务器怎么验证你登录？

> 它**不算回**你的密码，而是把你这次输入的密码**用同样的盐再算一次指纹**，比对两个指纹一不一样。
>
> 生活比喻：**指纹锁**。锁不保存你的手指，只保存指纹图案；你来了它现场采一次比对。

**不这样做会怎样？**

- 存明文 → 数据库一泄露，全站用户密码裸奔。而且**大量用户在多个网站用同一个密码**，你的泄露会连累他们的邮箱和网银。
- 用 MD5 这类「快」的算法 → 攻击者用显卡每秒能试几百亿次。**密码存储必须故意慢**，`bcrypt` 就是为此设计的（那串里的 `12` 是「难度档位」，越大越慢）。

**落地文件**：`app/security.py` 的 `hash_password()` / `verify_password()`，底层是 `passlib` + `bcrypt`。数据库列 `sys_user.password` 长度 255，实测指纹 60 字符。

> **绝不自己写加密算法。** 这是行业铁律 —— 自己想出来的加密一定有你没考虑到的攻击面。

### 2.4 凭证（JWT）：拆开看它在电脑里长什么样

**大白话**：登录成功后服务器发给你的，是一串用两个点分成三段的字符串。

**实测**（真的签发了一张然后拆开）：

```
第 1 段（头部）  eyJhbGciOiJIUzI1NiIsInR5cCI6...  →  {"alg": "HS256", "typ": "JWT"}
第 2 段（内容）  eyJzdWIiOiJ6aGFuZ3NhbiIsImV4...  →  {"sub": "zhangsan",
                                                       "exp": 1788515449,
                                                       "pwd": 1788508800}
第 3 段（签名）  ZEi5MTlb3K0DxPRXjhgzqoWBM55h...     （二进制，读不出字）
```

#### ⚠️ 必须记住的一点：**第 2 段没有加密**

上面那个 `→` 右边的内容，是我用**任何语言十行代码**就能还原出来的。也就是说：

> **任何人拿到你的凭证，都能直接读出里面写了什么。**
> 只是他**改不了** —— 一改，第 3 段的签名就对不上。

**实测**：把凭证最后一个字符改掉，服务器的校验函数返回 `None`（即「无效」）。

**生活比喻**：手环上的名字是**明刻**的，谁都能看；但手环上有一个**防伪钢印**，你想把「张三」磨掉改成「李四」，钢印就花了，一眼假。

**所以凭证里绝不能放密码、手机号、身份证号。** 本项目的凭证里只有三样东西：

| 字段 | 意思 |
| --- | --- |
| `sub` | 你是谁（用户名） |
| `exp` | 什么时候过期 |
| `pwd` | 签发那一刻，该用户「上次改密码的时间」的副本 ← 这个是精髓，见 2.6 |

#### 为什么故意不把「你是不是管理员」放进去？

见第 1 课 1.4 ⑤：放进去就等于把职位**印死在手环上**，降权了旧手环照样能进后台。所以本项目每个请求都去数据库现查一次。

**落地文件**：`app/security.py` 的 `create_access_token()` / `decode_token()`。

### 2.5 凭证存在哪：为什么浏览器脚本读不到它

这是本项目真实做过的一次安全改造（`TECH_DECISIONS.md` 的 TD-44）。

**大白话**：网页里跑的 JavaScript 是**别人写的代码**。如果页面被塞进一段恶意脚本（这类攻击叫 **XSS**），那段脚本能读到的东西就等于攻击者能读到的东西。

两种存法的区别：

| 存法 | 恶意脚本能拿到吗 | 比喻 |
| --- | --- | --- |
| 存在 `localStorage`（很多教程这么教） | **能，一行代码就读走** | 把家门钥匙放在门口地垫下 |
| 存在 **HttpOnly cookie**（本项目的做法） | **读不到**，浏览器直接拒绝 | 钥匙交给门卫，你刷脸进门 |

所以本项目的登录接口**同时走两条通道**：

- **浏览器** → 收到 `Set-Cookie`，之后浏览器自动带上，前端代码全程碰不到凭证
- **API 客户端 / Swagger 调试页** → 从响应体里拿 `access_token`，手动放在请求头里

代码在 `app/routers/auth.py` 的 `_set_auth_cookie()`，四个属性每个都有讲究：

| 属性 | 值 | 为什么 |
| --- | --- | --- |
| `HttpOnly` | 是 | 脚本读不到 —— **这就是整件事的目的** |
| `SameSite` | `Lax` | 挡住跨站的写操作（防 **CSRF**：别的网站偷偷用你的身份提交表单） |
| `Secure` | **仅生产环境** | 本地是 http，加了这个浏览器根本不存 cookie，本地就没法调试了 |
| `Max-Age` | 与凭证同寿命 | 免得 cookie 活得比凭证久，反复撞「未登录」 |

#### `Lax` 是有代价的，而且这个项目把代价管起来了

`Lax` 只挡跨站的 **POST/PUT/DELETE**；跨站的 **GET**（比如从微信里点个链接跳过来）**照样会带上凭证**。

所以推出一条铁律：**凡是「会产生副作用」的接口，一律不能是 GET。**

**这条铁律不是靠自觉，是靠测试钉住的**：`tests/test_auth_cookie.py` 里有一份「需要登录的 GET 路由」清单，谁新增一个就会被测试拦下来，逼他解释「你这个 GET 为什么没有副作用」。

> 举个真实例子：下载已购文件这个接口，本来最自然的写法是 `GET /shop/download/xxx`。但它会把订单状态从「已付款」烧成「已下载」—— 这是副作用，所以最终实现是 **`POST /shop/download/{order_no}`**，并且有专门的测试验证「用 GET 请求会被拒」。

同一个测试文件里还有一条更狠的：它**真的用 node 跑了一遍前端页面的内联脚本**，并给 `localStorage` 塞了一个「一被碰就报错」的假对象。谁哪天又把凭证写回浏览器存储，这条测试当场炸。

> **静态搜一遍只能证明「现在没有」；真的跑一遍才能证明「这段代码的执行路径上没有」。**

### 2.6 三个灵魂拷问：这张凭证到底什么时候失效？

这一节全部有**实测结果**，不是推理。

#### ① 改了密码，之前所有设备上的登录还有效吗？→ **立刻全部失效**

**做法很巧**：凭证里带一个 `pwd` 字段，值是「签发那一刻，用户上次改密码的时间」。每次请求，服务器拿它和**数据库里的当前值**比一比：

```
凭证里的时间  <  数据库里的时间   →  说明这张凭证是「改密码之前」签的  →  拒绝
```

**为什么不用一张「已作废凭证名单」？** 那种做法（叫**黑名单**）要建表、要写入、要清理过期条目。用时间戳比大小，**零存储成本**就实现了「一次吊销该用户所有旧凭证」。

> 这正是「改密码」最主要的用途：怀疑密码泄露时，**光改密码而旧凭证还能用，等于没改**。

而且改密码接口会**返回一张新凭证**并替换掉 cookie —— 当前这次会话不该被自己踢下线，要踢的是**其他**设备。

#### ② 账号被封了，手上那张还没过期的凭证还能用吗？→ **不能，立刻失效**

**这一条曾经记错过。** `TECH_DECISIONS.md` 的 TD-70 原文暗示「封号后旧凭证仍有效」，后来被测试订正了 —— 现在 `tests/test_token_revocation.py` 里有一条用例专门钉住它，名字就叫 `test_disabled_user_token_is_rejected_immediately`：

```
1. 注册并登录，拿到凭证        → 用它访问 /auth/me  → 200 ✓
2. 把该用户的 status 改成 0（封号）
3. 用同一张凭证再访问 /auth/me → 401 ✗ 被拒
```

我本地实跑了这个文件：**15 passed**。

**为什么能立刻生效？** 因为第 1 课讲过的那个设计 —— 每个请求都要查一次数据库（本来就要查密码修改时间），顺手就把账号状态一起看了。**这就是「不缓存、每次查库」换来的好处。**

#### ③ 点了「退出登录」，那张凭证真的作废了吗？→ **没有**

这一条要**诚实说清楚**，因为它是本项目的一个已知取舍。

退出接口做的唯一一件事是：**让浏览器把 cookie 删掉**。服务端**没有记录**发出去过哪些凭证，所以也就没有「作废」这个动作。

**后果**：如果那张凭证在退出前已经被人偷走了，它在那 30 分钟内**仍然有效**。

**为什么接受这个取舍？** 要真正做到「退出即作废」，就必须维护一张黑名单表 —— 而那恰恰是 ① 用时间戳巧妙绕开的东西。**代价记在 TD-70 的粒度说明里。**

> 顺带一个有意思的设计：退出接口**故意不要求登录**。因为拿着一个已过期凭证的客户端也应该能把它清掉，否则用户会卡在「我明明点了退出，浏览器却还带着一个死凭证」的怪状态。

### 2.7 完整流程串起来

```
你输入 张三 / 123456
        │
        ▼
┌────────────────────────────────────────────┐
│ 限流闸门：这一分钟你试太多次了？先等等      │
├────────────────────────────────────────────┤
│ 查库找到张三 → 取出那串指纹                  │
│ 把 123456 用同样的盐算一遍指纹 → 比对        │
│   不一样 → 401「用户名或密码错误」           │
│        （故意不说清是账号错还是密码错，       │
│          否则这接口就成了「猜账号」工具）     │
├────────────────────────────────────────────┤
│ 检查 status：被封了？→ 403「账号已禁用」      │
├────────────────────────────────────────────┤
│ 签发凭证：{sub: 张三, exp: 30分钟后,          │
│            pwd: 上次改密码的时间}             │
├────────────────────────────────────────────┤
│ 两条通道一起给：                             │
│   浏览器     ← Set-Cookie（HttpOnly）        │
│   API 客户端 ← 响应体里的 access_token        │
└────────────────────────────────────────────┘

之后每次请求：
   带上凭证 → 验签名 → 验过期 → 查库 → 验 status
            → 比 pwd 时间戳 → 取 role 判断权限 → 放行
```

### 2.9 行业里管这些叫什么

| 本项目的做法 | 行业术语 |
| --- | --- |
| 单向指纹 + 盐 + 故意慢 | **密码哈希（password hashing）**，`bcrypt` 是主流选型之一 |
| 三段式、带签名、内容可读 | **JWT（JSON Web Token）** |
| 内容不加密、只防篡改 | **签名（signature）而非加密（encryption）** |
| 每次请求都要出示凭证 | **无状态认证（stateless auth）** |
| 服务端不记会话 | 与 **Session/Cookie 有状态方案**相对 |
| 脚本读不到的 cookie | **HttpOnly cookie** |
| 挡跨站写操作 | **CSRF 防护**（靠 `SameSite`） |
| 挡注入脚本偷数据 | **XSS 防护**（靠 HttpOnly + CSP） |
| 返回信息里剔除敏感字段 | **DTO 白名单**（`UserOut` 只有 4 个字段，**不含 password**） |
| 「一次操作最多试几次」 | **限流 / 防暴力破解** |
| 登录失败不透露具体原因 | **防用户枚举（user enumeration）** |

### 2.10 术语白皮书（第 2 课）

| 术语 | 大白话 | 生活比喻 |
| --- | --- | --- |
| **哈希 / 指纹** | 单向压缩，算得出来但倒推不回去 | 指纹锁：不存手指，只存图案 |
| **盐（salt）** | 每次掺一点随机料，让相同密码产生不同结果 | 同一道菜，每家放不同的香料 |
| **彩虹表** | 攻击者预先算好的「密码 → 指纹」对照表 | 一本万能钥匙对照册 |
| **JWT** | 三段式的防伪身份凭证 | 演唱会手环 |
| **签名** | 防篡改的防伪印记（内容仍可被阅读） | 手环上的钢印 |
| **加密** | 让内容变得读不懂（与签名是两回事） | 把字放进保险箱 |
| **XSS** | 攻击者往网页里塞进自己的脚本 | 有人在你的公告栏贴了小广告 |
| **CSRF** | 别的网站偷偷借用你的身份提交操作 | 有人拿着你的印章去盖章 |
| **HttpOnly** | 这个 cookie 脚本读不到 | 钥匙交给门卫，不放地垫下 |
| **SameSite=Lax** | 跨站的写操作不带凭证 | 出了这个商场，印章就不认了 |
| **黑名单** | 记录「哪些凭证已作废」的清单 | 挂失名单 |
| **无状态** | 服务端不记你是谁，全靠你每次出示凭证 | 每次都看手环，不认脸 |
| **限流** | 单位时间最多试几次 | 输错三次锁卡 |
| **用户枚举** | 通过报错差异猜出「哪些账号存在」 | 挨家敲门看哪家有人应 |
| **role / 角色** | 你是普通用户还是管理员 | 工牌上的岗位 |
