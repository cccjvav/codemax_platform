# 管理员订单与收款工作台

入口：站点顶栏 **订单管理（管理员）**，地址 `/admin/payments`。普通用户和未登录者只能看到登录外壳；订单、核账依据和流水由管理员专用 API 返回，不在公开 HTML 或 sitemap 中。页面和数据响应均 no-store；这不是浏览器、代理和设备上的绝对防留痕保证。

## 1. 先知道这里能做什么

像一个“查原单、翻签收条、记录核对过程”的柜台：

- 查找所有订单、人工待核账单、微信未结算单、尚未绑定的历史单，以及**有过异常记录**的订单。每页最多50条，精确订单号可定位；最后一页满50条时下一页可能为空。
- 查看冻结合同、交付文件摘要、唯一收款凭证、发起人和过程事件；更早事件也按50条翻页。刷新只是读，不发起查单或确认。
- 输入真实参考流水、实际整数分和核账依据，确认人工到账。
- 核实历史合同后一次性绑定原支付渠道与原文件，不套用今天的商品配置。
- 对已绑定且商户/应用与当前微信凭据一致的订单主动查单。外部请求是 GET；本站入口是 POST，因为它会记录核查事件，可信成功时还会补记收款。

**不能做的事**：发起扣款、自动批量关单/发送退款、导入渠道日账单、自动财务异常结案、开票、完整会计报表、定制开发报价/里程碑签收。显式渠道关单见第十六批；默认关闭的系统退款凭证登记见第十三批，二者都不是无条件自动执行。`REFUND` 不等于退款已完成；普通交易REFUND观察不撤权；下面独立全额退款核验成功后会停止该订单后续下载。正式收费上线仍需完成这些流程及真实商户验收，不是有了页面就能签收。

## 2. 登录、搜索与核对

1. 用受控管理员账号登录。新测试库管理员按数据库指南 `bootstrap-admin` 创建，没有默认口令；不要给普通账号绕过角色检查。
2. 先选择范围；需要定位时填完整订单号。微信未结算含 pending/closed 且无收款凭证的微信单，并不表示这些订单一定没付款。
3. 点击订单，核对客户ID（左侧列表另有用户名）、产品名、合同金额、原渠道、商户与文件摘要。
4. 查看凭证与事件。`prepay_started` / `query_started` 没有后续结果表示进程可能中断，不能猜成失败；历史异常筛选不会因一次正常查询而删除旧证据，也不是待办已结案标记。
5. 必要时打开站内客服，按列表中的客户账号联系。你本人可以作为客服回复；平台没有外部客服、邮件/短信通知或保证实时在线。

## 3. 人工到账确认

仅当前配置和原订单均为 manual、订单 pending/closed 且没有凭证时显示操作。

1. 在独立、真实的收款记录中核实金额和归属，不只看客户截图。
2. **手动输入当前完整订单号**；填写单行3–500字核账依据。不要放密钥、口令、完整银行卡号等无关信息。
3. 填真实唯一参考流水和**实际收到的整数分**。例如199元是19900分；页面不会自动填一个看起来已核对的金额。
4. 再检查弹窗内的订单、客户ID、金额、流水后确认。
5. 查看凭证中的来源、流水、首次发起人和本地入账时间。人工付款时间未提供时保持空，不假造银行时间；凭证不是发票。

请求超时或响应丢失时先刷新记录。不能另造流水强行重试；原记录已提交则页面应显示凭证并隐藏重复确认表单。完全相同的接口重试不新增收入；冲突409保留原证据。浏览器关闭/退出/取消请求，不保证撤销服务端已提交操作。

## 4. 主动查微信原订单

先经可信渠道配置真实商户私钥/证书序列号、平台证书或带ID的微信公钥、商户/app、APIv3密钥和回调地址。不要拿商户私钥当平台验签公钥；平台密钥轮换需维护本地可信配置，程序不跟随应答下载任意新密钥。当前为保守配置门禁，查单也要求整套支付凭据齐全。暂停新微信下单、切到其他全局支付模式后，仍可查询与当前凭据匹配的已冻结微信单。

输入确认单号和原因，点“核查这个原订单”。程序先提交 `query_started`，释放数据库锁后请求微信；回来后重新锁定并核对管理员角色、启用状态和凭据版本。

| 结果 | 当前处理 |
| --- | --- |
| 可信且完整匹配的 SUCCESS | 原单金额/CNY、商户/app、订单号、NATIVE、流水及带时区付款时间全部校验；成功事件、唯一凭证和paid同事务提交。已有同一凭证只追加本次核查事件，不覆盖首次发起人 |
| NOTPAY / CLOSED | 只记录本次观察；不关闭本地单。已有paid/downloaded则记冲突，不撤销权益 |
| REFUND | 记退款观察，人工继续跟进；请转独立退款核验入口，普通查单本身不撤权 |
| 未签名、验签/身份/字段错误、超时、404、429、其他HTTP错误 | 502并记录unknown；不当作未付款。进程或提交故障可能仅留started，仍按未知处理 |
| 可信成功但与原凭证冲突 | 409，保留原凭证，单独提交冲突事件 |
| 核查期间管理员被降权、停用或改凭据 | 403，记录aborted，不据此补记收款；可由有权限的人重新核对 |

网络限制：固定微信主域名，不跟随重定向，拒绝压缩应答；最多64KiB，每个HTTP阶段10秒、整个交换20秒。应答四个签名头必须单值有界，时间偏差不超过5分钟，按**原始UTF-8字节**验签，签名探测也必须拒绝。所有非200应答即便验签成功也不推断未付款。SUCCESS要求完整金额；未付观察可缺少可选字段，但给出的金额/币种必须匹配。

单号只支持本项目生成的ASCII字母、数字、下划线、连字符，最多32字。异常历史编号需另行核实，不扩展成任意路径请求。查单使用独立 `payment-reconcile` 限流桶，配额沿用 `RATE_LIMIT_TOOLS` / `RATE_LIMIT_WINDOW`；内存限流不等于多实例共享配额。

## 5. 历史合同绑定

选择“历史合同待绑定”。仅在已核实**原支付渠道、原商户和原交付文件**后，填写确认单号、依据、渠道和存储根目录内原文件的相对路径。微信渠道会绑定当前可信配置，必须先确认它就是原商户；文件将冻结为可校验快照。页面只提供 manual/wechat，不提供生产模拟支付入口。

绑定不可重复或覆盖。已付历史单可以恢复经核实的文件合同，但不会凭空创建收入凭证；本页也没有“把已付无凭证历史单伪装新到账”的按钮。凭证缺失的财务历史解决方案仍待后续。文件缺失/损坏时按交付恢复指南找回相同字节，不换成新产品。

## 6. 权限与操作边界

十一种管理员财务写操作（含复核、两个退款核验、本地准备、独立授权及显式发送）都核验管理员，并额外核验浏览器 Origin/Fetch Metadata；不接受外来或同站不同源页面的Cookie财务写请求。有效Bearer API客户端仍走显式令牌通道，非法Bearer不会回退Cookie。兼容无来源头的非浏览器Cookie客户端；这不是完整CSRF token系统，不能宣称防任意被盗Cookie。生产比较配置的canonical来源，开发按实际/可信代理来源，不能为解决错误而信任任意转发头。

前端用会话、列表和详情序号抛弃迟到响应，换账号清除数据和输入；403/401清屏。它不替代后端角色检查，Node VM也不替代浏览器验证。

## 第五批补充：把历史异常分成待复核与当前已复核

现在增加两个范围：**需要复核 / 继续跟进**、**当前进展已复核（非已退款）**。原“有历史异常”仍是历史检索，不因为复核完成就删掉异常证据。

1. 打开待复核范围，点选原单，核对原合同、凭证和各次尝试记录。超60秒仍无对应结束记录的prepay/query开始事件会被发现；这表示未知，不是确定支付失败。
2. 手动输入完整单号，在共同依据栏写3–160字单行复核说明；不要填密钥、完整银行卡号，或把未发生的退款写成已完成。其他人工到账/绑定操作仍允许原来的3–500字依据。
3. 在“处理进度”选“记录跟进”保留待办；完成**本轮资料核对**后可选“完成本轮复核”；需要继续处理则“重新跟进”。弹窗明确不确认到账/退款，也不改变下载权。
4. 保存后看复核人、时间和说明，并刷新左侧清单。没有自动分派、到期提醒或外部通知；你本人仍可通过站内客服联系客户。无渠道异常的订单也能主动登记跟进。
5. 出现新资料后旧完成标记自动失效，包括新的支付/查询事件、到账凭证、订单状态变化，以及未结束尝试到达60秒。状态“有新进展”不一定代表更严重，也可能是付款已经到账，需要你核对新资料。重复的成功查单也是新记录。

**并发与重试**：页面带当时的资料摘要和复核版本，别人处理或资料更新后旧提交409，刷新重新核对。请求ID绑定原单/操作者/内容，丢响应时保留原内容重试，不增加第二条；若刷新已看见本次记录则不用再提交。修改未确认请求的内容会被页面拦住；应先重试原请求或重新选单核对历史后再开始新操作。退出/abort不能撤销已提交的服务端操作。

**分页**：每次返回最多50张、最多筛200张候选；空列表带“下一页”并不代表全局没有待办。换筛选条件不会继承旧范围游标。聚合历史仍有数据库开销，未做生产容量认证。

**存储与可信范围**：复核是现有PaymentEvent的一条`operator_review`记录，证据列保存v1 JSON（动作、上轮版本、资料摘要、说明），原始历史仍可读。摘要包含事件数量与最大ID，不能只看编号：数据库序列号可能提前分配、晚些提交。读取不创建/关闭任务；并发追加资料后，下次读取会使过期的完成标记失效。四次批量读取不是全库强一致快照，不承诺页面永久显示瞬时最新事实。坏格式/缺发起人的记录不算已完成，且原内容仍保留。

复核不等于资金问题已解决，尤其REFUND仍需完整退款流程和真实渠道证据。此阶段没有新增数据库迁移/应用依赖；不要为了使用待办界面重建业务库。

历史事件按记录ID倒序展示，不是事务提交时间排序。第六批已将RefundReceipt加入复核摘要，并覆盖退款尝试老化；未退款凭证保持旧摘要编码兼容。

## 第六批：已经办理退款后，单独核验并停止下载

本批只处理**当前单文件订单的一笔全额退款**：不支持部分退款累计、退款至其他账户或定制服务里程碑取消，不会调用发起退款API。原收款凭证必须存在且与订单匹配；缺失历史凭证不能凭空补写退款。先完成0011迁移，不能重建业务库。

### 微信已办理的全额原路退款

1. 管理员核对原订单、客户和原商户/应用及付款流水。在原渠道按实际审批办理退款，取得**商户退款单号**；本站的独立授权/显式申请见第九批（默认关闭），也可核验在原渠道外部办理的退款。不要把付款订单号或微信退款ID当作此字段。
2. 打开该订单，输入完整订单号与3–160字核验理由，在退款区填商户退款单号，确认后查询。只GET普通商户接口，平台应答必须验签；不自动轮询，建议至少间隔一分钟，长期处理中逐步降低频率。
3. SUCCESS且原订单/交易/退款号、全额、CNY/ORIGINAL和成功时间均通过核验，才保存成功凭证；状态PROCESSING/ABNORMAL/CLOSED只是观察，会进入待复核，保留下载权。404/超时/坏签名/部分退款等返回未知，不认定退款完成或没发生。
4. 再看成功退款凭证区和客户订单记录。原收款/paid或downloaded保留，refunded独立为真；其他订单不受影响。即使迟到付款通知或后来查询又报处理中，也不会删除退款凭证或恢复下载。

微信这里的金额是合同退款总额，不等于用户现金退款额、净结算额或手续费返还；暂未建立优惠券与净结算会计账。接口出处：[普通商户查询](https://pay.weixin.qq.com/doc/v3/merchant/4012791884.md)、[申请规则](https://pay.weixin.qq.com/doc/v3/merchant/4013071036.md)。申请接口返回受理并不代表退款成功，本批没有实现该POST。

### 人工收款的已完成全额退款

先在实际渠道退回并核实，之后在本页填写**退款**流水（不是付款流水）、整数分及真实成功时间，例如2026-09-17T15:00:00+02:00。时区必须对应真实记录，不要把丹麦时间当中国时间；金额必须等于原合同全额。依据不要放完整银行卡号/密钥。确认会写不可覆盖退款凭证并停止后续下载，但不会替你转账；管理员有责任核实实际退款，自动测试不能验证你的银行记录。

相同资金事实重试保留首次凭证/人/时间；改流水、金额或成功时间不能覆盖旧记录。网络失败先刷新，再用原内容重试，不另造流水。原人工订单即使当前SHOP_PAY_MODE已切微信，仍按原人工凭证登记；微信/mock单不能借此人工退款。纠错当前需另行受控方案，不提供改库或一键恢复下载。

### 旧链接与验收边界

所有旧key-only链接升级后403，未退款购买权益保留，可在“我的订单”重领绑定订单的短链。退款提交后的新授权/重领被拒绝；已接纳传输、浏览器外缓存与已经下载的副本无法召回。签名链接有效期内仍可转交。退款接口不是客户自助申请页，客户疑问由站内客服中你本人接待。退款通知现在仅作为已验签的待核验线索留存，见下节；自动补偿、部分退款记账/权益规则、真实商户与本机浏览器验收仍须后续执行。


## 第七批：收到微信退款通知，不等于本地已确认退款

`POST /shop/refunds/notify` 是普通商户退款通知接收地址，与收款 `/shop/pay/notify` 分开。依据2026-09-18核对的[官方退款通知协议](https://pay.weixin.qq.com/doc/v3/merchant/4013071196.md)：回调没有channel、currency和appid，不能凭SUCCESS推断ORIGINAL。本站用原订单/收款绑定商户、应用和CNY，但仍须第六批的独立查询取得原路退款证据。

1. 通知先核验四个单值签名头、可信平台身份/时效、原始正文RSA签名，再AES-GCM解密、核对内外状态及原付款。只接SUCCESS/ABNORMAL/CLOSED；PROCESSING不是当前文档列出的通知事件。金额是严格整数合同分；payer金额仅校验界限，不冒充净结算账。
2. 合法且能对应本地真实微信收款的通知提交到现有PaymentEvent，固定种类`refund_notify_signal`，之后才204空响应。商户+通知ID确定幂等键；同ID同事实重试204不新增，改变事实/归属409。加密随机数、签名和不保存的账号显示可以不同。没有原付款凭证、错误商户/应用或金额的通知不能被凭空认领。
3. 管理员主动打开“需要复核”范围并刷新；通知使当前已复核标记过期，精确重发不会再次打开已复核记录。详情显示最新**本地记录ID**的有效摘要，事件分页不影响摘要；不是按渠道状态优先级或业务完成时间挑“最终状态”。所有历史仍在事件列表，坏摘要不会退回旧摘要冒充最新。
4. 全额通知可点“填入最新全额通知的商户退款号（不提交）”，只填退款号，不填确认单号/依据，也不发送查询。手动核对并按上一节显式查询；查询可信SUCCESS才会生成成功退款凭证和停止下载。已存在成功凭证时，以该凭证为准，后来CLOSED/ABNORMAL通知不会恢复权益。
5. 部分退款通知只留待办、标明当前不支持自动核验/权益计算，不提供快捷填号；这不代表已支持部分退款申请、累计或纠错。你需在原渠道核账并通过站内客服处理客户问题，不能手工把部分金额改成全额骗过核验。

**故障与部署**：最多64KiB、拒绝压缩；整个读取/保存设4秒应用预算，为官方5秒应答要求留余量，不等于代理、数据库拥塞和生产负载已测达标。未配置503、验签/协议400、过大413、压缩415、业务冲突409、数据库/超时503；失败会让渠道重试。提交成功但响应丢失，原ID重发可安全确认。没有先204再靠内存任务处理，也没有回调内同步查询外网。数据库故障时不伪造成功；不承诺一定能收到所有渠道通知，仍要主动查询。

**接入限制**：当前已有第九批默认关闭的显式申请API，没有自动发送消费者；只读核验worker见第十一批，本地准备见下节。退款通知地址可在微信商户平台“交易中心→退款管理→退款配置”登记，或由外部申请流程显式传无参数的 `notify_url` 覆盖平台配置；必须真实配置到本站独立HTTPS地址才可能收到对应通知。仅部署本路由或修改`WX_NOTIFY_URL`不能让历史退款自动补发。不要把收款回调地址改成退款地址。复用可信WX商户/app/APIv3/平台凭据，最初通知子项无新配置项/依赖/迁移；第十一批新增核验开关/0015，当前应用需完整账本至0017；不存银行卡显示、完整解密正文、密文或签名包，只存有界摘要和已验证字段的指纹。该指纹是冲突检测，不是可独立复验的RSA原文证据，也不是WORM。


## 第八批：先保存本地退款准备，不是向微信申请退款

升级至0012后，管理员可以为**尚无退款通知/退款查询/成功凭证、也无准备记录**的原微信收款登记一笔全额准备。不是客户自助申请，不支持人工/mock/无原凭证或部分退款准备；也不保证渠道期限、余额等条件已经满足。

1. 在原订单详情核对原收款、商户/app、金额，手动输入完整单号和3–160字单行内部依据，再填合同全额整数分。页面显示准备入口只是提示，服务端会重新检查。
2. 点击“保存退款准备（不发送）”，确认弹窗后只在本站保存准备与过程事件。服务器生成35字符的`CMR`开头商户退款号；客户端请求ID另用于恢复本地保存，**两个号码不是一回事**。没有发送退款、没有资金预留/划转、没有提前撤销下载，也不是同意以后自动退款。
3. 网络错误表示保存结果未知，先刷新原单。读到记录后保留该号码；未确认前用原内容重试，不改金额/依据、不开新号。不同管理员不能覆盖首笔，一单不能另造准备。即使后来已有退款通知或成功凭证，原请求重放仍可恢复首次准备；已产生的新事实不会被撤回。
4. 准备进入需要复核；完成本轮仅记录工作进度，不表示已发送。若只是登记错误或决定不继续，保留原准备并在复核说明中写清，不删除重建、不因此必须执行退款。此批不提供撤销/纠错及金额释放状态机。
5. “填入已保存的准备号”只填现有退款查询框，不提交。当前本站尚未向渠道发送这个号，因此查不到不能认定退款失败或允许换号。只有实际办理流程确实使用了同号，再按既有显式查询核验；如果渠道生成了其他号，查询那个真实号并核查关联，不能冒充与准备号相同。
6. 通知SUCCESS仍只是线索。仅独立查询形成匹配RefundReceipt后，准备展示“已有匹配成功退款凭证”；若实际是另一个号，展示“已有其他退款号的成功凭证”，保留原准备且禁用填号，不能另发一笔。下载仍只看成功凭证，不看准备。

**协议与后续**：2026-09-18再次核对[普通商户申请退款](https://pay.weixin.qq.com/doc/v3/merchant/4013071036.md)：重试须原商户退款号，受理不等于成功。此批只落实本地持久准备与保存幂等；未实现完整渠道请求快照、显式发送授权、发送尝试/租约或向微信发送后未知结果的恢复。内部依据160字符不是面向客户的微信reason（最多80字节），以后不得直接透传；也不得把所有历史准备自动送往微信。真实办理与接入另行授权，不能拿合成测试当银行/微信凭证。


## 第九批：独立授权与显式向微信申请

当前代码已提供可能转出真实资金的发送入口，但WX_REFUND_SEND_ENABLED默认false；部署、真实商户、备份恢复尚未签收，不要为了试按钮开启业务环境。开发测试全部合成；本次没有替你执行真实退款。

1. 先有第八批原准备，且没有独立退款通知/查询/成功凭证。手输原订单号、固定CMR退款号、全额分数、内部依据；客户可见reason另填，最多80 UTF-8字节（27个常见汉字已超限），不要复制内部依据或敏感资料。
2. “冻结请求并独立授权”只保存，不发送。检查展示的完整正文、客户reason、原商户、回调URL与摘要。回调从当时SITE_BASE_URL派生，之后配置改变不会改旧正文；误填或迁移域名没有就地纠错接口，先停止发送并人工跟进，不删表重建。
3. 只有部署显式开启发送后才出现发送按钮。当前管理员还须再次确认原号/金额/完整请求；此动作可能真实转款。发送前先保存尝试，之后无数据库锁跨网络。旧准备/授权不会自动消费，无后台发送任务。
4. 网络失败/进程中断不证明未发送。同attempt_id恢复只读取已有记录，绝不再次发HTTP。若确需重试未知申请，用“未知时准备同号新尝试”按钮，再单独确认；服务端至少60秒，原正文/商户退款号不变。已受理（含CLOSED/ABNORMAL）、任一独立查询或通知、成功凭证均阻止重新申请。
5. 优先使用原号独立查询以确认金融结果。已有查询即使404/失败也保守阻止本站再次发送；本批没有“清除未知/删除事件/换号”按钮，需在原商户平台继续核查和受控后续处理。不能把本批称为全自动补偿闭环。
6. 申请应答即便SUCCESS仍只是观察，既有独立签名全额原路查询形成RefundReceipt后才撤销后续下载。登出/撤角色无法召回已经开始的网络请求；服务会保留其观察，但新的发送必须重新通过当前权限校验。所有历史进展进入复核，复核完成不是财务完成。

仍不支持部分累计、授权正文修改/重新启用、异常退款另号重开、定制服务取消、后台自动退款发送器或真实商户联调认证。


## 第十批：停止后续本站发送，不是撤回微信退款

发现客户原因/回调填错、决定暂不退款或需要人工核查时，可对已有独立授权登记永久停止。原版本正文/金额/商户退款号不修改，也不解除其停止；第十四批仅允许发送前另建显式后继授权，见后文。

1. 打开原单，核对完整授权；手输完整订单号、原CMR退款号和全额分数，共用内部依据填写停办/纠错原因，不填敏感账户资料。
2. 点击“停止后续本站发送（不撤回渠道退款）”并确认。默认发送开关关闭时也可使用，无须开启真实发送。
3. 成功后核对首次停止人/时间/依据；新发送和新尝试入口隐藏。保存失败先刷新，按同请求ID/内容恢复，不改未知依据、不另建授权/退款号。后续补充进展写已有复核说明，不能覆盖首次停止事实。
4. 停止与发送开始争用同一订单锁。**开始以started记录持久提交为界，不以HTTP是否已经抵达微信为界。** 停止先提交则禁止新开始；开始先提交的尝试仍可能继续转款，停止不保证召回。
5. 因此必须继续按原号查询/核账。即使停止后收到通知或签名申请SUCCESS，仍沿用独立全额原路查询确认成功凭证，再停止后续下载；不能把停止当成退款失败或恢复下载。旧attempt原样重放只读回，不会因停止而新发。

这是本地发送权限的永久停止及不可覆盖的纠错依据，不是完整取消/纠错系统；已有授权才能停止。准备、授权、停止、渠道观察和成功凭证分别保留。真实渠道取消/异常处理及发送后改正仍未支持；发送前重新授权见第十四批；默认关闭的系统成功登记见第十三批；只读核验队列已补，见下一节；需要时通过站内客服与原商户平台核查，不直接改库解除保护。


## 第十一批：通知后续核验队列

详情新增只读任务区：pending待核验；running附90秒租约（过期可恢复，不代表进程一定在线）；retry等待退避；verified表示查询SUCCESS、待管理员按原号独立确认；attention需要人工核账。显示原号、通知事件ID、次数、更新时间；最多最近50项，旧结果见事件历史。刷新读取，不会发送退款。

发送开关/本地停止不阻止只读核验。部分通知不查询全额接口；失败或PROCESSING最多8次领取、30秒起指数退避，之后转人工。未知/坏签名/404不等于没有退款；先在原商户核账，不能换号重退、删任务重置次数或篡改金额。修复配置后可按第十二批规则重排剩余次数；没有清零预算入口，耗尽仍需人工查询。

默认自动登记开关关闭时，查询SUCCESS仍不是后台授权撤权：用任务显示的原号在既有“独立核验”表单手工确认，重新取得成功结果才生成凭证；已有同原号成功凭证时页面注明。队列不伪造操作者，不自动转款；仅核验模式不恢复/撤销下载，显式系统登记模式见第十三批，不发送外部提醒。使用站内客服处理客户疑问。

结果码速查：queued待领取；querying已领取不代表进程在线；processing渠道处理中；success_needs_admin查询成功待管理员；untrusted_or_unavailable涵盖配置/网络/验签或不适用应答，不表示未退款；identity_conflict原退款ID不符；time_conflict成功时间不合规；invalid_or_partial_notice原通知/收款不适用或部分退款；exhausted领取次数耗尽。固定码不包含真实账户、原始响应或密钥。

## 第十二批：接管一个任务，而不是重置整个退款

像把一张待办从自动处理夹取出交给自己：在当前详情核对任务ID和原退款号，手动填写订单号、任务ID及3–160字依据，选“人工接管”并确认。该任务转manual_hold，已开始GET仍可能到达渠道，但旧结果不能覆盖接管；其他任务或新通知不被暂停。它不撤销退款、不改变下载权，也不关闭核验部署开关。

处理配置/人工排查后，若任务待人工、未满8次、通知对应原全额且无成功凭证，可选“重新排队”；只用剩余次数，不变原号、不重置历史。开关false仍只排队，不能把入队当成执行。已核验成功、耗尽或部分退款请走原号人工查询/原渠道处理；系统登记使用真实系统归属而非管理员冒名，且另有默认关闭开关，见下一节。

页面显示最近调度操作的人/依据/时间和当前任务状态，两者可能不同。刷新遇新进展会409，重新核对再确认；网络/503未知则保持原请求内容重试，不改key。服务端相同请求仅读首次动作，不会再次接管一个后来已重排的任务。记录与调度同事务保留，禁止直接SQL清次数/删历史。

接管的界线是持久领取，而不是HTTP到达渠道：领取已提交的尝试，即使尚未发出HTTP，也可能在接管返回后继续GET；接管保证不再领取该暂停任务，并使旧结果不能覆盖当前任务，不是网络召回。


## 第十三批：系统成功登记是单独的部署授权

这里的“自动登记”只是确认**已经完成**的全额原路退款并停止该订单后续领链，不是发起转账。三个开关分开：SEND控制既有显式人工发送入口；VERIFY允许独立worker GET查询；AUTO_RECORD允许本次可信SUCCESS查询登记系统凭证。三个默认均false，AUTO_RECORD不能越过VERIFY或给SEND授权。

先停旧Web/worker写入，备份数据库和storage并验证恢复，该子项新增0016，现行使用原CLI status/migrate到0017，历史SQL不得修改；本批未替你操作业务库。保持`WX_REFUND_AUTO_RECORD_ENABLED=false`是默认安全行为。只有运维明确接受系统登记会停止原订单后续下载授权、完成专用环境验收后，才在该环境将VERIFY和AUTO_RECORD设true，分别重启Web与**独立worker**；只重启Web不会更新worker配置。运行命令仍是`python -m app.refund_worker --once`或无--once常驻，第十五批提供本地监测/监督模板，仍未接外部告警送达。此部署授权不记录一个虚构管理员，不是页面上的开关或管理员会话授权；管理页显示Web配置，不代表工作进程在线/一致。

凭证显示“系统核验（非管理员代办）”及验证开始事件ID；数据库actor_id为空、固定system:refund-verifier、verification_event_id指向本次不可变开始事件。人工凭证保留真实管理员。系统凭证、success_recorded观察和verified任务同提交；同事实重复success_already_recorded不改变首次人/时间，冲突receipt_conflict转人工且不覆盖。原收款/paid或downloaded事实保留，另一个未退款订单仍可下载，已交付副本和已接纳传输不能召回。

通知SUCCESS、申请受理/POST SUCCESS、支付状态REFUND都不能代替独立验签GET的全额ORIGINAL/CNY SUCCESS。签名/配置错误仍退避，最多8次；人工hold使旧任务结果不能登记，但不召回已经领取的GET，也不暂停其他任务。关开关/改.env不是在途取消；需要按任务接管并核实当前结果。此前verified或attention不会因启用开关自动复活；verified/耗尽仍按原号管理员独立查询，符合条件的attention只能用剩余预算重排。部分退款、发送后纠错、渠道取消、外部提醒与真实商户签收仍未完成。


## 第十四批：发送前更正并重新授权

本功能只处理**本站尚未持久开始发送**的请求，不证明有人未在商户平台另行操作。原准备号和全额永不改；允许重新确认客户可见reason和当前SITE_BASE_URL派生的退款notify_url，不开放自填回调URL、改商户/付款流水/金额或换号。新增授权不发送；三个部署开关保持原默认false。

1. 打开原单核对准备与当前授权；如需更正，先用原授权ID/摘要/原号/全额登记停止，保存依据。
2. 仅最新授权已停止、整单没有任何发送开始/观察、独立退款查询/通知/核验或成功凭证时，才显示“确认更正并重新授权”。未显示不意味着可以改库解除。未知、已受理、查询过、在途及已完成一律不能走本入口。
3. 手动确认原号/全额、内部依据，填新的客户可见原因（1–80 UTF-8字节）。正式回调来自当前Web配置；若改域名，先按部署手册校验配置和可达性。确认弹窗只保存新的独立授权；原授权和原停止永久保留，新版显示前版本ID、正文、摘要、首次人/时间。
4. 如另有真实发送授权，仍须在新版本单独确认发送，WX_REFUND_SEND_ENABLED仍限制该动作。旧版本不能发送，不能把“重新授权成功”当退款完成。下载权与原收款不变。
5. 响应未知时保留原ID、前版本ID/摘要、原号/全额、原因和依据重试；后端先找首次记录，不随当前域名或后续版本进展重写它。响应authorization表示该原请求的记录，submission表示当前版本，两者可能不同。原初始授权/停止也能按原key读回，不影响新版本。

历史区独立于事件翻页，显示当前及最近50版/截断提示，更早操作看事件历史；这不是全历史正文下载器。换账号清空正文/输入/未知请求并拒绝迟到响应。只要发送开始曾提交，即使提交回执丢失且实际上尚未触网，也按未知拒绝改正文；继续原号独立核验，不凭“我没看到请求”重新授权。错误金额/原付款/成功凭证、部分退款、发送后纠错和渠道取消仍不支持。

## 第十五批：健康与告警不是财务结案

[核验运行手册](REFUND_OPERATIONS.md)提供本地状态/告警命令及可选监督模板。管理页仍不能证明worker在线；检测默认120秒滞后，不表示商户配置、队列清空或成功凭证。needs_operator可能来自你主动hold，query_retry可能仅是正常退避，均需按原单核查；不要自动重排或不断重启。没有短信/邮件或外部报警送达。本次新增监测不改变原号、授权历史、8次总预算或下载权益。

## 第十六批：先核查，再显式关闭原微信订单

只有原微信订单在本站已是closed、没有收款流水/凭证时才可能使用；不会把当前pending订单自动改成closed，也不会取消已付订单或退款。WX_ORDER_CLOSE_ENABLED默认false，开关不是自动关单任务；没有为本批开启生产开关。

1. 管理页选择原单，核对原商户、金额和历史，点“核查这个原订单”。只有最新可信NOTPAY、观察在5分钟内，才可出现独立关单按钮。CLOSED无需再关，SUCCESS按原收款流程入账，失败/REFUND不是未支付证明。
2. 门禁经专用环境验收且明确开启后，手输完整原单号、原合同整数分、3–160字单行依据，再确认关单。会影响旧码可支付性；不是退款，不改变下载权限或原收款。客户付款与关单可能竞争，不能承诺一定没付。
3. 结果acknowledged仅表示本站验过平台204空应答；unknown表示无法确认。两者都请另点原单查询，不由页面自动查/关/结案。可信迟到SUCCESS仍接受并保留原收款凭证；人工“完成复核”不替代资金结果。
4. 丢应答保留原请求ID、原query_attempt_id、原号、金额和依据重试，同key只读首次且不再发POST。改未知内容会被拒绝；刷新后的新查单不会悄悄改原命令。换账号清空内存正文，完整历史仍在事件台账，最新关单展示不受事件翻页影响。
5. 确有unknown需要新关单尝试时，必须先独立取得**晚于原start的新**可信NOTPAY且距原start至少60秒，再用新key单独确认；不是自动重试。任何已ack挡新发送。禁止换订单号、删事件或把404/ORDERPAID错误当关单完成。页面先恢复原尝试取得已记录结果，再新查单；如旧命令从未落库且查询窗口已过，原内容会409而不是重发。保留原ID/依据，在新的查单完成后重新选择原订单、手工重填并单独确认，服务端仍会重查资格；不要靠重载页面猜测原操作未发生。

这是单笔原单核查衔接，**不是渠道日账、批量对账、手续费核算或定制服务取消**。这些仍需后续设计及验收。
