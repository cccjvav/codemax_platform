# 管理员订单与收款工作台

入口：站点顶栏 **订单管理（管理员）**，地址 `/admin/payments`。普通用户和未登录者只能看到登录外壳；订单、核账依据和流水由管理员专用 API 返回，不在公开 HTML 或 sitemap 中。页面和数据响应均 no-store；这不是浏览器、代理和设备上的绝对防留痕保证。

## 1. 先知道这里能做什么

像一个“查原单、翻签收条、记录核对过程”的柜台：

- 查找所有订单、人工待核账单、微信未结算单、尚未绑定的历史单，以及**有过异常记录**的订单。每页最多50条，精确订单号可定位；最后一页满50条时下一页可能为空。
- 查看冻结合同、交付文件摘要、唯一收款凭证、发起人和过程事件；更早事件也按50条翻页。刷新只是读，不发起查单或确认。
- 输入真实参考流水、实际整数分和核账依据，确认人工到账。
- 核实历史合同后一次性绑定原支付渠道与原文件，不套用今天的商品配置。
- 对已绑定且商户/应用与当前微信凭据一致的订单主动查单。外部请求是 GET；本站入口是 POST，因为它会记录核查事件，可信成功时还会补记收款。

**不能做的事**：发起扣款、调用微信关单/退款、自动轮询补偿、导入渠道日账单、异常结案、开票、完整会计报表、定制开发报价/里程碑签收。`REFUND` 不等于退款已完成；本版本不会自动撤销已购下载权。正式收费上线仍需完成这些流程及真实商户验收，不是有了页面就能签收。

## 2. 登录、搜索与核对

1. 用受控管理员账号登录。新测试库管理员按数据库指南 `bootstrap-admin` 创建，没有默认口令；不要给普通账号绕过角色检查。
2. 先选择范围；需要定位时填完整订单号。微信未结算含 pending/closed 且无收款凭证的微信单，并不表示这些订单一定没付款。
3. 点击订单，核对客户ID（左侧列表另有用户名）、产品名、合同金额、原渠道、商户与文件摘要。
4. 查看凭证与事件。`prepay_started` / `query_started` 没有后续结果表示进程可能中断，不能猜成失败；历史异常筛选不会因一次正常查询而删除旧证据，也不是待办已结案标记。
5. 必要时打开站内客服，按列表中的客户账号联系。你本人可以作为客服回复；平台没有外部客服、邮件/短信通知或保证实时在线。

## 3. 人工到账确认

仅当前配置和原订单均为 manual、订单 pending/closed 且没有凭证时显示操作。

1. 在独立、真实的收款记录中核实金额和归属，不只看客户截图。
2. **手动输入当前完整订单号**；填写单行3–500字核账依据。不要放密钥、口令、完整银行卡号等无关信息。
3. 填真实唯一参考流水和**实际收到的整数分**。例如199元是19900分；页面不会自动填一个看起来已核对的金额。
4. 再检查弹窗内的订单、客户ID、金额、流水后确认。
5. 查看凭证中的来源、流水、首次发起人和本地入账时间。人工付款时间未提供时保持空，不假造银行时间；凭证不是发票。

请求超时或响应丢失时先刷新记录。不能另造流水强行重试；原记录已提交则页面应显示凭证并隐藏重复确认表单。完全相同的接口重试不新增收入；冲突409保留原证据。浏览器关闭/退出/取消请求，不保证撤销服务端已提交操作。

## 4. 主动查微信原订单

先经可信渠道配置真实商户私钥/证书序列号、平台证书或带ID的微信公钥、商户/app、APIv3密钥和回调地址。不要拿商户私钥当平台验签公钥；平台密钥轮换需维护本地可信配置，程序不跟随应答下载任意新密钥。当前为保守配置门禁，查单也要求整套支付凭据齐全。暂停新微信下单、切到其他全局支付模式后，仍可查询与当前凭据匹配的已冻结微信单。

输入确认单号和原因，点“核查这个原订单”。程序先提交 `query_started`，释放数据库锁后请求微信；回来后重新锁定并核对管理员角色、启用状态和凭据版本。

| 结果 | 当前处理 |
| --- | --- |
| 可信且完整匹配的 SUCCESS | 原单金额/CNY、商户/app、订单号、NATIVE、流水及带时区付款时间全部校验；成功事件、唯一凭证和paid同事务提交。已有同一凭证只追加本次核查事件，不覆盖首次发起人 |
| NOTPAY / CLOSED | 只记录本次观察；不关闭本地单。已有paid/downloaded则记冲突，不撤销权益 |
| REFUND | 记退款观察，人工继续跟进；没有退款调用和权益撤销流程 |
| 未签名、验签/身份/字段错误、超时、404、429、其他HTTP错误 | 502并记录unknown；不当作未付款。进程或提交故障可能仅留started，仍按未知处理 |
| 可信成功但与原凭证冲突 | 409，保留原凭证，单独提交冲突事件 |
| 核查期间管理员被降权、停用或改凭据 | 403，记录aborted，不据此补记收款；可由有权限的人重新核对 |

网络限制：固定微信主域名，不跟随重定向，拒绝压缩应答；最多64KiB，每个HTTP阶段10秒、整个交换20秒。应答四个签名头必须单值有界，时间偏差不超过5分钟，按**原始UTF-8字节**验签，签名探测也必须拒绝。所有非200应答即便验签成功也不推断未付款。SUCCESS要求完整金额；未付观察可缺少可选字段，但给出的金额/币种必须匹配。

单号只支持本项目生成的ASCII字母、数字、下划线、连字符，最多32字。异常历史编号需另行核实，不扩展成任意路径请求。查单使用独立 `payment-reconcile` 限流桶，配额沿用 `RATE_LIMIT_TOOLS` / `RATE_LIMIT_WINDOW`；内存限流不等于多实例共享配额。

## 5. 历史合同绑定

选择“历史合同待绑定”。仅在已核实**原支付渠道、原商户和原交付文件**后，填写确认单号、依据、渠道和存储根目录内原文件的相对路径。微信渠道会绑定当前可信配置，必须先确认它就是原商户；文件将冻结为可校验快照。页面只提供 manual/wechat，不提供生产模拟支付入口。

绑定不可重复或覆盖。已付历史单可以恢复经核实的文件合同，但不会凭空创建收入凭证；本页也没有“把已付无凭证历史单伪装新到账”的按钮。凭证缺失的财务历史解决方案仍待后续。文件缺失/损坏时按交付恢复指南找回相同字节，不换成新产品。

## 6. 权限与操作边界

四种财务写操作（含复核记录）都核验管理员，并额外核验浏览器 Origin/Fetch Metadata；不接受外来或同站不同源页面的Cookie财务写请求。有效Bearer API客户端仍走显式令牌通道，非法Bearer不会回退Cookie。兼容无来源头的非浏览器Cookie客户端；这不是完整CSRF token系统，不能宣称防任意被盗Cookie。生产比较配置的canonical来源，开发按实际/可信代理来源，不能为解决错误而信任任意转发头。

前端用会话、列表和详情序号抛弃迟到响应，换账号清除数据和输入；403/401清屏。它不替代后端角色检查，Node VM也不替代浏览器验证。

## 7. 在哪里验收

- 沙箱/CI：`python -m pytest -q tests/test_payment_queries.py tests/test_payments_admin.py tests/test_payments_frontend.py`。均为合成商户密钥/HTTP替身、独立数据库和Node VM，不访问真实支付账号。另运行全量SQLite与专用真实PG测试。
- Windows浏览器：见根目录新手指南的第四批补充。需实际检查登录、清屏、分页、确认弹窗、错误提示和两种屏幕布局；未执行不填写通过。
- 真实商户：部署到正确HTTPS域名，校准时钟和可信平台密钥；另行授权小额交易，在渠道后台核对真实流水/金额/回调/主动查询/丢失响应后的重查，并留脱敏证据。不要用测试流水替代真实到账，也不要在业务库跑pytest。

## 第五批补充：把历史异常分成待复核与当前已复核

现在增加两个范围：**需要复核 / 继续跟进**、**当前进展已复核（非已退款）**。原“有历史异常”仍是历史检索，不因为复核完成就删掉异常证据。

1. 打开待复核范围，点选原单，核对原合同、凭证和各次尝试记录。超60秒仍无对应结束记录的prepay/query开始事件会被发现；这表示未知，不是确定支付失败。
2. 手动输入完整单号，在共同依据栏写3–160字单行复核说明；不要填密钥、完整银行卡号，或把未发生的退款写成已完成。其他人工到账/绑定操作仍允许原来的3–500字依据。
3. 在“处理进度”选“记录跟进”保留待办；完成**本轮资料核对**后可选“完成本轮复核”；需要继续处理则“重新跟进”。弹窗明确不确认到账/退款，也不改变下载权。
4. 保存后看复核人、时间和说明，并刷新左侧清单。没有自动分派、到期提醒或外部通知；你本人仍可通过站内客服联系客户。无渠道异常的订单也能主动登记跟进。
5. 出现新资料后旧完成标记自动失效，包括新的支付/查询事件、到账凭证、订单状态变化，以及未结束尝试到达60秒。状态“有新进展”不一定代表更严重，也可能是付款已经到账，需要你核对新资料。重复的成功查单也是新记录。

**并发与重试**：页面带当时的资料摘要和复核版本，别人处理或资料更新后旧提交409，刷新重新核对。请求ID绑定原单/操作者/内容，丢响应时保留原内容重试，不增加第二条；若刷新已看见本次记录则不用再提交。修改未确认请求的内容会被页面拦住；应先重试原请求或重新选单核对历史后再开始新操作。退出/abort不能撤销已提交的服务端操作。

**分页**：每次返回最多50张、最多筛200张候选；空列表带“下一页”并不代表全局没有待办。换筛选条件不会继承旧范围游标。聚合历史仍有数据库开销，未做生产容量认证。

**存储与可信范围**：复核是现有PaymentEvent的一条`operator_review`记录，证据列保存v1 JSON（动作、上轮版本、资料摘要、说明），原始历史仍可读。摘要包含事件数量与最大ID，不能只看编号：数据库序列号可能提前分配、晚些提交。读取不创建/关闭任务；并发追加资料后，下次读取会使过期的完成标记失效。四次批量读取不是全库强一致快照，不承诺页面永久显示瞬时最新事实。坏格式/缺发起人的记录不算已完成，且原内容仍保留。

复核不等于资金问题已解决，尤其REFUND仍需完整退款流程和真实渠道证据。此阶段没有新增数据库迁移/应用依赖；不要为了使用待办界面重建业务库。

历史事件按记录ID倒序展示，不是事务提交时间排序。以后新增退款凭证等资金模型时，必须同步扩展复核摘要与失效测试；当前摘要不覆盖尚未实现的模型。
