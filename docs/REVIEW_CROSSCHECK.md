## 1. 如何判断两份报告的结论

- **本批已修**：有新增回归测试，且已验证旧实现出现预期失败；完整验收结果见末节。
- **确认／待修**：源码核实，或上一轮已有隔离复现；不代表当前环境已重新运行所有旧实验。
- **需纠正／部分成立**：根因存在，但报告中的严重度、覆盖范围或建议不能照搬。
- **待决策**：需要 schema、部署形态或产品约定；未经确认不擅自改表或改变已购权益。

上一轮临时浏览器／网络实验不等于生产验证。本轮新建的测试只用隔离数据库、MockTransport 和 Node；没有请求真实支付平台、商业 LLM 或内网目标。

## 4. 需要用户拍板的事项

### A. 数据库迁移与凭证兼容

建议允许新增可靠的用户凭证版本／语料修订机制，并同步 ORM、SQL、迁移和测试。仅用秒级时间戳或只清本进程缓存不足以覆盖并发、多实例。

需要确认：是否允许必要的 schema 迁移？安全升级时，是否接受现有登录会话统一重新登录？在此之前不改表、不改变现有 JWT 契约。

### B. 下载产品规则

建议选择“订单权益可恢复，短时签名链接可重试／支持 Range，领取和补发有审计”，而非严格一次 HTTP 请求；后者容易在断网／浏览器重试时误伤付费用户。

需要确认：已付款用户是否允许在期限内重新领取链接、期限多久、是否设置次数或人工补发？当前一次发链接即 consumed 的行为本批未改。

### C. 部署形态与 API 文档

需要确认：目标是单机单 worker、多 worker 还是多实例？入口代理是否唯一且不可绕过？生产要保留 `/docs`、`/redoc` 吗？

建议应用端口仅对可信入口开放、爬虫使用隔离出口。API 文档若保留，需独立受控资源／CSP；不能用放宽全站白名单来掩盖问题。新增自托管依赖需另获授权。

### D. 实际商品与客服承诺

需要确认：销售固定数字交付物、定制开发服务，还是两者都有？目前 FAQ 中开票、我的订单、真人接入等是否有仓库之外的实际承接流程？未确认前不能将文案变成虚假的功能完成承诺。

这些决策不阻塞继续修复纯解析、错误展示和文档链接等确定性问题。
