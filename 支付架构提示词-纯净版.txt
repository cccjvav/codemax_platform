我有一个已上线项目采用了下面这套支付+授权架构,想和你讨论能否移植到我们当前的项目。这套设计是从真实源码里逐行读出来的,请你**对照评估**,而不是直接照抄。

### 一、核心设计:客户端完全不碰支付

客户端(一个桌面 IDE 扩展)从头到尾**没有任何支付 SDK、没有任何商户凭证**。完整流程:

```
客户端                          自建服务端(Cloudflare Worker)         支付渠道
  │                                      │                              │
  │ 1. POST /v1/payments/orders          │                              │
  │    Authorization: Bearer <会话令牌>   │                              │
  │    { planId, paymentType: "alipay" } │                              │
  │─────────────────────────────────────▶│                              │
  │                                      │ 2. 调用渠道下单(密钥只在这里)│
  │                                      │─────────────────────────────▶│
  │ 3. { orderId, checkoutUrl, status }  │                              │
  │◀─────────────────────────────────────│                              │
  │                                      │                              │
  │ 4. 校验 checkoutUrl 合法性(白名单)   │                              │
  │ 5. 用【系统浏览器】打开它 ────────────────────────────────────────▶│
  │ 6. 轮询 GET /v1/payments/orders/{id} │                              │
  │─────────────────────────────────────▶│ 查询渠道 / 接收渠道回调 ◀────│
  │    status: pending→paid/failed/expired                              │
```

客户端只做四件事:**要链接 → 校验链接 → 交给系统浏览器 → 轮询订单状态**。

### 二、授权(entitlement)用签名令牌,不是"服务器说了算"

支付成功后不是简单地在服务端记一个布尔值,而是:

1. 服务端签发一个 **JWT 许可令牌**(license token),用 **Ed25519** 私钥签名
2. 客户端内置对应的**公钥**(编译进产物,公钥公开无妨)
3. 客户端**本地验签 + 校验 issuer / audience / 过期时间**,再决定功能是否放行
4. 令牌存在系统密钥库(`secrets` API),不是明文配置文件

私钥**只存在于 Cloudflare Worker 的 secrets 里**,从不下发。

### 三、功能门禁与离线宽限(这段设计我觉得最值得参考)

```
requireFeature("bridge"):
  1. 取本地缓存令牌 → 本地验签,得到 cachedClaims(可能为空)
  2. 尝试在线刷新 /v1/licenses/refresh
     ├─ 成功        → 放行
     ├─ 401/403/404 → 【删除本地令牌】并拒绝   ← 明确的"你没权限"
     └─ 其他错误(网络不通/服务挂了)
            ├─ 有仍然有效的 cachedClaims → 放行,仅记日志
            └─ 没有                      → 拒绝
```

要点:**区分"被拒绝"和"连不上"**。被服务端明确拒绝(401/403/404)就立刻清本地令牌;只是网络问题则用尚未过期的缓存令牌继续放行。用户断网出差不会被锁死,但退款/封禁能及时生效。

刷新请求会带一个 `installationId`(本机安装标识),服务端可据此做设备数限制。

### 四、登录不自建账号体系

用 **OAuth 第三方登录**(该项目用的 Gitee,也支持 GitHub):

- 客户端在 `127.0.0.1` 上起一个**临时本地 HTTP 服务**,随机端口
- 回调地址就是 `http://127.0.0.1:<随机端口>/callback`,带 `nonce` 防重放
- 换到会话令牌后本地服务立刻关闭

**好处**:不用做注册、密码、找回密码、邮箱验证这一整套,也不用存储用户密码。

### 五、服务端 API 清单(共 9 个端点)

```
POST /v1/auth/gitee              发起 OAuth
GET  /v1/auth/gitee/callback     OAuth 回调
POST /v1/auth/github             (备用登录渠道)
POST /v1/licenses/refresh        刷新许可令牌(带 installationId)
POST /v1/licenses/redeem         兑换码激活
GET  /v1/payments/plans          价格方案列表
POST /v1/payments/orders         创建订单 → 返回 checkoutUrl
GET  /v1/payments/orders/{id}    查询指定订单
GET  /v1/payments/orders/latest  查询最近一笔订单
POST /v1/usage/report            用量上报
```

订单状态机只有四个:`pending` → `paid` / `failed` / `expired`。
