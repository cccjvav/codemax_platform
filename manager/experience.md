## 外部依赖：网页可达与进程 API 联调必须拆分

- 日期：2026-09-13；标签：TLS、模型、授权、验收。
- 场景：用户授权远端用所给 key；网页抓取能见到 API 的 token-required 响应，而 Python/httpx 和 curl 在 TLS 阶段断开。
- 根因边界：尚未定位具体网络设备/服务方策略，不能断言是哪一方故障。它发生在 HTTP 前，不能判 key 权限，更不能用营销页上的名称替代模型 ID。
- 处理：带凭证请求只发到用户指定的 HTTPS 提供方；诊断再用不带凭证的请求。记录网络异常、协议层与未完成能力；不绕证书、不把密钥发到第三方代理、不循环消耗额度。
- 预防：显式探测工具拆开 models/chat/mermaid/embeddings，复用真实 LLMClient；默认测试只用 MockTransport。向量返回有效还须另测 FAQ 标定，Mermaid 前缀有效还须浏览器渲染。
- 证据：[本轮阶段](stages/windows-acceptance.md)、[新手指南](../Windows新手逐步验收.md)、`tests/test_probe_llm.py`。

## 能力与免费额度：失败不证明不存在，价格表不等于上线资格

- 日期：2026-09-13；标签：Agnes、embedding、诊断证据、免费服务。
- 场景：用户质疑“未找到文档”是否被说成“不支持”；带 Secret 的聊天成功，聊天 ID 的向量请求返回 HTTP 500，日志下载通道又受限。

- 选型：分开记录开源本地推理无 API 费、云端免费额度、账号/地区/数据条款和实际集成效果；不把模型卡当成托管免费价格证明，也不在新手项目悄悄增加服务/依赖。

## 第二批元复盘与技能进化（2026-09-15）

初始化保护不能只改函数：Compose自动挂载、Docker排除SQL、当前目录.env、Windows教程都是实际调用路径。本批逐一同步；跨连接事务锁、失败回滚、签名有效但业务身份错误是关键反例。现行workflow由2.2升2.3、schema-sync由2.1升2.2，删除“当前full_init一定DROP”的过期前提，保留历史版本/测试清库警告，权威源与manager副本同步。其余Skill无需变化，未修改不可访问的全局源。后续回看完整schema对照、真实恢复与财务事件；当前证据集中[第二批](../review/RELEASE_BLOCKERS_PHASE2.md)。

第二批收尾教训：下单配置齐全不代表能处理回调；预支付前需验证本地平台凭据和解密密钥。补上这个门禁后完整重跑双后端，而不是继承补丁前全量结果；7种反例仅在测试进程内替换，避免与并行全量测试相互污染。

第三批教训：数据库事务测试不能让多个会话共用一条SQLite连接；原支付信息保护不能把不同流水吞成幂等成功；迁移基线不能跟随最新ORM增列而漂移；已购文件不是当前配置。按本批实际反例保存证据并按最终提交验证，不把触发器/文件快照说成防DB管理员篡改或完成财务合规。

第三批收尾发现同用户5次并发下单会先重复复制、把两槽挤满。改为复制前持数据库用户锁，外部网络前释放；完整双后端重跑而非放宽全200断言。路径保护必须用规范化后位置，不能只检查字符串前缀。

取锁的同值UPDATE也会触发SQLAlchemy的onupdate；显式保留update_time并用旧时间哨兵验精确重放。移除此保护的第10种反例被拒绝，最终功能再次双后端全量通过，细节集中第三批报告。


## 第四批元复盘（2026-09-17）

- 原“HTTP 200+二维码字段”未核验服务商应答；补验签后把旧格式负例也换成有效合成签名，避免所有坏JSON测试都在缺签名处提前失败。成功路径必须走真实密码学，不能只替身返回成功对象。

- 读取旧README时发现若干当前正文仍说商品未冻结/full_init删表；只追加新阶段会留下矛盾，本次直接改当前段落，不改写历史报告。

第四批晚审发现HTML pattern使用Unicode Sets的v标志，普通JS正则中合法的字面斜线/连字符写法在浏览器表单中会失效。用Node v构造确认缺陷、修模板转义并加实际匹配回归；最终双后端重新运行，不沿用此前全量。另审计命中沙箱新建环境旧pip/setuptools，仅升级忽略环境中的引导工具，不新增应用依赖/忽略项。
